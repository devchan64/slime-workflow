# 생성 요청

1. 원하는 산출물과 해당 서비스, 입력과 참조 자료를 확인하고 불명확한 필수 값은 질문한다. 가정과 기본값은 구분한다.
2. 현재 지원 기능은 capabilities와 원본 서비스의 계약을 확인한다. 기존 작업을 다시 사용할 때는 원본 ID와 입력을 확인한다.
3. 제공된 서비스별 제안 형식과 검증을 따르고 직접 GPU 작업을 실행하지 않는다. 사용자에게 입력과 대기열 접수 확인을 안내한다.
4. 제안과 접수, 생성 완료 및 결과 품질을 구분한다. 접수 결과가 불확실하면 기존 접수와 원본 상태를 확인하고 자동 재접수하지 않는다.
5. Kimodo 등록 예제를 그대로 요청받으면 `/workspace/generators/kimodo/config/prompt-examples.yaml`에서 예제 ID를 확인하고 `HERMES_KIMODO_PROPOSAL` 블록에 `{"example_id":"확인한 ID"}`만 제안한다. 전용 폼에서 예제의 구간 프레임, 설정과 참조를 함께 불러온다. 예제를 네 필드로 축약하거나 임시 스크립트와 JSON을 작성하지 않는다. 격리 환경에서 runtime.py를 직접 실행하거나 접수했다고 주장하지 않는다. 실제 접수는 전용 폼에서 확인 후 이루어진다.
6. FLUX 이미지 요청은 용도에 맞는 개별 서비스와 필수 참조를 확인한다. 일반 이미지는 `flux-image`, 캐릭터·마네킨·빌보드·소품·식생·건물·심리스·표정은 해당 `flux-*` 서비스를 사용한다. 마네킨·빌보드·건물은 첫 참조, 표정은 등록된 표정 ID와 얼굴 참조가 필요하다. 심리스는 512×512 무참조다. 제안에는 이미지 본문을 넣지 않으며 사용자가 폼에서 참조를 선택한다. 모델 카드는 완전한 장면 설명을 권장한다. 요청 의도를 보존하면서 피사체, 구도, 배경과 조명 중 확인된 내용을 프롬프트에 담고, 불명확한 세부 사항은 임의의 확정 조건으로 추가하지 않는다. 자동 프롬프트 확장이 실행됐다고 주장하지 않는다.
7. FLUX.3 Image Klein Distilled 모델 카드 권장값은 16스텝이다. 제안은 16스텝으로 검증되며 생성 폼에서 실제 설정을 확인한다. 대화의 FLUX 제안에서 접수한 작업은 해당 제안과 세션 작업 목록에서 확인한다. 독립 생성기 화면에서 직접 접수한 작업은 대화에 자동 연결되지 않으므로 서비스와 작업 ID로 원본 상태를 조회하도록 안내한다.
8. 고용량 GPU 작업에서 Qwen 3.8 해제가 필요하면 대상 입력과 진행 중인 대화가 끝난 뒤 모델을 해제하고 생성 종료 후 다시 적재하는 순서를 설명한다. Kimodo·FLUX·Wan Fun·DWPose·VACE·HeartMuLa·Dasheng은 같은 대화의 생성 폼에서 입력을 검토하면 해당 상주 모델이 준비된 경우 해제·생성·재적재 동의가 표시된다. 사용자가 그 화면에서 명시적으로 확인해야 접수된다. 대화에서 동의했다고 대신 확인하거나 다른 프로세스를 종료하지 않는다. 지원하지 않는 작업에는 자동 양도나 재적재를 약속하지 않는다. 접수·생성 완료·Qwen 재적재 완료는 각각 실제 상태로 확인해 구분한다. 재적재가 확인 필요나 실패인 경우 원인을 안내한다.
9. Kimodo 키프레임 ID나 배치가 대화에 추가되어도 생성 폼에 자동 적용되었다고 말하지 않는다. 사용자가 생성 폼의 키프레임 배치 편집에서 해당 ID와 출력 프레임을 선택하고 원본과 배치를 검증한 뒤 적용하도록 안내한다. 생성 요청 검토와 대기열 접수 확인은 그 다음 별도 단계다. 원본이 변경되면 배치를 다시 검증한다.
10. Wan 2.2 I2V는 첫 프레임 이미지 1장과 동작 프롬프트를 받는다. 영상 제안에서 `service=wan22-i2v`, `mode=first_frame`을 사용하고 제안 확인 후 생성기를 열어 이미지를 첨부하고 설정을 확인하도록 안내한다. Lightning은 4스텝·CFG 1이며 KungFu는 선택 사항이다. 생성 접수와 결과 확인을 구분하고, GPU 양도가 지원된다고 가정하지 않는다.
