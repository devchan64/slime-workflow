# VACE-Fun 부분 편집 실험

## 권장 용도

이 생성기는 새로운 모션을 처음부터 만드는 용도보다 **이미 확보한 모션 영상을 편집·가공하는 용도로 우선 사용하는 것을 권장한다.** 원본 영상과 편집 영역을 지정하는 `video_edit` 또는 원본 영상 전체를 조건으로 사용하는 `video_condition`을 목적에 맞게 선택한다.

로컬 한손검 실험에서는 동작 영상 없이 첫 프레임과 프롬프트만 사용했을 때, 4스텝 Lightning·CFG 1~5 및 격투 LoRA 조합에서 한 걸음 전진하면서 베거나 연속으로 베는 동작이 일관되게 확인되지 않았다. 검 소실·배경 변화도 관찰됐다. 이는 해당 입력과 설정에 대한 관측이며 모든 모션 생성이 불가능하다는 뜻은 아니다.

기존 영상을 편집하더라도 모델이 원본 모션이나 외형을 그대로 보존한다고 보장하지 않는다. 편집 결과를 원본과 비교해 움직임·검과 손의 연결·배경·편집 영역 밖의 변화를 직접 검수한다. 아직 모션 영상이 없다면 별도 모션 생성 또는 제작 도구로 원본을 확보한 뒤 활용한다. 위 사용 권장은 이 워크플로의 실험 경험에 따른 것이며 공식 모델 카드의 권장 문구가 아니다.

## 사용 순서와 입력

참조 이미지, 첫 프레임 또는 제어 영상을 프롬프트와 함께 사용하거나 프롬프트만으로 영상을 생성한다.

1. 모델 준비 상태를 확인한다.
2. 생성 모드를 선택하고 화면에 표시되는 필수 입력을 첨부한다.
3. 장면·동작과 카메라, 출력 길이와 설정을 입력한다.
4. 요청을 검토해 접수한 뒤 현재 작업과 이력에서 진행 상황과 결과를 확인한다.

포즈 제어에는 DWPose MP4를 사용한다. 영상 입력은 832×480·16fps, 파일당 32MiB 이하이며 출력 길이는 입력 영상 이내여야 한다. 참조 이미지는 외형 조건으로 동작이나 첫 화면의 일치를 보장하지 않으며 첫 프레임 조건도 픽셀의 완전 일치를 보장하지 않는다. 영상 편집에서 흰 마스크는 재생성, 검정 마스크는 보존 조건이며 마스크 밖도 달라질 수 있다.


모델 관리의 `Wan 2.2 Videogame Fighting LoRA · High`는 제3자 공개 사본을 고정 리비전과 SHA-256으로 다운로드한다. CLI에서는 `python tools/manager.py command wan22-fighting-lora prepare` 및 `python tools/manager.py command wan22-fighting-lora model-status`를 사용한다. VACE 본체와 독립적으로 준비하며 선택한 작업에만 적용한다. 가중치 이름과 크기는 High 전문가와 일치한다. [원본 모델 정보](https://civitai.com/models/2093652/luisap-wan-22-videogame-fighting?modelVersionId=2368809), [다운로드 사본](https://huggingface.co/r4tn4/Bubble/tree/338e12cb179abf0573b61c310db6163018effdde).

`격투 + Lightning · 실험`은 격투 High와 LightX2V T2V V1.1 High/Low를 각각 대응 전문가에 강도 1로 병합한다. 모델 관리에서 두 LoRA 준비가 필요하다. GUI 또는 `wan22-vace generate` 요청의 `lora_mode: fighting_lightning`을 사용하며 4스텝·shift 5로 제한하며 CFG 1을 기본으로 하고 더 높은 CFG는 실험 설정이다. CFG 1에서는 부정 프롬프트 효과를 기대할 수 없다. LoRA 해시·병합 개수는 시도 폴더의 `lora-merge.json`에 남긴다. 기존 GPU BF16 상주, SDPA와 `expandable_segments:False` 정책을 유지한다. 2026-11-22의 5프레임 텍스트와 37프레임 포즈 시험은 완료했으나 번짐·포즈 차이 등 품질 문제가 관찰됐다. 세부 사항은 변경 기록을 참조한다.

`격투만 · 실험` 또는 `lora_mode: fighting`은 Lightning 없이 격투 LoRA를 High 전문가에 강도 1로 병합한다. 격투 LoRA만 준비하며 일반 스텝·CFG·shift를 사용한다. 격투 LoRA 강도는 0 초과 2 이하로 지정할 수 있고 기본값은 1이다. 격투 단독 GPU 생성 품질은 별도 검증이 필요하다.

`Lightning만 · 실험` 또는 `lora_mode: lightning`은 격투 LoRA 없이 같은 Lightning High/Low만 적용한다. 4스텝·shift 5를 사용하고 CFG 1을 기본으로 하며, 더 높은 CFG는 실험적으로 선택할 수 있다. Lightning 파일만 준비하면 된다.

## 모델 설명과 실험 결과 구분

Fighting High LoRA는 `.model/wan22-fighting-lora-high`, Lightning T2V 고·저 쌍은 `.model/wan22-lightning-t2v-v11`에서 관리한다. 이전 `wan22-vace-loras` 백업 스냅샷은 이관 이력으로 보존한다.

모델 사용법이나 설정을 설명할 때는 **공식 모델 카드에 명시된 내용**, **이 생성기에서 관찰한 실험 결과**, **그 결과를 바탕으로 한 추론**을 구분한다. 문서가 말하지 않은 권장값이나 효과를 공식 권장 사항처럼 단정하지 않고, 확인하지 못한 사항은 미확인으로 표시한다.

[Wan2.2-Lightning 모델 카드](https://huggingface.co/lightx2v/Wan2.2-Lightning)는 CFG 기법 없이 4스텝으로 생성할 수 있다고 설명한다. 카드 본문은 높은 CFG가 프롬프트 추종에 미치는 효과를 비교하거나, 이 VACE 조합의 CFG 최적값을 명시하지 않는다. 이 생성기의 Lightning 단독 CFG 1은 **로컬 기본값**이며 더 높은 값은 사용자가 시험할 수 있다. 기존 CFG 1·2 전진 베기 결과는 목표 동작을 확실히 따르지 못했지만, 제한된 실험만으로 CFG 값의 일반적인 효과나 원인을 단정할 수 없다. CFG 1에서는 이 생성기에서 부정 프롬프트 분기를 사용하지 않는다.

## 영상 전체 조건 실험

`video_condition`과 `video_edit`는 모두 원본 영상을 조건으로 새 영상을 생성한다. 원본 픽셀을 그대로 복사한 뒤 일부만 수정하는 방식은 아니다. 차이는 편집 위치를 마스크로 지정하는지에 있다. 영상 전체를 참고하려면 `video_condition`을, 특정 영역을 재생성하도록 지정하려면 `video_edit`를 선택한다. 두 방식 모두 원본 동작·외형과 배경의 완전한 보존을 보장하지 않는다.

`video_condition`은 RGB 원본 MP4와 외형 참조 PNG 1장을 입력한다. 모델에 전체 검정 마스크를
전달해 영상 전체를 조건으로 사용한다. 입력·출력은 자동 합성하지 않으며 자세·외형 보존과
셰이딩 개선은 보장하지 않는다. 사용자가 마스크를 입력하지 않으며 기존 부분 마스크 검증은
유지한다. GUI와 공용 게이트웨이는 동일한 `edit_video` base64를 사용하며 832×480·16fps·
32MiB 이하, 요청 프레임 이상이어야 한다. 8GB 실행 및 품질은 별도 검증한다.

`video_edit`는 완성된 원본 영상에서 지정 영역을 재생성하는 실험 모드다.
GUI·공용 게이트웨이 `wan22-vace generate`에서 기존 입력에 `mode: video_edit`,
`edit_video`, `edit_mask` MP4 base64를 추가한다. 외형 참조 `images`는 PNG 1장이다.
두 영상은 832×480·16fps·각 32MiB 이하이며 요청 프레임 이상이어야 한다.
마스크는 무채색이며 128 이상은 편집, 미만은 보존 조건으로 이진화한다.
마스크는 편집할 위치를 지정할 뿐 특정 동작이나 더 큰 움직임을 보장하지 않는다. 움직임의 범위를 바꾸려면 움직일 대상뿐 아니라 바뀔 수 있는 주변 공간도 고려해 마스크를 만든다.

2026-11-24 한손검 영상의 Q8·Lightning 4스텝 비교에서는 `video_condition` 강도 1.0과 0.5 모두 확인한 다섯 표본 프레임에서 원본과 유사한 자세를 보였고, 요청한 큰 베기는 확인되지 않았다. 0.5에서는 배경이 회색으로 변하고 인물과 검이 어두워졌다. 한 입력과 시드의 제한된 관측이며 전체 동작의 매끄러움과 다른 입력에서의 효과는 확인하지 않았다.

공식 [마스크 편집 예제](https://github.com/aigc-apps/VideoX-Fun/blob/main/examples/wan2.2_vace_fun/predict_v2v_mask.py)의
`video`, `mask_video`, `subject_ref_images` 조합을 공식 파이프라인에 전달한다.
공식 pipeline의 `input_video = init_video * (mask_condition < 0.5)`에 맞춰
공식 파이프라인이 편집 영역을 정규화 중립값으로 지운다.
조건 강도는 전체 VACE 조건에 적용하며 얼굴 참조 전용 강도가 아니다.
원본과 자동 합성하지 않으므로 마스크 밖도 생성 결과에서 달라질 수 있다.

입력 사본 `edit-video.mp4`, `edit-mask.mp4`와 해시를 작업 폴더에 보존한다.
결과·로그·이력·GPU 측정은 기존 공용 작업 서비스에 저장한다.
원본·참조·편집 결과를 같은 프레임으로 비교하여 외형 개선과 동작 손실을 함께 평가한다.
영상·마스크를 불러온 뒤 다른 모드로 전환할 때는 두 첨부를 지워야 한다.

## Q8 모델 실행 실험

모델 관리의 `Wan VACE Q8_0 · 파일 준비`는 QuantStack의 고정 리비전 Q8_0 GGUF 고·저노이즈 파일을 다운로드하고 크기와 SHA-256을 검증한다. 각 파일은 약 18.7GB다. Q8 전문가의 양자화 가중치는 GPU에 상주하며 선형 연산마다 GPU에서 BF16으로 역양자화한다. 텍스트 인코더와 VAE는 BF16이며, LoRA는 Q8 가중치에 영구 병합하지 않고 GPU에서 별도 저랭크 연산으로 적용한다. 2026-11-23에 49프레임·4스텝·CFG 1에서 Lightning 단독과 격투 강도 0.5 조합의 실제 ROCm 생성을 각각 한 번 완료하고 수치 검사를 통과했다. 두 결과 모두 명확한 전진 베기는 확인되지 않았으며, 한정된 입력·설정의 실행 성공은 일반적인 품질이나 TLB 근본 원인 해결을 뜻하지 않는다. Q8 선택 시 BF16 전문가로 자동 대체하지 않는다.

## 공식 비양자화 모델

VACE용 UMT5 BF16 인코더는 `.model/umt5-xxl-encoder-bf16`, 공식 토크나이저는 `.model/umt5-xxl-tokenizer-vace`에서 관리한다. 기존 `wan22-vace` 상위 백업 스냅샷과 별도 SentencePiece 사본은 보존한다.

공식 `alibaba-pai/Wan2.2-VACE-Fun-A14B` 리비전 `4438caabbfdd7437bbb0283d86cb200d1b7223ba`의 BF16 고·저노이즈 전문가를 고정한다. Q4 모델 생성·재개는 폐기했으며 이력은 보존한다. `python -m generators.wan_vace.prepare`는 고정 가중치·인코더·VAE와 공식 소스·토크나이저를 준비하고 크기와 SHA-256을 검증한다. 전문가 두 파일은 합계 69,350,650,000바이트다. 고정 해시가 있는 누락 가중치는 Samba 백업을 우선 확인하며 공용 VAE도 포함한다. 일치하는 백업이 없으면 공급처에서 받는다. 공식 소스와 실행 환경은 별도이므로 전체 준비의 오프라인 완료를 보장하지 않는다.

AMD ROCm에서 두 전문가·텍스트 인코더·VAE와 활성값은 GPU에 상주한다. CPU 오프로드나 자동 양자화 전환은 없다. GPU 메모리가 부족하면 실패하며 8GB 실행을 보장하지 않는다. 비양자화 경로의 전체 생성과 품질은 아직 검증되지 않았다.

## 키모도 DWPose 입력

`mode: pose`는 키모도의 처리된 DWPose MP4를 `pose_video` base64로 받는다.
캐릭터 외형 참조 PNG 1장을 `images`에 함께 전달한다. 영상은 832×480·16fps,
32MiB 이하이며 요청 프레임 이상이어야 한다. 재검출·프레임 반복을 하지 않는다.
`pose-video.mp4` 사본·SHA-256을 작업 폴더에 보존하고 이력에서 불러올 수 있다.
공식 `predict_v2v_control_ref.py`와 같이 `control_video`와 `subject_ref_images`,
빈 `video` 및 전체 생성 `mask_video`를 전달한다. 사용자 마스크는 받지 않는다.
GUI·CLI 모두 같은 `wan22-vace generate` 명령과 누적 이력을 사용한다.

화면의 기본 스텝은 20이다. 제작자 제어 예제의 50스텝은 비교 설정이며 필요할 때 고급 설정에서 직접 선택한다.

화면의 `제어 영상 + 참조 이미지 · 포즈`는 모델카드의 제어 영상과 참조 이미지 조합에 해당하며 현재 DWPose 입력만 받는다. 화면에 표시하는 생성 모드 이름은 입력 안내용이고 API의 `pose`, `reference`, `first_frame`, `text`, `video_edit`, `video_condition` 값은 유지한다. 각 모드를 선택하면 입력과 설정 안내가 바뀌며 설정값을 자동으로 변경하지 않는다.

## 공식 파이프라인 보존 정책

고정 공식 소스와 BF16 가중치를 사용하며 기본 실행에서 공식 수식과 스케줄러를 유지한다. 실험용 attention 격리 요청은 예외이며 실행 기록에 표시한다. 전문가를 포함한 모델과 활성값에 CPU 오프로드를 사용하지 않는다. 과거 Q4·오프로드 검증 결과는 현행 비양자화 모델의 실행 또는 품질 검증이 아니다.

### 초기 노이즈 통제 실험

공용 `wan22-vace generate --payload-file` 요청에 `noise_prefix_frames: 21`을
명시하면 `pose` 모드의 41프레임 작업에만 적용한다. 일반 GUI 생성에는 이 필드를
추가하지 않는다. 기본 경로는 그대로이며 실험 이력의 요청에 해당 값이 남는다.
동일 시드·CUDA·텍스트 인코더 dtype으로 21/41프레임 노이즈를 각각 생성한 뒤,
41프레임 노이즈의 첫 7개 잠재 슬롯(참조 1개 포함)을 21프레임 노이즈로 교체한다.
나머지 슬롯은 원래 41프레임 노이즈를 유지한다. 공식 파이프라인의 `latents`
인자를 사용하며 모델 연산은 바꾸지 않는다. 실행 시도에 `initial-noise.safetensors`와
형상·dtype·해시·공통 구간 일치를 담은 `noise-experiment.json`을 기록한다.
입력값 재사용 시 이 실험 필드를 누락하면 일반 실행이므로 기록을 구분해야 한다.

동일 요청에 `attention_prefix_frames: 21`을 추가하면 진단 전용으로 모든
self-attention에서 앞 7잠재 슬롯의 질의가 뒤쪽 슬롯을 참조하지 않게 한다.
뒤쪽 질의와 텍스트 cross-attention은 유지한다. 이는 공식 연산을 변경하는
원인 분리 실험이며 일반 생성의 품질 개선 옵션이 아니다. 실행 기록에
`official_math_unmodified: false`, `custom_math_patches: true`와
`attention-experiment.json`을 남긴다. `final-latents.safetensors`를 저장하고,
참조 슬롯을 제외한 앞 6잠재 슬롯을 별도로 디코딩한 21프레임 결과를
`comparison-prefix/`에 보관한다. 기본 GUI는 진단 필드를 추가하지 않는다.

분기 비교는 `attention_branch_scope: base`(본체) 또는 `vace`(제어 분기)를
추가한다. 생략하거나 `all`이면 두 분기를 제한한다. 고·저노이즈 전문가에
동일하게 적용하며 선택하지 않은 분기의 attention은 그대로 유지한다.

## AMD ROCm 실행 환경

공용 영상 작업자는 이미지 실행 환경 `.venv`를 사용한다. `./scripts/workflow.sh setup --scope image`로 ROCm·영상 패키지를 준비하고 모델·공식 소스는 관리도구 모델 준비에서 별도로 내려받는다. 환경 준비와 import 성공만으로 전체 생성·수치 정확도·영상 품질이 검증되는 것은 아니다.

ROCm PyTorch는 AMD GPU에서도 `torch.cuda`와 `cuda` 장치 이름을 사용한다. 실행은 BF16 지원 AMD GPU가 필요하며 GPU 백엔드·버전·모델 해시를 기록한다. 모델 및 활성값의 CPU 오프로드는 사용하지 않는다. AMD 전체 생성·메모리 한계는 별도 검증해야 한다.

CUDA 전환 시 데이터 단위·dtype·어텐션과 NaN 검증 절차는 [ROCm 추론 가이드](../../docs/rocm-inference.md)를 따른다.

VAE 내부 인코딩 출력, 디코딩 제한 전 출력과 조건 텐서를 검사한다. 비유한 값은 단계·형상·stride·dtype을 작업의 `numerical-failure.json`에 기록하고 실패 처리한다. 검사는 GPU 동기화와 실행 시간에 영향을 줄 수 있다. 합성 CPU 테스트만 수행했으며 실제 ROCm VAE 정확도·생성·영상 품질은 검증하지 않았다.

VAE SDPA 진단은 작업자 환경에 `SLIME_VACE_VAE_SDPA_DIAGNOSTIC=1`을 명시할 때만 켜진다. 인코딩·디코딩 각각 첫 호출의 동일 Q/K/V와 마스크로 기본 경로 두 번과 수학 경로 한 번을 실행한다. 작업 시도 폴더의 `vae-sdpa-encode`·`vae-sdpa-decode` JSON에는 원래 shape·stride·dtype, 옵션, 환경, 유한값, 오차, 반복 차이와 시간이 남고 safetensors에는 입력과 마스크를 연속 배치로 저장한다. 실제 선택 커널은 미확인으로 기록한다. 이 진단은 추가 GPU 연산·동기화·입력 복사와 디스크 공간을 사용하며 타이밍·메모리 상태를 바꾼다. dropout이 있으면 반복 비교를 생략한다. 진단 입력은 작업 데이터이므로 Git에 등록하지 않는다. 이 기능은 합성 CPU 테스트만 수행했으며 VACE 실제 입력의 ROCm 비교 및 영상 생성·품질 검증은 수행하지 않았다.

VAE·조건·전문가·스케줄러·최종 출력에서 비유한 값이 감지되면 작업 시도에 `numerical-failure.json`과 가능한 경우 실패 텐서의 연속 CPU 사본 `numerical-failure.safetensors`를 보존한다. VAE 입력이 텐서이면 함께 저장하며 중첩된 출력의 위치와 원래 stride를 기록한다. 실패 텐서 복사는 추가 메모리와 디스크가 필요하다. Transformer 어텐션 실패 행의 수학 경로 비교는 명시적 SDPA이고 마스크·길이·별도 scale·부분 창 등 비교 의미를 바꾸는 옵션이 없을 때만 수행한다. 그 외는 미실행으로 기록한다. 합성 CPU 테스트만 수행했으며 ROCm 실생성과 정확도는 미검증이다.

선택적 어텐션 진단에서 출력이 비유한이면 해당 출력을 작업 시도에 보존하고 실패한다. 오차 통계는 큰 유한 FP32/BF16 출력의 뺄셈 오버플로를 피하려고 FP64로 계산하며 추가 GPU 메모리와 시간이 필요하다. 합성 CPU 테스트만 수행했으며 ROCm 실생성·정확도·품질은 별도 검증한다.
