# Fun Control VAE 처리

## 진행 이벤트

새 Wan Fun 실행은 OpenTelemetry SDK로 `generation.progress` 로그를 발생시키고 현재 시도의 최신 이벤트를 `otel-progress.json`에 저장한다. 생성기와 Hermes 대화는 같은 진행 상황 영역이 표시된 동안 기본 30초 간격으로 해당 관측을 조회하며 자동 갱신을 끌 수 있다. 이전 작업에는 이벤트가 없을 수 있으며, 추정 시간은 추론 종료까지의 범위로 저장·후처리 시간을 포함하지 않는다. 추정에 필요한 스텝 표본이 없으면 예상 시간을 제공하지 않는다.

모델 환경 준비 시 `otel-requirements.txt`의 SDK를 별도 경로에 설치한다. OTLP/HTTP 수집기로도 전송하려면 작업자 환경에 `OTEL_EXPORTER_OTLP_ENDPOINT` 또는 `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`를 지정한다. 지정하지 않으면 외부 전송은 하지 않으며 최신 이벤트만 로컬에 보존한다. 프롬프트와 첨부 데이터는 이벤트에 포함하지 않는다.

## 1.3B 모델 선택

생성기의 **생성 모델**에서 `Wan 2.1 1.3B`를 선택하면 기존과 같은 외형 참조 이미지·포즈 영상·프롬프트를 사용한다. 이 모델은 단일 확산 모델로 전체 스텝을 실행하므로 고·저노이즈 전환 비율은 적용하지 않는다. 기존 이력에 모델 선택이 없으면 14B로 복원한다.

모델 관리의 **Wan Fun Control → Wan 2.1 Fun Control 1.3B**에서 가중치와 참조 인코더 다운로드·파일별 진행률·준비 상태를 확인한다. 1.3B 파일은 `alibaba-pai/Wan2.1-Fun-V1.1-1.3B-Control`의 고정 리비전에서, FP16 참조 인코더는 `Comfy-Org/Wan-2.1`의 고정 리비전에서 받으며 크기와 SHA-256을 검증한다. 텍스트 인코더·VAE·ROCm 환경은 기존 Wan Fun 준비 자산을 사용한다. 생성 기록에는 선택 모델과 참조 인코더 출처가 보존된다. 모델 준비 완료는 영상 품질 보증이 아니다.

관리도구 **모델 관리 → Wan Fun Control**에서 모델 준비 상태와 파일별 다운로드·이어받기를 확인하고 준비가 필요하면 **모델 다운로드**를 실행한다. 기존 생성기 화면과 CLI `command wan22-fun-control prepare`도 같은 게이트웨이 명령을 사용한다. 준비 작업은 ROCm 환경 검사 때문에 공용 GPU 대기열에서 수행하며, 대기 중과 실행 중에는 중복 요청을 막는다. 새 예약 정책이 적용된 게이트웨이에서는 준비가 다른 대기열 작업과 겹치지 않는다. 이미 실행 중인 구버전 게이트웨이에는 이 정책이 적용되지 않으므로 작업 상태를 확인한 후 재시작해야 한다. 대기열 밖 GPU 프로세스는 배타 예약 대상이 아니다. 실제 모델 파일은 공용 Hugging Face 다운로더로 받는다.

Wan Fun 모델과 포즈 가중치는 HTTP 전송을 사용한다. 부분 파일의 연속된 데이터를 서버와 대조한 뒤 이어받기 위해 Xet 희소 파일 전송은 사용하지 않는다. 기존 Xet 부분 파일은 보존하며 안전하게 확인할 수 있는 구간만 복구한다.

모델과 전체 준비는 공용 CLI `./scripts/workflow.sh model prepare wan22-fun-control` 또는 모델 관리 화면에서 접수한다. 모델을 받지 않고 ROCm 실행 환경만 준비하려면 `./scripts/workflow.sh setup --scope wan-fun-runtime`을 사용한다. 이 명령은 공유 대기열의 활성 예약이 있으면 중단하며 설치 중 새 GPU 작업을 대기시킨다. 대기열 밖에서 직접 실행한 작업은 보호하지 못하므로 별도로 확인해야 한다. 준비 과정은 기존 전용 환경의 패키지를 설치·갱신할 수 있으며, 해당 환경은 현재 Kimodo도 참조할 수 있다. 실행 전 공유 의존성과 대기열 외 작업을 확인한다. 설치 전 기존 PyTorch·MIGraphX·ONNX 공급자 버전이 지정된 값과 다르면 자동 교체하지 않고 중단한다. 각 설치 단계는 공용 PyTorch 제약과 Wan Fun 전용 MIGraphX 제약을 함께 사용한다. 이 검사는 다른 모든 의존성의 변경이 없음을 보장하지 않는다. 별도 `.local/venvs/wan-fun-rocm`에 AMD ROCm PyTorch·MIGraphX 환경과 DWPose를 준비한다. 고·저노이즈 BF16 모델, UMT5 FP16, Wan2.1 VAE는 고정 리비전에서 받아 크기와 SHA-256을 검증한다. 고정 커밋의 ComfyUI 의존성을 설치하며 기존 소스에 수정 사항이나 다른 커밋이 있으면 중단한다. 로그는 `.tmp/management-launcher-logs/`와 `.tmp/test/wan22-fun-control-prepare/`에 저장한다.

고·저노이즈 모델은 비양자화 BF16으로 GPU에 직접 적재하고 순차 실행·해제한다. UMT5 FP16과 VAE도 GPU 전용으로 실행하며 모델·레이어 CPU 오프로드를 사용하지 않는다. 파일 로딩 중 일시적인 호스트 메모리 사용은 가능하다. 직접 적재 전 GPU 여유가 가중치 파일 크기의 두 배에 4GiB를 더한 값보다 작으면 실패하며, 그 밖의 GPU 메모리 부족도 오프로드로 우회하지 않는다. gfx1151에서 긴 self-attention은 여유 GPU 메모리가 있을 때 연속 배치를 사용하며, 여유 부족이나 복사 OOM에는 원래 배치로 실행한다. 입력·출력의 NaN과 무한대는 실패로 처리한다. 진단 시 `SLIME_WAN_ATTENTION_PROFILE=1`을 설정하면 실행 시도 폴더의 `attention-profile.jsonl`에 앞쪽 attention 호출의 GPU 동기화 시간과 첫 커널을 기록한다.

참조·포즈 인코딩과 결과 디코딩은 FP32 일반 ComfyUI VAE로 고정한다. 인코딩 후 VAE를 해제하고 확산 추론이 끝나면 새 VAE를 로드해 디코딩한다. 이 과정은 CPU 오프로드가 아니다. 추론 전 텍스트·참조·포즈·초기 노이즈의 유한값을 검사하고 해시를 `conditioning-fingerprints.json`에 기록한다. 각 샘플러 콜백의 예측값과 갱신 전 잠재값은 `numerical-steps.jsonl`에 기록한다. 최종 갱신 후 잠재값도 별도로 검사한다.

gfx1151의 ROCm에서 PyTorch 확장형 GPU 메모리 세그먼트가 같은 입력의 VAE 조건값을 실행마다 다르게 만든 실측 결과가 있어, 작업자는 torch를 불러오기 전에 `expandable_segments:False`로 고정한다. GPU 메모리가 부족하면 오프로드 없이 실패한다. 이 설정 변경이 모든 ROCm 환경에서 같은 문제를 해결한다는 뜻은 아니다.

2026-11-15 Radeon 8060S·ROCm 9프레임 실험에서 동일한 VAE 가중치와 입력으로 확장형 설정만 바꾸었을 때 참조 잠재값의 평균 절대 차이는 1.24, 포즈 조건 잠재값은 0.92였다. 확장형을 끈 후 동일 시드·10스텝 전체 생성 두 번이 완료됐고 두 첫 프레임의 평균 픽셀 차이는 0~255 기준 약 0.75였다. 실험 전에는 비유한 VAE 조건과 디코딩 출력이 관측됐다. 이 결과는 이 환경·입력에서의 안정성 검증이며 장영상과 모든 시드의 품질이나 NaN 부재를 보장하지 않는다.
타일 VAE 실행·UI 선택은 제거했으며 OOM 시 자동 타일 대체 없이 명시적으로 실패한다.

이전 이력은 보존한다. 입력을 불러와 신규 생성하면 일반 VAE를 사용한다.
CLI 호환을 위해 `use_regular_vae: true`, `pose_encode_full_temporal: false`는 허용하지만,
타일 처리를 요청하는 반대 값은 접수 시 거절한다. 필드 생략도 일반 VAE다.
`encode-policy.json`, `decode-policy.json`에 실제 정책을 기록한다.

참조 이미지와 프롬프트만 사용하는 모드는 폐기되었습니다. 포즈 영상과 참조 이미지를 사용하세요. 기존 결과 조회는 유지되며 생성·재개·입력 재사용은 거절합니다.

### 걷기 예제와 프레임 확장

`걷기 예제 불러오기`는 `examples/walk-21frames-50steps/`의 참조 PNG·포즈 MP4·설정을 입력에 복원하며 자동 생성하지 않는다. 원본 작업은 `2026-11-02_23-24-48-85eb00f7`이며 21프레임·50스텝·시드 42·시프트 5·CFG 6·고노이즈 비율 0.3이다.

GUI·CLI 입력 범위는 5~129프레임(`4n+1`)으로 고정한다. 2026-11-14 Radeon 8060S의 96GiB GPU 예약 환경에서 113프레임·2스텝 BF16 실행을 확인했다. 이 진단은 출력 품질을 보장하지 않으며 20스텝 전체는 별도 검증이 필요하다. 포즈 MP4는 요청 프레임 이상이어야 하며 부족한 프레임을 반복하지 않는다.

### 폐기된 양끝 이미지 자체 확장

시작·종료 이미지 입력 및 조건 텐서 자체 확장은 제거했습니다. 해당 조건이 있는 기존 작업은 재개·입력 재사용할 수 없으며 결과 조회는 유지합니다.

RGB 영상 직접 입력 실험은 폐기했습니다. 신규 생성·기존 RGB 작업 재개·입력값 복원은 거절하며, 기존 결과와 실행 기록 조회는 유지합니다. 포즈 영상과 외형 참조 이미지를 사용하세요.

VAE 내부 인코딩 출력과 디코딩 후처리 전 출력을 검사하여 무한대가 영상 범위 제한으로 가려지기 전에 실패 처리한다. 실행 시도 `runtime-environment.json`에 환경 설정과 VAE에 지정된 어텐션 함수 이름을 기록한다. 함수 이름은 실제 실행 GPU 커널을 뜻하지 않는다. 조건값 지문의 해시는 CPU FP32 연속 배치 기준이며 원래 dtype·device·stride를 별도 기록한다.

선택적으로 작업자 환경에 `SLIME_FUN_VAE_ATTENTION_DIAGNOSTIC=1`을 설정하면 인코딩·디코딩 각각 첫 VAE 어텐션의 입력·출력을 검사하고 `vae-attention-encode`·`vae-attention-decode`의 JSON과 safetensors에 입력과 형상을 보존한다. 선택 함수가 고정 ComfyUI의 `pytorch_attention`일 때만 같은 입력으로 기본 경로 반복과 수학 SDPA를 비교하고 다른 경로는 비교를 생략한다. PyTorch 경로는 내부 OOM 시 분할 어텐션으로 대체될 수 있어 함수명만으로 GPU 커널을 확정하지 않는다. 진단은 추가 연산·복사·동기화로 시간과 메모리 상태를 바꾼다. 파일은 작업별 비공개 데이터이며 Git에 등록하지 않는다. 합성 CPU 테스트만 수행했고 실제 ROCm 입력 비교·생성·품질 검증은 수행하지 않았다.

수치 오류 시 `numerical-failure.json`에 최초 감지 경계와 원래 텐서 형상·stride·dtype을 기록하고, 가능한 경우 `numerical-failure.safetensors`에 실패 텐서와 VAE 입출력을 연속 CPU 사본으로 보존한다. 저장 실패나 대형 텐서 복사는 추가 메모리·디스크가 필요하다. SDPA 진단은 ComfyUI 변환 후 실제 비교에 사용한 Q/K/V 형상·stride와 scale도 기록한다. 합성 CPU 검증만 수행했다.

선택적 어텐션 진단에서 출력이 비유한이면 해당 출력을 작업 시도에 보존하고 실패한다. 오차 통계는 큰 유한 FP32/BF16 출력의 뺄셈 오버플로를 피하려고 FP64로 계산하며 추가 GPU 메모리와 시간이 필요하다. 합성 CPU 테스트만 수행했으며 ROCm 실생성·정확도·품질은 별도 검증한다.

생성 작업 재개는 저장된 참조 이미지 수·순서와 사본 무결성, 포즈 또는 동작 영상의 일반 파일 여부와 기록된 SHA-256을 확인한다. 영상 해시가 없는 구형 이력은 파일 존재만 확인하므로 원래 입력과 같은지 보장하지 않는다. 모델 준비 작업의 기존 재개 계약은 별도다.

내부 재개 지문은 생성 작업의 저장 요청·상태·실행 명령과 참조 프레임 전체, 포즈 또는 동작 영상을 포함한다. 모델 준비 작업은 이 지문의 대상이 아니다. 원 서비스의 `resume-preview`는 재개·실행 잠금 아래 이 지문과 입력을 검토하고 숨긴 이력을 포함해 저장된 준비 작업의 대기·실행·확인 불가를 조회한다. 확인된 값은 조회 시점의 기록 상태이며 다른 프로세스의 이후 변경이나 실제 프로세스 생존을 보장하지 않는다. 원 서비스의 검토 기반 접수는 같은 저장소를 쓰는 새 관리 프로세스의 공용 접수 잠금과 재개·실행 잠금 아래 지문과 입력·실행 명령을 재검증한다. 잠금을 따르지 않는 구버전·외부 프로세스나 접수 이후의 변경은 막지 못하며 실제 GPU 실행은 검증하지 않았다.

Hermes와 Codex MCP에서도 Wan Fun 생성 작업의 재개 입력을 예비 검토할 수 있다. Hermes는 준비 충돌 상태를 재확인하고 검토 지문과 접수 ID를 이용해 재개를 접수한다.

Hermes를 통한 Wan Fun 예비 검토도 원 서비스의 준비 상태 관측을 반환하며, 확인 불가 또는 준비 중에는 접수를 보류한다.

Wan Fun의 생성·준비 접수와 검토된 재개 접수는 작업 저장소의 공용 파일 잠금을 사용한다. 접수 구간만 보호하며 작업 실행 전체를 잠그지는 않는다.

임시 HTTP 게이트웨이에서 다른 관리기의 공용 접수 잠금이 점유된 상태로 모델 준비를 요청하면, 준비 작업 디렉터리나 실행기를 만들기 전에 거부되는 것을 확인했다. 실제 준비·GPU 작업은 실행하지 않았다.

재개 전 준비 충돌 확인은 일반 작업 ID뿐 아니라 공용 이력에서 사용하는 과거 `-prepare` 작업 이름도 검사한다. 해당 기록이 손상됐거나 상태를 알 수 없으면 재개를 보류한다.

Wan Fun 재개 예비 검토는 생성 작업만 대상으로 하며, 준비 작업은 중단 상태 복구를 시도하기 전에 거부한다. 이후 잠금을 따르지 않는 외부 파일 변경까지 원자적으로 막지는 못한다.

기존 화면·CLI의 직접 재개도 공용 접수 잠금 아래 다른 준비 작업과 저장 요청·실행 명령을 다시 확인한다. 직접 재개에는 사용자가 확인한 입력 지문이 없으므로 검토 지문 기반 재개와는 확인 범위가 다르다.

직접 재개도 작업 저장소 바로 아래의 실제 디렉터리만 접수하며 심볼릭 링크 작업은 거부한다. 요청 기록을 처음 읽기 전에 이 경로 검사를 수행한다. 잠금을 따르지 않는 외부 경로 교체까지 원자적으로 막지는 못한다.

임시 HTTP 게이트웨이에서 심볼릭 링크 작업의 직접 재개가 런타임·재개 검증 함수 호출 전에 거부됨을 확인했다. 외부 테스트 파일은 변경하지 않았다.

새 모델 준비도 기존 준비 이력의 상태를 확인할 수 없으면 중복 여부를 알 수 없어 접수를 보류한다. 확인된 중단 작업의 기존 복구 절차는 유지한다.
