# Hermes 로컬 관리 에이전트

관리 화면은 Hermes와의 대화를 첫 작업 공간으로 표시한다. 기존 조회·제안 검토·직접 실행 기능은 **기존 연결 기능 · 직접 조회와 작업**에 있으며, Kimodo·FLUX 이미지·번역·오디오·텍스트 영상 제안과 빌보드·이펙트·야외 맵·스프라이트 변경 제안은 완료된 세션 작업을 선택해 대화에서 검토·확인·상태 조회할 수 있다. 텍스트 영상의 설정에는 기본값이 포함되므로 확정 전에 확인한다. 이미지·영상 첨부가 필요한 영상 제안은 별도 첨부 검토 영역에서 필요한 파일과 기본 설정을 확인한다. 첨부 합계는 24 MiB 이하이며 해시와 크기를 확인하고 설정·첨부 변경 시 재검토해야 한다. 새로 연 기존 접수는 첨부를 다시 보내지 않고 상태를 조회한다. 작가 요청도 대화에서 검토·접수하고 결과를 확인할 수 있다. 변경 근거 전체는 작가 AI 화면에서 검토한 뒤 대화에서 적용을 확인한다. 원본의 실제 이미지·배치와 저장 후 소비자 상태는 해당 도구에서 확인한다. 세션과 제안 작업이 같은 접수는 다시 열어 확인하며 불확실한 접수는 재실행하지 않는다. 기존 도구에서 별도로 접수한 작업은 자동 연결되지 않는다. 각 도구 페이지에서 작업과 입력을 자세히 확인할 수 있다.

대화에서 생성 제안을 다시 열 때는 기존 접수만 확인한다. 접수 ID·서비스가 일치한 기록이 없을 때만 새 접수를 검토할 수 있고, 기존 접수의 작업 상태·결과는 별도 확인 버튼으로 조회한다. MCP에서는 `read_hermes_service_receipt` 또는 Kimodo의 `read_hermes_delegation_status`로 접수 여부를 먼저 확인할 수 있다. 접수 기록은 실행기 생존·작업 완료·결과 품질을 뜻하지 않는다. 일부 원 서비스의 상태 조회는 중단 작업의 기록 복구를 수반할 수 있다. 구버전 게이트웨이에서 식별 정보를 확인하지 못하면 새 접수를 막으므로 원 서비스 이력을 확인하고 게이트웨이를 갱신한다.

공용 상단의 **운영 이력**에서는 최근 세션의 지시, Hermes 작업 이력과 현재 GPU 대기·예약 기록을 따로 조회한다. Hermes 작업 이력은 한국어 상태 필터로 바로 좁힐 수 있으며, 인식하지 못한 기록 상태도 확인 불가에 포함한다. **이전 Hermes 작업 찾기**는 30건씩 이전·최근 방향으로 이동하며 100건 이전의 이력도 조회한다. 검색어와 상태 필터는 전체 작업 이력에 적용한 뒤 결과를 페이지로 나눈다. 목록 또는 해당 조건의 검색 결과가 바뀌면 처음부터 조회해야 하며 각 작업과 GPU 상태는 별도의 조회 시점 기준이다. 목록을 새로고침하거나 검색·상태 필터를 변경하면 이전 작업 상세와 로그는 지워지며 행을 다시 선택해 조회한다. 기본 최근 작업 표는 최근 100건을 대상으로 하며 전체 검색은 이전 작업 찾기에서 사용한다. 예약 조회 실패·손상·잘림·중복을 구분하며, 작업자 리더가 확인돼도 그룹 전체의 생존이나 종료를 단정하지 않는다. 예약 정리는 별도 검토·확인을 거쳐 접수하며, 단순 조회로는 해제하지 않는다. Hermes 작업과 대기 기록은 서비스와 작업 ID가 명확히 일치할 때만 연결한다. 이력 행에서 작업 지시·응답·diff·로그를 읽고, 선택 세션은 새 탭으로 대화를 열 수 있다. 기본 세션 목록은 최근 100개이며 **이전 세션 찾기**에서 전체 세션을 30개씩 조회하거나 사용자 지시 내용·세션 ID 일부로 검색할 수 있다. 검색 결과 목록에는 지시 원문을 표시하지 않는다. 찾은 행을 선택하고 지시를 조회한 뒤 해당 운영 대화로 돌아갈 수 있다. 선택 세션의 지시는 최근 20개씩 이전·최근 방향으로 이동하며 저장된 시각을 표시한다. 이력을 새로고침하거나 검색할 때 최근 목록 또는 직접 조회한 원본으로 선택 세션을 확인하면 유지한다. 원본을 확인할 수 없거나 목록에 중복되면 선택을 해제하고 안내한다. 조회 사이 세션 기록이 바뀌면 처음부터 다시 조회해야 한다. 대화 제안 접수 기록 조회는 화면에 표시된 지시 페이지를 대상으로 하며, 페이지를 바꾸면 기존 접수 결과를 지운다. 세션 기록이 바뀌면 지시부터 다시 조회한다. Hermes 작업 ID가 세션 내 여러 지시에 연결된 경우 접수 연결을 생략하며, 서비스 작업 ID의 중복 확인은 표시 페이지에 한정된다. Kimodo·FLUX·번역·오디오·영상·작가의 접수는 ID로 직접 조회하므로 최근 100건 제한을 받지 않는다. 손상 기록이나 다른 서비스의 ID는 조회 불가로 표시한다. 공용 기능 목록의 접수 조회 입력에는 실제 지원 서비스가 열거되며 Kimodo는 별도 접수 조회를 사용한다. 생성기 원본 이력은 서비스별로 한국어 기록 상태와 GPU 대기 관측을 페이지 단위로 조회하고 이전·다음 페이지로 이동할 수 있다. 목록 확인값이 달라지면 처음부터 다시 조회한다. 행을 선택하면 확인된 작업 ID와 실제 원본 서비스의 이력 링크를 표시한다. 지원 도구에서는 전달된 작업 찾기 버튼을 눌러 선택하고, 그 외 도구에서는 ID를 확인해 직접 선택한다. 서비스·작업 ID가 일치할 때만 대기 기록에 연결하며, 공유 이력은 실제 원본 서비스를 표시한다. 기존 작업과 대화·접수 관계 및 상세 결과는 아직 원 도구에서 확인한다. 조회 시각이 다를 수 있고 대기 목록에 없다는 사실은 작업 완료를 뜻하지 않는다. 공용 GPU 관측은 일치 기록이 없을 때와 다른 GPU 서비스에 같은 ID가 있을 때를 구분한다. 다른 서비스의 동일 ID는 같은 작업으로 연결하지 않는다.

Hermes는 관리도구의 현재 추적 파일과 Git에서 무시하지 않는 새 파일을 격리 작업 공간에 복사해 작업한다. GUI, 통합 CLI, MCP는 공용 관리 게이트웨이와 같은 작업 기록을 사용한다. 격리된 터미널과 파일 읽기·검색·패치 도구를 제공하며 한 작업의 도구 호출은 최대 20회다. 작업 결과는 검토용 diff이며 원본에 자동 적용하지 않는다.

화면의 **사용 가능한 관리 기능**과 MCP `list_hermes_management_capabilities`에서 주요 명령의 입력 형식·영향·GPU 사용·재시도와 연결 범위를 확인할 수 있다. 게이트웨이에 등록됐지만 기능 목록에 없는 Hermes 명령은 별도로 표시해 지원 여부 확인을 요구한다. 화면 표에는 명령 식별자·연결 경로·필수 입력·영향·GPU·재시도 기준을 함께 표시하며 검색어 입력 후 Enter 또는 목록 새로고침으로 찾을 수 있다. 제안·작업 이력·세션과 접수 기록 조회는 로컬 잠금 파일을 만들 수 있어 MCP에서 순수 읽기로 표시하지 않는다. 목록은 안내이며 별도 역할 권한을 부여하지 않는다. 실제 입력 검증과 확인은 기존 서비스·클라이언트가 담당한다.

## 구성과 준비

- **모델:** Qwen3.8-27B IQ4_XS. 모델 관리의 Hermes 코딩 모델에서 다운로드하며 파일 SHA-256은 실행 직전에 다시 확인한다. 고정 출처와 해시는 [모델 준비 구현](../../tools/review/common/hermes_model_download.py)을 따른다.
- **Hermes:** 공식 `v0.23.1`, Git 리비전 `3b421578588243f920886e6fe79a6faa87ea026e`. Git 제외 경로 `.local/hermes-agent-runtime/`에 준비한다. `prepared-local.json`, Git HEAD, 추적 파일 변경과 무시되지 않은 신규 파일을 실행 직전에 검사한다. 이 검사는 `.venv/`의 모든 패키지 파일 해시를 검증하는 기능은 아니다.
- **추론 서버:** 작가 AI가 준비한 ROCm `llama-server` 바이너리와 준비 manifest를 읽고 바이너리 SHA-256을 확인한다. 모델 프로세스는 Hermes 전용이며 작가 AI 서버의 실행 상태를 변경하지 않는다.
- **GPU 프로세스 정리:** PID 재사용에 안전한 프로세스 그룹 종료를 위해 Linux 6.9 이상의 `pidfd_send_signal` 그룹 신호 지원이 필요하다. 지원되지 않으면 GPU 사용 전에 작업을 실패 처리한다.
- **MCP 실행환경:** Python 3.14 전용 별도 환경에 버전 고정 의존성을 설치한다.

저장소 루트의 공용 진입점에서 필요한 환경을 선택하여 준비한다. `writer-runtime`은 공용 서버와 작가 AI 모델 두 개도 준비하며, 기존 준비 환경은 해시만 검증한다. Hermes 모델 다운로드와 Codex 등록은 별도 단계다.

```bash
./scripts/workflow.sh setup --scope writer-runtime
./scripts/workflow.sh setup --scope hermes-runtime
./scripts/workflow.sh setup --scope hermes-mcp
```

Hermes 소스는 [공식 소스](https://github.com/NousResearch/hermes-agent)의 고정 리비전을 내려받고 `uv sync --locked --no-dev`로 준비한다. 실행에는 `uv`가 필요하다. 이미 설치된 소스는 리비전과 변경 여부를 검증하고 재사용한다. 기존 MCP 환경은 Python 버전과 고정 패키지 버전, `pip check`를 확인하며 자동 변경하지 않는다. 설치가 중간에 실패하거나 기존 디렉터리가 불완전하면 남은 파일과 로그를 확인해야 한다. 자동 삭제·덮어쓰기는 하지 않는다. 패키지 파일 자체의 해시 전체를 검사한다는 뜻은 아니다.

모델 다운로드만으로 Hermes·ROCm 서버가 준비되는 것은 아니다. 추론 서버 준비는 [작가 AI 실행 안내](../../workflows/writer-agent.md)를 참고한다.

## 실행과 결과

상단의 **관리 상태 새로고침**은 Hermes와 Kimodo 모델 준비·Kimodo 활성 작업·최근 Hermes 작업 ID와 상태·GPU 상태·예약 기록·대기 작업 수를 조회한다. 예약은 기록 시점의 값이며 실행기 생존을 보증하지 않는다. 최근 Hermes 작업 관측은 최대 10건의 ID와 상태만 포함하고 지시·로그·경로는 포함하지 않는다. 최근 작업 관측은 로컬 잠금 파일을 만들 수 있다. Kimodo 활성 작업은 상태 파일의 대기·실행 기록 건수와 최신 ID를 표시하고, 손상·누락된 상태는 확인 불가 건수로 구분한다. 실제 프로세스 생존이나 종료를 보증하지 않고 공용 대기열 목록과 구분한다. 이 관측은 작업 상태를 복구하지 않는다. 새 관측 명령을 운영 게이트웨이에 반영하려면 기존 작업 상태를 확인한 뒤 게이트웨이를 재시작해야 하며, 이전 게이트웨이는 해당 항목을 조회 불가로 표시한다. 모델 관리와 동일한 준비 판정이며 모델 추론을 시작하지 않는다. GPU 관측은 짧은 캐시를 사용할 수 있고 조회 실패는 조회 불가로 표시한다. Codex MCP의 `read_hermes_management_status`와 격리 작업자의 고정 상태 조회 명령도 같은 관측을 제공한다. 메모리 표시는 공용 대기열과 같은 VRAM 또는 GTT 영역을 선택하고 호스트 여유를 함께 표시한다. GTT는 공유 RAM이므로 대기열과 표시에서 호스트 보호 여유 6GiB를 제외한다. 대기 중인 실행기는 대기열·메모리 추정·호스트 보호 코드 변경을 감지하면 동일 작업과 대기 순서를 유지해 갱신한다. 이미 실행 중인 작업은 선점하지 않는다. 메모리 기준 충족은 관측 시점의 단순 비교이며 다른 예약과 대기 순서, 이후 변화를 반영한 실행 보장은 아니다.

Hermes 화면의 **Kimodo 키프레임 찾기**와 MCP `list_hermes_kimodo_keyframes`는 기존 키프레임 기록을 ID·태그로 검색한다. 목록에는 원본 프레임 번호만 제공한다. 화면의 다음 페이지는 검색 결과 기준 해시를 확인하며 목록이 바뀌면 처음부터 다시 검색한다. MCP에서도 후속 조회에 첫 응답의 `snapshot`을 전달할 수 있다. 화면의 원본 검증·미리보기 또는 MCP `read_hermes_kimodo_keyframe_preview`는 Kimodo의 모션·골격·이미지 해시 검증을 사용한다. 화면의 배치 원본 일괄 검증과 MCP `validate_hermes_kimodo_keyframes`는 선택 원본의 해시와 관절·부모 구조 일치 여부를 확인한다. 정지 이미지 확인은 생성 동작 품질을 보증하지 않는다. 위임 화면의 선택 입력에 `[{"id":"키프레임ID","frame":1}]` 형식으로 배치할 수 있다. `frame`은 생성 결과의 프레임 번호다. 키프레임 사용 시 공식 후처리를 켜고 수평 이동을 유지하며 입력을 변경하면 다시 검토한다. 원본은 접수 시 다시 검증하여 작업에 고정하므로, 화면 검토 후 원본이 바뀔 수 있다.

Codex MCP의 Hermes 작업·세션 메시지 접수 도구 설명에도 GPU 대기열과 외부 작업 성능 경합 범위를 표시한다. 실행 중인 MCP 프로세스에는 소스 변경이 즉시 반영되지 않을 수 있으므로, 안전한 시점에 MCP 연결을 다시 시작한 뒤 설명을 확인한다. 연결 재시작은 별도 운영 작업이며 다른 GPU 작업을 중지하지 않는다.

음악·효과음과 번역 재개는 각각 검토·접수·접수 확인 MCP 도구를 제공한다. 코드 등록과 현재 연결의 도구 목록은 다를 수 있다. 도구가 목록에 없으면 실행 중인 MCP 연결이 새 코드를 반영했는지 확인하고, 안전한 시점에 연결을 다시 시작한 후 여섯 도구의 목록과 설명을 확인한다. 재개 접수는 GPU 대기열에 작업을 등록하므로 확인을 위해 실제 접수하지 않는다.

운영 이력에서는 음악·효과음·번역의 원본 이력 행을 선택해 재개 대상을 검토하고 공용 GPU 확인을 거쳐 접수한다. 검토 후 이력 페이지나 선택 대상이 바뀌면 다시 검토해야 한다. 접수 ID로 결과를 확인할 수 있으며, 결과가 불확실하면 다시 접수하기 전에 원 서비스와 대기열을 확인한다. 접수 완료는 생성·번역 완료나 GPU 종료를 의미하지 않는다. 실제 합성 관리 화면에서 확인·취소·화면 배치는 별도 브라우저 검증이 필요하다.

대화에서 세션과 작업을 선택하고 **운영 이력에서 찾기**를 누르면 해당 작업 ID와 세션을 이력 화면에 전달한다. 이력은 최근 목록과 전체 이력 검색을 열며, 정확히 일치하는 작업 ID는 전체 검색의 첫 결과에 우선한다. 행을 선택해 상세를 확인하고 세션 지시를 조회하면 같은 대화로 돌아갈 수 있다. 전체 이력 검색을 지원하지 않는 구버전 게이트웨이에서는 조회 실패를 표시하므로 화면과 게이트웨이가 같은 계약을 사용하는지 확인한다.

Codex MCP의 `delegate_hermes_kimodo_generation`은 명시적으로 요청된 Kimodo 생성 입력을 기존 서비스에 접수하고 즉시 작업 ID를 반환한다. 동일 식별자와 동일 입력의 재시도는 기존 ID를 반환하며 입력이 다르면 거절한다. 화면을 다시 열었다면 **위임 접수 이력 새로고침**으로 최근 100개 접수 ID와 상태를 찾아 선택할 수 있다. 입력 원문은 이력에 저장하지 않으며 손상된 기록은 확인 불가로 표시한다. 접수 응답이 유실되면 화면의 **위임 접수 ID로 확인** 또는 MCP `read_hermes_delegation_status`로 재접수 없이 확인한다. `unknown`이면 Kimodo 이력과 실제 작업 상태를 확인해야 하며 자동 재실행하지 않는다. 이 기능은 접수 성공이 생성 완료를 뜻하지 않으며 기존 공용 GPU 대기열과 예약 정책을 따른다. Hermes 화면의 **Kimodo 작업 위임**에서 지시·프레임·단계·시드를 입력해 확정값을 검토하고 공용 GPU 확인 후 접수할 수 있으며 작업 ID로 상태를 조회한다. 검토 후 입력을 수정하면 이전 검토와 접수 버튼이 해제된다. 다시 검토해야 하며, 확인 시 입력과 검토본이 다르면 접수를 거부한다. GPU 확인창을 연 뒤 입력이 달라진 경우에도 접수를 거부하고 다시 확인해야 한다. 세션의 완료된 Hermes 작업을 선택하고 **Hermes 제안 불러오기**를 누르면 형식과 입력 검증을 통과한 Kimodo 제안을 입력란에 채운다. 제안은 미신뢰 입력이므로 자동 접수하지 않고 사용자가 검토·확인한다. 대화에는 내부 제안 형식 대신 검토 안내를 표시하며 원본 답변은 작업 기록에 보존한다. 실제 모델 시험에서 관리 상태 조회·제안 형식 출력·후속 대화와 Kimodo GPU 대기열 인계를 확인했다. 30프레임·2단계 인계 시험이 완료되고 미리보기 파일이 생성됐으나 품질을 검수한 것은 아니다. 다른 요청에서도 항상 같은 형식을 따른다는 보장은 없다. 위임된 작업의 중지는 접수 ID와 작업 ID를 확인한 뒤 화면에서 **위임 작업 중지 요청 검토**를 거치거나 Codex MCP `cancel_hermes_kimodo_delegation`으로 요청한다. 중지 요청과 실제 프로세스 종료는 다르므로 Kimodo 상태를 확인한다. 실제 Kimodo 시험 작업이 VRAM 약 14 GiB를 사용 중일 때 중지 요청 후 취소 상태·작업 프로세스 종료·실행 잠금 및 예약 해제를 확인했다. Codex에서는 `read_hermes_kimodo_job_status`에 접수 ID를 전달해 기존 Kimodo 작업 상태를 확인한다. 기존 Kimodo 상태 조회는 중단된 작업의 기록을 실패로 복구 표시할 수 있어 순수 읽기 전용으로 분류하지 않는다. 화면 상태 요약은 최근 로그에 DWPose SimCC 출력 형상 경고가 있으면 품질 확인 안내를 표시한다. 기존 실행기는 출력 길이를 검사해 축 순서를 보정하지만 이 검사가 포즈 품질을 보증하지는 않는다. 접수 결과가 불확실하거나 ID가 일치하지 않으면 중지 요청을 보내지 않는다.

세션에서 **세션 작업 선택 → 선택 작업 상세 열기**를 누르면 해당 작업의 최종 응답, 검토용 diff, 로그와 독립 검증 결과를 기존 상세 영역에서 확인할 수 있다. 작업 목록은 화면에 표시된 최근 20개 메시지에 해당한다.

관리 메뉴의 **텍스트 기반 → Hermes 관리 에이전트**에서 지시와 GPU 대기열 확인을 거쳐 접수한다. 동일한 접수 식별자와 지시는 재시도해도 기존 ID를 돌려주며, 다른 지시에 같은 식별자를 재사용할 수 없다. 응답이 유실되면 새 식별자를 만들기 전에 같은 식별자로 조회 또는 재접수해 결과를 확인한다. 작업 상태는 `queued`, `running`, `completed`, `failed`, `cancelled`이며 접수 중 비정상 종료로 상태가 없으면 `unknown`으로 표시하고 자동 재실행하지 않는다.

선택적으로 공용 회귀 실행기에 등록된 모듈을 최대 5개 지정할 수 있다. Hermes가 최종 수정을 마친 후 추론 서버를 내리고, 같은 격리 사본에서 지정 모듈을 별도 실행한다. 공용 회귀 실행기 파일이 작업 중 변경되면 독립 검증을 거부한다. 테스트 코드 자체는 작업 사본을 사용하므로 검증 통과와 함께 변경 diff도 검토해야 한다. 독립 검증 실패 또는 시간 초과는 에이전트 자체가 성공했더라도 작업 실패로 기록한다. 검증을 지정하지 않은 경우에는 자동으로 테스트를 실행하지 않는다. GPU 예약은 독립 검증이 끝날 때까지 유지하는 보수적 정책이다.

사용할 수 있는 모듈 이름은 `.venv/bin/python tools/review/tests/run_management_audit.py --help`에서 확인한다. 예를 들어 `tools.review.tests.test_hermes_service`를 지정하면 그 모듈만 독립 실행한다.

공용 GPU 대기열은 Hermes의 초기 예약을 32,768 MiB로 잡고 다른 대기열 작업과 배타적으로 실행한다. 이 배타성은 대기열이 관리하는 예약에만 적용된다. 대기열 밖에서 직접 실행한 GPU 프로세스는 이 예약으로 중지하거나 선점하지 않지만, 가용 메모리가 충분하면 동시에 실행되어 성능이 저하될 수 있다. 다른 작업에 GPU를 사용하는 동안에는 GPU 프로세스와 상태를 확인하고 필요하면 요청을 미룬다. 이미 실행 중인 작업은 선점하지 않는다. GPU 메모리 부족 시 대기하며 이미지 생성기를 CPU로 대체하지 않는다. 취소는 요청과 실제 종료를 구분한다. Hermes 프로세스 그룹을 정리한 후 예약을 해제하며 가능한 부분 diff와 로그를 보존한다. 대기열 실행기가 비정상 종료되면 다음 대기 작업이 시작 시각과 작업별 식별값이 일치하는 프로세스 그룹을 PID 핸들로 정리하고 기존 작업을 실패로 표시한다. 식별값이 없거나 일치 여부를 확인할 수 없는 예약은 안전하게 대기하므로 운영자가 실제 프로세스를 확인해 복구해야 한다.

격리 공간에는 일반 파일만 복사하고 심볼릭 링크와 2 GiB 초과 복사는 거부한다. Git에서 무시된 파일은 복사하지 않는다. 다만 관리도구의 `.venv`는 격리 작업에서 공용 회귀 실행기를 사용할 수 있도록 읽기 전용으로 연결한다. 이 환경이 없거나 심볼릭 링크라면 작업을 실행하지 않는다. 실제 bubblewrap 경계 시험에서는 격리 프로세스가 호스트 루프백과 홈, 시험용 환경변수에 접근하지 못하는 것을 확인했다. 격리 `/tmp`는 최대 2 GiB의 메모리 파일 시스템이며 이 한도는 프로세스 전체 메모리 사용량에 적용되지 않는다. 외부 네트워크, 호스트 홈, 호스트 `/run`은 보이지 않으며 추론 서버와 고정 읽기 전용 관리 상태 조회만 각각 전용 로컬 소켓으로 연결한다. 격리 공간에 GPU 장치를 노출하지 않으므로 실제 GPU 생성기 검사는 Hermes 종료 후 공용 대기열에서 별도로 수행한다. `.git`도 읽기 전용이다. 모델 응답과 도구 출력은 작업 로그에 기록되므로 로컬 작업 기록도 비공개로 취급한다. 컨테이너나 VM 수준의 보안 경계를 주장하는 것은 아니다.

Hermes 샌드박스와 독립 검증 프로세스는 호스트 환경변수를 물려받지 않고 필요한 최소 환경만 사용한다. 초기 시험에서는 이 차단이 보장되지 않았다. 시험 로그의 도구 호출에서 명시적인 환경변수 조회 명령은 발견하지 못했으나, 이것만으로 과거 노출이 없었다고 증명할 수는 없다.

상세 화면과 MCP 응답은 상태·변경 diff·도구 출력·최종 답변을 제공한다. 화면에서 이력이나 세션 작업을 열면 전달된 전체 지시를 별도 읽기 전용 영역에 표시하며, 작성 중인 새 작업 지시는 보존한다. 세션 후속 작업의 지시에는 이전 대화 문맥이 포함될 수 있다. diff가 500,000바이트를 넘으면 표시가 잘리며 `diff_truncated`가 참이 된다. 전체 파일은 작업 기록의 `change.diff`에 있고 MCP의 `read_hermes_task_diff`로도 바이트 조각을 읽을 수 있다. 각 조각을 base64에서 디코딩하고 `next_offset`이 `null`이 될 때까지 바이트를 이어 붙인다. 미커밋 변경도 복사한 시점이 기준이므로 diff를 원본에 적용하기 전 기준과 충돌을 직접 확인한다.

## Codex MCP 연결

[Codex MCP 안내](https://developers.openai.com/codex/mcp)의 로컬 stdio 구성을 사용한다. 서버는 `.local/hermes-mcp/bin/python`으로 `tools/review/domains/hermes_agent/mcp_server.py`를 실행한다. 저장소 루트에서 실행하면 다음 명령이 현재 경로를 절대 경로로 등록한다. 이미 같은 이름이 등록되어 있으면 기존 설정을 먼저 확인한다.

```bash
codex mcp add slime-hermes -- "$PWD/.local/hermes-mcp/bin/python" "$PWD/tools/review/domains/hermes_agent/mcp_server.py"
codex mcp get slime-hermes
```

세션 생성은 호출자가 유지하는 32자리 소문자 16진수 ID를 사용하고 동일 ID 재시도는 기존 세션을 반환한다. 세션 메시지는 `submit_hermes_session_message`로 기존 격리 작업에 접수한다. 이전 작업이 종료된 뒤 다음 요청을 보낼 수 있으며, 최근 대화와 답변 최대 2,500자를 새 작업에 포함한다. 일부가 생략되면 `context_truncated`가 참이다. 이전 작업의 파일 변경은 다음 작업 공간에 자동 반영되지 않으며 각 작업은 기존처럼 원본의 새 격리 사본에서 시작한다. 관리 화면의 대화 세션에서 세션을 만들고 선택해 메시지와 작업 상태를 조회할 수 있다. 접수 확인이 유실되어 작업 연결이 비어 있으면 미확인 요청 복원으로 원래 식별자와 입력을 되살린 뒤 재시도한다. 선택한 세션에 대기·실행 중인 작업이 있으면 10초마다 상태를 갱신하고, 종료되면 자동 조회를 멈춘다. 대화에는 최근 도구 호출·대상·결과를 시간순으로 표시하며 긴 기록은 최근 일부만 보여 준다. 상세 출력은 기존 작업 로그에서 확인한다. 확인 시각을 표시하며 수동 새로고침도 가능하다. 접수·취소에는 Codex의 승인 정책이 적용될 수 있다. 설정 변경을 기존 대화에서 바로 사용할 수 있는지는 클라이언트 세션에 따라 확인한다. 격리 HTTP 게이트웨이 재시작 시험에서 세션과 위임 접수의 기존 ID 유지, 중복 실행 방지 및 불확실 상태 보존을 확인했다.

MCP `list_hermes_sessions_page`는 사용자 지시 내용 또는 세션 ID 일부와 페이지를 지정해 이전 세션을 조회하며, 다음 페이지에는 첫 응답의 `snapshot`을 전달한다. 세션 순서나 내용이 바뀌면 처음부터 다시 조회한다. 기존 `list_hermes_sessions`는 최근 100개 계약을 유지한다.

MCP `list_hermes_coding_tasks_page`는 `query_text`·`status_name`으로 전체 작업 이력을 검색하고 `offset_value`·`limit_value`로 결과를 나누어 읽는다. 다음 페이지에는 첫 응답의 `snapshot`을 `snapshot_value`로 전달한다. 기존 `list_hermes_coding_tasks`는 최근 100건 계약을 유지한다.

도구는 세션을 만들고 조회하는 `create_hermes_session`, `read_hermes_session`, `read_hermes_session_view`, `list_hermes_sessions`, 공용 GPU 상태와 대기열을 읽는 `read_hermes_gpu_queue_status`, `submit_hermes_coding_task`, `read_hermes_coding_task`, `list_hermes_coding_tasks`, `read_hermes_task_diff`, `cancel_hermes_coding_task`다. 접수에는 `request_identifier_value`와 `coding_prompt_text`가 필요하며, `verification_module_names`로 선택 검증 모듈을 전달할 수 있다. 같은 접수 식별자로 재시도할 때는 지시와 검증 모듈을 모두 동일하게 유지한다. 조회·취소는 `job_identifier_value`를 사용한다. diff 조회의 `byte_offset_value`와 `byte_limit_value` 기본값은 각각 0과 65,536이며 최대 조각 크기는 262,144바이트다. GPU 상태 도구는 기존 `/management/gpu-queue`를 조회하며 응답의 조회 시각과 짧은 GPU 측정 캐시를 구분한다. 격리 Hermes 작업자는 고정 읽기 전용 상태 조회 명령을 통해 GPU와 대기열을 조회할 수 있다. 이 연결은 임의 명령이나 외부 네트워크를 전달하지 않는다. 모델이 실제로 조회를 선택해 사용하는지는 별도 시험이 필요하다. MCP 서버는 기본적으로 `http://127.0.0.1:8771`의 정해진 관리 경로에만 연결하며, `SLIME_MANAGEMENT_GATEWAY_URL`로 지정하는 주소도 localhost HTTP로 제한한다.

공용 게이트웨이가 이전 코드로 이미 실행 중이면 새 명령이 `400`으로 거절될 수 있다. 작가 작업을 포함한 현재 상태를 확인한 뒤 정식 실행 스크립트의 재시작 절차를 사용한다. 접수 중인 요청이나 별도 GPU 작업의 상태를 확인하지 않은 채 기존 프로세스를 강제 종료하지 않는다. 게이트웨이 재시작과 작업 재접수는 별개다.

FLUX 프로필·음악·영상·번역 위임의 중지는 소유 서비스가 `cancel_requested: true`를 반환한 경우에만 요청 접수로 표시한다. 화면에서 Kimodo·일반 FLUX를 포함한 중지 응답이 없거나 형식이 다르면 확인창을 닫고 결과 확인 필요로 표시한다. 같은 접수 ID와 작업 ID를 유지해 해당 작업 상태와 실제 종료를 확인한 뒤 재요청 여부를 판단한다. 이미 종료된 작업의 중지 요청은 기존 생성기가 거절할 수 있으므로 MCP에서도 중지 요청을 반복 성공으로 표시하지 않는다.

## 검증 범위

이 장비에서 64,000 문맥, 전체 66개 레이어 GPU 적재, 단일 함수 결함 수정, 격리 작업의 diff 회수, GPU 적재 중 취소와 실행기 강제 종료 후 예약 복구를 시험했다. 별도 시험 게이트웨이에서는 실제 Codex가 MCP로 코딩 작업을 접수했고 Hermes가 작성한 테스트 2개를 독립된 격리 환경에서 통과시켰다. MCP 중복 접수 방지도 별도 시험했다. 관측 메모리 피크 약 17.9 GiB는 해당 시험의 값이며 모든 작업의 최대치가 아니다. 재시작한 운영 게이트웨이에서 MCP 작업 접수와 브라우저 이력·완료 상태·diff 조회를 확인했다.

최신 단순 파일 작성 시험에서는 실행은 완료됐지만 지정된 텍스트 끝에 줄바꿈을 추가해 정확한 바이트 비교에 실패했다. 에이전트의 완료 응답과 검사 통과를 구분하고 생성된 diff와 독립 검사 결과를 검토해야 한다.

터미널만 제공한 후속 시험에서는 테스트 추가를 마치기 전에 12회 도구 호출 한도에 도달했다. 이후 파일 패치 도구를 추가하고 한도를 20회로 조정했으며, 이 변경의 실제 과제 성능은 별도 시험 결과로 판단한다.

별도의 Codex 위임 시험에서 Hermes는 기존 서비스 테스트에 잘못된 요청 ID 검사를 추가하고 공용 회귀 실행기를 한 차례 사용했다. 첫 검사 뒤 테스트를 다시 수정했지만 최종 수정 후 직접 재실행하지 않았다. 최종 diff는 독립된 격리 환경의 공용 실행기로 확인해 6개 검사가 통과했다. 이 시험의 GPU 메모리 관측 피크는 17,923 MiB였고 모델 로딩을 포함한 실행 시간은 약 9분 15초였다. 같은 모델의 모든 작업 속도를 대표하지는 않는다.

2026-11-17 추가 시험에서는 실제 Codex가 MCP를 통해 요청을 접수하고 Hermes가 격리 사본의 잘못된 요청 ID 검사를 추가했다. 작업 후 지정한 공용 회귀 모듈의 자동 독립 검증 7개가 모두 통과했으며, 관측 GPU 메모리 피크는 17,924 MiB였다. 같은 날 최신 pidfd 방식으로 GPU 적재 중 취소했을 때 작업 상태와 부분 결과를 보존하고 GPU 예약을 해제하는 것도 확인했다. 이 결과는 별도 시험 게이트웨이에서 얻었으며 기존 운영 게이트웨이의 적용 검증을 대신하지 않는다.

운영 게이트웨이 재시작 후 Codex MCP로 격리 코딩 작업을 접수해 요청 ID 거부 검사를 추가했고, 관리 화면에서 같은 작업의 완료 상태와 diff를 확인했다. 이 작업은 자동 검증을 지정하지 않아 별도로 격리 공용 회귀 실행기를 실행했으며 7개 검사가 통과했다. 모델이 직접 실행한 동일 모듈 검사도 통과했다. 변경은 격리 사본에만 존재한다.

모델 파일 보유량 조회는 모델별 파일 수와 합계 용량만 반환한다. 파일이 있다는 사실은 준비 완료나 해시 검증을 뜻하지 않으며, 일부 경로 읽기에 실패하면 불완전으로 표시한다. 격리 에이전트는 `/runtime/.venv/bin/python /control/management-status.py model-inventory`로 같은 정보를 읽는다. 다운로드 상태 조회는 기록 정리 부수 효과가 있으므로 이 조회에 포함하지 않는다.

전체 관리 서비스 등록 목록은 공용 게이트웨이의 서비스·명령 등록을 읽는다. 목록은 게이트웨이의 명시 차단과 음악·캐릭터 애니메이션 서비스에서 확인된 폐기 명령과 Wan VACE·Fun Control과 FLUX 이미지·표정 생성기의 확인된 조건부 제한을 구분해 사유를 표시한다. 음악·영상·FLUX·Kimodo·작가·번역과 맵 에셋·스프라이트 편집 서비스에는 연결된 주요 Hermes 명령을 화면과 `hermes_links` 응답으로 함께 제공한다. 이전 게이트웨이가 연결 정보를 보내지 않으면 화면에 미제공으로 표시한다. 모델 관리에 등록된 서비스는 준비 상태와 접수 조회도 연결하며 준비 요청은 기존 정책이 허용하는 경우에만 기재한다. 이 연결은 해당 서비스의 모든 기능을 지원한다는 뜻이 아니다. 조건부 제한은 전체 목록이 아니다. 그 밖의 소유 서비스 정책은 아직 전수 확인하지 않았으며, 차단 표시가 없는 명령도 실행 지원이나 권한이 확인된 것은 아니다. 격리 에이전트는 `/runtime/.venv/bin/python /control/management-status.py service-registration`으로 전체 등록을 조회하거나 `service-registration '{"query":"music","limit":5}'`으로 최대 10건씩 검색하고 `capabilities` 인자로 화면·MCP와 같은 실제 Hermes 기능 목록과 미기재 명령을 확인한다. 서비스 등록 검색은 서비스 이름·등록 명령·Hermes 연결 명령과 한국어 기능명을 대상으로 한다. 화면의 서비스·기능 검색과 Codex MCP `search_hermes_management_services`도 같은 검색을 사용하며 최대 10건씩 조회한다. 다음 시작 위치는 화면에 표시하거나 MCP 응답의 `next_offset`으로 반환한다. `capabilities '{"query":"FLUX","limit":10}'`은 Hermes 기능을 최대 20건씩 검색한다. 두 검색의 다음 페이지는 같은 검색어와 `next_offset`을 `offset`으로 전달한다. 이 조회는 실행 권한을 부여하지 않는다.

Codex MCP의 `delegate_hermes_flux_generation`은 사용자가 요청한 FLUX 일반 이미지 생성을 기존 공용 GPU 대기열에 위임한다. 입력은 `action=generate`, `prompt`, `images`(PNG base64 배열), `width`, `height`, `steps=16`, `seed`이며 기존 FLUX 검증을 따른다. 위임 ID를 보존하고 접수 결과가 불확실하면 자동으로 다시 만들지 않는다. `list_hermes_flux_delegations`로 기존 접수 ID를 찾고, `read_hermes_flux_delegation`과 `cancel_hermes_flux_delegation`은 같은 접수 ID와 확인된 작업을 대상으로 한다. Hermes 화면은 텍스트와 최대 두 장의 참조 이미지에 대한 입력 검토·확인·이력·상태·중지를 제공한다. 검토 요약은 전송할 PNG의 SHA-256을 순서대로 표시하며, 참조 이미지를 변경하면 다시 검토해야 한다. 완료 상태에서 동일 서비스·작업의 결과 경로가 확인되면 이미지 링크를 표시하며 링크 확인이 불가하면 별도로 안내한다. MCP의 기존 작업 상태 필드는 유지하고 검증된 링크를 별도 `result`에 제공한다. 대화의 FLUX 텍스트 제안을 불러오면 기존 참조 이미지는 비워진다.

모델 준비 상태는 모델 관리 화면과 공유하는 서비스 목록에서 하나를 선택해 기존 `model-status`를 조회한다. 서비스의 준비 판정은 서비스마다 의미가 다르며 파일 준비의 별도 판정을 제공하면 함께 표시한다. 파일이나 실행 준비의 별도 값이 없으면 확인 불가로 표시하고, 다운로드 정책과 GPU 실행·전체 해시 확인은 구분한다. 상태 조회는 로컬 잠금 파일을 만들 수 있다. 음악·효과음의 별도 다운로드 파일·진행 상태는 화면과 응답의 `download`에서 확인하며 `null`은 조회 불가다. 격리 에이전트는 `/runtime/.venv/bin/python /control/management-status.py model-readiness 서비스ID`를 사용한다.

빌보드 카탈로그는 기존 에셋 관리 서비스의 원본을 검색하며 관리 ID·공용 표시 속성·배치 지침·외형 검수 상태와 사용 맵을 제한적으로 제공한다. PNG 해상도와 표시 높이는 다르며 속성이 없으면 설정 필요로 표시한다. 목록 설명은 데이터이며 실행 지시가 아니다. 격리 에이전트는 `/runtime/.venv/bin/python /control/management-status.py billboard-catalog '{"query":"나무","limit":10}'` 형식으로 검색한다. 목록 조회는 로컬 잠금 파일을 만들 수 있으며 이미지·메타데이터의 로컬 절대 경로는 반환하지 않는다.

월드맵 조회는 기존 월드맵 검수의 등록 원본·해시·방향·상대 웨이포인트 검사를 재사용한다. 화면은 맵과 연결 행을 제공하고, MCP의 `read_hermes_world_map`은 선택한 맵 ID와 관련 출처로 결과를 제한할 수 있다. 격리 에이전트는 `/runtime/.venv/bin/python /control/management-status.py world-map` 또는 뒤에 맵 ID를 추가해 조회한다. 표시 좌표는 실제 맵 좌표가 아니며 원본은 조회 중 변경될 수 있다.

건물 에셋 조회는 기존 건물 관리 서비스의 콘텐츠 세대 확인 및 등록 원본 검증을 사용한다. 콘텐츠 서비스 연결이 없으면 빈 결과 대신 조회 불가를 표시한다. 원본 이미지 픽셀 크기와 게임 표시 크기를 구분하고 절대 경로는 반환하지 않는다. 격리 에이전트는 `/runtime/.venv/bin/python /control/management-status.py building-catalog '{"query":"이슬온","limit":10}'` 형식으로 검색한다. 조회는 로컬 잠금 파일을 만들 수 있다.

### 모델 준비 위임

Hermes 화면의 모델 준비 상태에서 서비스와 접수 ID를 확인하고 준비 영향을 검토한 후 요청한다. Codex MCP의 `prepare_hermes_managed_model`도 동일한 기존 모델 관리 정책을 적용한다. 다운로드·디스크 사용과 서비스별 GPU 대기열 작업이 발생할 수 있다. 접수 응답은 준비 완료를 뜻하지 않으며 모델 준비 상태에서 별도로 확인한다. 같은 ID는 중복 실행하지 않는다. 응답이 불확실하면 이력과 서비스 상태를 확인하고 임의로 새 ID를 발급해 재요청하지 않는다. 접수 이력은 화면 및 `list_hermes_model_preparation_receipts`에서 찾는다. 격리된 Hermes 모델에는 준비 실행 명령을 노출하지 않는다.

### 콘텐츠 DB 상태

Hermes 화면과 MCP 및 격리 상태 조회의 `content-database-status`에서 DB 저장 세대, 원장 반영 세대, 대기 여부와 최근 반영 상태를 확인한다. 로컬 에셋 저장소의 맵 YAML 파일 집합과 SHA-256을 등록부 및 인접 백엔드 저장소의 잠금 목록과 읽기 전용으로 비교해 일치·불일치·확인 불가를 별도 표시한다. 결과의 `map_sources`에는 불일치 건수와 최대 30개 상대 경로 및 목록 생략 여부가 포함된다. DB 조회 실패와 파일 비교 실패도 각각 구분한다. 파일 비교는 조회 시점 기준이며 DB 내용과의 일치나 실행 중인 백엔드에 적용됐는지는 확인하지 않는다. 기존 API의 `snapshotGeneration`은 호환 필드명이며 파일 스냅샷을 보관한다는 뜻이 아니다. 동기화·복구 명령은 이 조회에서 실행하지 않는다.

### 야외 맵 초안

Hermes 화면에서 야외 맵 원본을 불러와 `cells` 변경과 전체 `objects` 장식 목록을 편집한다. 초안 검증은 기존 편집기의 리비전, 충돌, 출구 도달성 등을 사용하고 임시 초안 기록을 남긴다. 사용자는 초안과 원본을 검토한 후 저장을 확인한다. 저장은 기존 편집기를 통해 원본·등록부·소비자 잠금·카탈로그 또는 콘텐츠 DB를 갱신할 수 있다. MCP의 `load_hermes_field_map`, `preview_hermes_field_map`, `save_hermes_field_map`도 같은 경로를 사용한다. 저장 응답이 유실되면 같은 접수 ID와 초안을 유지하고 원본 상태를 확인한다. 이 야외 맵 편집 경로는 도시 맵에 사용할 수 없으며, 도시 맵은 아래의 별도 경로를 사용한다.

대화의 야외 맵 제안은 선택한 작업 ID와 요청한 맵 ID가 조회 응답과 일치해야 초안에 적용한다. 저장 결과와 접수 이력도 접수 ID·맵 ID를 대조하며, 응답이 다르거나 유실되면 원본과 이력을 확인하고 자동으로 다시 저장하지 않는다.

야외 맵 저장 응답과 접수 이력은 같은 접수 ID를 반환한다. 화면은 ID·맵·완료 상태·저장 여부를 확인하며 결과가 불명확하면 저장을 반복하지 않는다. 저장 완료는 실행 중인 게임 서비스 반영까지 보장하지 않으므로 원본·등록부·소비자 잠금과 실행 서비스를 별도로 확인한다.

야외 맵 저장 접수는 화면의 이력 조회 또는 MCP `list_hermes_field_map_receipts`, `read_hermes_field_map_receipt`로 확인한다. 맵 원본 읽기도 기존 편집기 잠금 파일을 만들 수 있다.

### 도시 맵 초안

콘텐츠 DB 연결 시 도시 원장을 불러와 세대·리비전을 유지한 초안을 검증하고 사용자가 확인한 뒤 저장한다. 건물·통행·출입구 검증은 기존 도시 편집기가 수행한다. 변경이 없으면 DB 쓰기를 생략한다. 저장 응답이 불확실하면 도시 저장 이력과 원장 상태를 확인하고 같은 접수 ID를 유지한다. MCP는 `load_hermes_city_map`, `preview_hermes_city_map`, `save_hermes_city_map`과 접수 이력 조회를 제공한다. 저장 후 원장 반영 상태는 별도 확인한다.

격리 Hermes는 `management-status.py field-region`에 맵 ID와 영역·페이지 JSON을 전달해 최대 16×16 셀과 최대 30개 오브젝트를 읽는다. 다음 페이지에는 반환된 `revision`과 `object_next_offset`을 사용한다. `blocked`는 원본 지형 차단값이며 빌보드·고도를 반영한 실제 통행 판정은 기존 맵 검증에서 확인한다. MCP의 `read_hermes_field_region`도 같은 계약을 사용한다.

영역 응답의 `summary`는 서버가 계산한 지형·고도·원본 차단 셀 집계다. 모델이 개별 셀을 수동 합산한 내용은 원본 집계와 대조해야 한다.

Hermes가 야외 맵 셀 변경을 제안하면 세션 작업을 선택한 후 야외 맵 화면의 제안 불러오기로 현재 초안을 교체할 수 있다. 제안 당시 리비전이 현재 원본과 다르면 거부하며, 현재 장식 목록은 유지한다. 불러오기는 저장이 아니며 사용자는 셀 내용을 확인하고 기존 검증과 저장 확인을 별도로 수행한다. MCP의 `read_hermes_field_map_proposal`은 제안만 반환한다.

### 프롬프트 번역 위임

Hermes 화면에서 한국어 원문과 영어 또는 중국어 간체, 확인 용어를 입력해 검토한 뒤 GPU 대기열 접수를 확인한다. 기존 번역기의 승인 용어 검증과 용어·조건 점검을 재사용한다. 결과의 검토 항목은 자동 품질 보증이 아니므로 사용자가 확인한다. 응답이 유실되면 같은 접수 ID를 유지하고 번역기 이력을 확인한다. MCP는 `delegate_hermes_translation`, `read_hermes_translation_status`, `list_hermes_translation_receipts`, `cancel_hermes_translation`을 제공한다. 중지는 접수 ID와 작업 ID가 일치할 때 요청한다.

Hermes가 번역 위임을 제안하면 세션 작업을 선택하고 번역 위임 화면에서 제안을 불러온다. 기존 입력이 교체되며 원문·언어·용어를 확인하고 다시 검토한 뒤 GPU 접수를 확인해야 한다. MCP `read_hermes_translation_proposal`은 완료된 작업의 제안만 읽으며 번역을 실행하지 않는다.

### 작가 AI 작업 위임

문서 색인 갱신, 작성 제안, 중복 검토를 기존 작가 AI와 공용 GPU 대기열에 위임할 수 있다. 작성·중복 검토 전에는 실제 색인 최신성을 확인한다. 접수 ID가 같으면 중복 실행하지 않으며 응답 유실 시 이력과 작업 상태를 확인한다. Hermes의 diff는 20개 변경 및 100,000바이트로 제한되므로 원본 적용 전 [작가 AI](/management/frame/writer-agent/)에서 전체 변경과 근거를 확인한다. 전체 변경과 근거를 작가 AI 화면에서 확인한 뒤 Hermes의 별도 적용 확인 절차를 사용할 수 있다. 제안을 다시 열면 이전에 확인한 작가 결과와 전체 검토 확인이 해제되므로 변경과 근거를 다시 확인해야 한다. MCP는 `delegate_hermes_writer`, `read_hermes_writer_status`, `list_hermes_writer_receipts`를 제공한다.

작가 제안 적용은 전체 diff가 표시 가능한 검토 상태, 작업 ID와 제안 해시가 일치해야 한다. 사용자는 작가 AI 화면에서 전체 변경과 근거를 확인하고 적용 대상과 원본 변경을 다시 확인한다. 적용 결과가 불확실하면 적용 이력과 원본을 확인하고 같은 접수 ID로 확인한다. MCP는 `apply_hermes_writer_proposal`, `read_hermes_writer_apply_receipt`, `list_hermes_writer_apply_receipts`를 제공한다.

### FLUX 프로필 위임

일반 이미지·캐릭터·마네킨·빌보드·소품·식생·건물·심리스 8개 기존 FLUX 프로필을 선택해 최대 두 장의 참조를 전달하고 GPU 대기열에 위임한다. 마네킨·빌보드·건물에는 첫 참조가 필요하며 두 번째 참조만 지정할 수 없다. 심리스는 512×512 무참조만 허용한다. 프로필 변경 시 기본 크기를 적용하며 입력과 참조가 바뀌면 다시 검토한다. 완료 응답의 이미지 경로가 위임 서비스와 작업 ID에 정확히 일치하면 화면과 MCP에 결과 링크를 제공하고, 확인 가능한 링크가 없으면 완료 상태와 구분해 표시한다. 상세 결과와 로그는 해당 생성기 화면에서 확인한다. 별도 FLUX 표정 생성기는 전용 화면에서 얼굴 참조와 표정 프리셋으로 위임한다. MCP의 `delegate_hermes_flux_profile`과 상태·이력·중지 도구는 기존 프로필 검증과 서비스별 접수 기록을 사용한다.

FLUX 표정 생성에는 얼굴 참조 한 장과 기존 표정 프리셋이 필요하다. 선택한 한국어 추가 지시는 기존 번역 대기열을 거친다. 입력과 참조를 검토하고 GPU 접수를 확인하며 결과의 얼굴 특징과 색상은 표정 생성기에서 비교한다. MCP는 `delegate_hermes_flux_profile`의 서비스 `flux-expression`과 공용 상태·이력·중지 도구를 사용한다.

### 음악·효과음 위임

Hermes 화면 또는 MCP에서 HeartMuLa 음악과 Dasheng 효과음의 입력을 검토해 기존 공용 GPU 대기열에 접수한다. HeartMuLa는 가사와 최대 출력 상한을 지정하며 빈 가사가 무보컬이나 완결 길이를 보장하지 않는다. Dasheng은 길이를 모델이 결정하며 음악 가사를 받지 않는다. 서비스별 입력 검증과 접수 기록을 사용하고, 결과는 동일 출처 음원 링크 또는 해당 생성기 이력에서 확인하며, 완료 상태라도 확인 가능한 음원 링크가 없으면 별도로 표시한다. 생성 결과는 에셋에 자동 등록되지 않는다. MCP는 `delegate_hermes_audio`, `read_hermes_audio_status`, `list_hermes_audio_receipts`, `cancel_hermes_audio`를 제공한다.

Hermes 화면의 생성기 원본 이력 조회는 Hermes 외 작업을 포함해 한 페이지에 최대 30건의 기록 상태를 보여 주며 다음 페이지로 이동할 수 있다. MCP `list_hermes_audio_source_history`는 페이지별로 조회하며 후속 페이지에 첫 응답의 `snapshot`이 필요하다. 로그·지시를 반환하지 않으며 기록 상태는 실제 프로세스 생존을 보증하지 않는다. 개별 상태 파일이 없거나 손상된 작업은 `unknown`으로 표시한다. 영문·숫자·밑줄·하이픈으로 된 80자 이하의 이전 ID는 표시하며 작업 상태 파일이 없으면 색인에 남은 상태를 사용하며 상태 출처를 작업 파일·이전 색인·확인 불가로 구분한다. 읽을 수 없거나 이 ID 형식에 맞지 않는 색인은 목록에서 제외하고 `unavailable_count`로 건수를 알린다. 원 생성기에서 해당 기록을 확인해야 한다. 원 서비스 잠금 파일이 생성될 수 있다.

Hermes가 음악·효과음 위임을 제안하면 세션 작업을 선택하고 오디오 위임 화면에서 제안을 불러온다. 기존 입력이 교체되며 서비스·지시·가사·길이·가정을 확인하고 다시 검토한 후 GPU 접수를 확인해야 한다. 음악은 가사·최대 출력 상한을 보존하고 효과음은 길이를 지정하지 않는다. MCP `read_hermes_audio_proposal`은 제안만 읽으며 생성하지 않는다.

### 동작·영상 위임

DWPose와 Wan Animate-2·Fun Control·VACE의 설정 JSON과 순서가 있는 PNG, 동작·포즈·편집·마스크 MP4 첨부를 검토해 기존 생성기와 GPU 대기열에 위임한다. 화면에서는 이미지·영상·마스크를 파일로 첨부해야 하며 설정 JSON에 직접 인코딩해 넣을 수 없다. 화면 검토 요약에는 각 첨부의 역할·바이트 크기·전체 SHA-256을 표시한다. 화면 업로드 합계는 24MiB, MCP 요청 JSON은 39MB 이하다. 서비스별 모델·프레임·이미지·영상 검증은 기존 생성기가 수행한다. 서비스 전환은 설정 JSON을 기본 예제로 교체한다. 결과 링크는 서비스·작업·실행 시도가 일치할 때만 표시하며, 완료 기록과 결과 파일 확인 실패 또는 일부 확인을 구분한다. 상태 조회에 기존 중단 작업 복구가 따를 수 있다. MCP는 `delegate_hermes_video`, `read_hermes_video_status`, `list_hermes_video_receipts`, `cancel_hermes_video`를 제공한다. 실제 GPU 메모리·속도·결과 품질은 별도 검증해야 한다.

Hermes가 동작·영상 작업을 제안하면 세션 작업을 선택하고 위임 화면에서 불러온다. 제안은 서비스·입력 모드·장면 지시만 포함하며 임의 경로와 첨부를 지정하지 않는다. 불러오기는 기존 설정과 첨부를 교체하므로 필요한 PNG·MP4를 다시 첨부하고 기본 프레임·스텝과 기타 설정을 검토한다. 기존 생성기 검증과 GPU 확인 전에는 작업이 실행되지 않는다. MCP `read_hermes_video_proposal`은 제안만 조회한다.

빌보드 공용 속성 변경은 MCP에서 원본 불러오기·미리보기·사용자 확인 후 저장·접수 확인을 지원한다. Hermes 화면에서도 카탈로그 행을 선택해 편집 ID를 채우고 현재 속성, 변경 전후, 영향 맵과 경고를 확인한 후 저장할 수 있다. 기존 파일 편집은 revision·검증 토큰과 공용 잠금을 사용하고 등록부·백엔드 잠금·카탈로그를 함께 갱신한다. DB 편집도 에셋별 revision을 확인하고 사용 맵마다 DB 스냅샷의 접지·장식 간 충돌을 경고한다. 이는 각 미리보기 시점의 검사이며 이후 맵 변경이나 전체 게임 통행의 유효성까지 보장하지 않는다. MCP 저장 전 사용자는 변경 전후·영향 맵·경고와 이 제한을 확인해야 한다. 저장 직전 공용 편집 잠금 안에서 검수 결과를 다시 비교하므로 관리도구를 통한 편집이 검수와 저장 사이에 끼어들지 않는다. 직접 파일을 수정하거나 DB를 다른 경로에서 변경하는 동시 작업은 이 잠금의 보호 범위 밖이다. 검수 결과가 달라지면 재검토가 필요하며 응답 유실은 unknown으로 남고 자동 재저장하지 않는다.

Hermes는 카탈로그에서 확인한 빌보드 속성의 현재값과 새 값을 제안할 수 있다. 세션 작업에서 제안을 불러올 때 현재 원본의 해당 속성이 제안의 현재값과 다르면 거절한다. 제안은 편집 초안일 뿐이며 사용자가 기존 미리보기의 변경 전후·맵 경고를 확인하고 저장해야 적용된다.

맵 이펙트는 Hermes 화면·MCP·격리 조회에서 콘텐츠 DB의 검수 목록과 좌표를 읽는다. 격리 명령은 `management-status.py effect-catalog '{"query":"", "limit":20}'`와 `management-status.py effect-detail 이펙트ID`다. 이미지 파일과 로컬 경로는 반환하지 않으며 실제 외형은 이펙트 검수 화면에서 확인한다. 공용 좌표·불투명도는 화면과 MCP에서 원본 리비전 확인, 변경 전후 검토 후 저장할 수 있다. 이미지와 연결 대상은 변경하지 않으며 응답 유실은 unknown으로 남는다. 신규 이펙트 등록은 화면과 MCP에서 원본 검토·등록·접수 조회를 지원한다. 웨이포인트는 4×2 8프레임 PNG와 등록된 애니메이션 메타데이터를 검증한다. 기존 백엔드의 등록·교체 API도 사용할 수 있다. 격리 PostgreSQL과 기존 백엔드 API·관리 게이트웨이를 연결해 등록·교체·중복 재확인을 검증했다. 지원 여부를 알 수 없는 서버의 응답이 유실되면 접수 상태를 확인한다. 응답이 불확실하면 원장을 확인하고 자동 재등록하지 않는다. 웨이포인트 교체는 MCP의 `preview_hermes_waypoint_replacement`, `replace_hermes_waypoint`, `read_hermes_waypoint_receipt`로 검토·실행·접수를 확인할 수 있다. 기존 DB ID가 제거되므로 실제 외형과 사용 맵을 기존 이펙트 편집기에서 확인해야 한다. 게임은 에셋 저장소 원본을 직접 참조하므로 DB 교체만으로 바뀌지 않으며 게임 참조·잠금 목록은 별도 갱신이 필요하다. 원본 리비전·등록 해시가 변경되면 다시 검토하며 응답 유실은 unknown으로 남는다. Hermes 화면의 이펙트 조회에서도 선택한 대상과 초안·접수 ID를 검토한 뒤 교체할 수 있으며 같은 영역에서 현재 DB 저장·원장 반영 세대를 조회한다.

이펙트 등록과 웨이포인트 교체는 응답의 접수 ID와 결과 이펙트 ID를 확인한다. 전송 오류나 불일치 응답이 오면 화면의 이전 실행 확인을 해제하며, 같은 접수 ID로 원장과 접수 상태를 확인하기 전 자동으로 다시 실행하지 않는다. 등록 이력의 완료는 저장 시점의 DB 결과이며 현재 원장 반영이나 게임 사용을 뜻하지 않는다.

신규 이펙트는 기존 에셋 등록부의 이미지와 선택한 메타데이터를 해시 검증한다. `swarm`·`fog`·`billboard-glow`는 4×2 8프레임 정렬 정보가 필요하며, 안전지대 오라는 정렬 정보를 받지 않고 이펙트 좌표 검수기에 표시되지 않는다. 안개·군집 등록은 정렬 키의 원자적 중복 차단을 지원하는 에셋 서비스를 요구한다. 기존 백엔드에도 이 보호와 지원 표시를 추가했으며, 해당 변경이 반영되지 않은 구버전 서버는 안전한 신규 등록 대상에서 제외한다. 기존 원장 조회와 좌표 편집은 유지한다. 빌보드 발광은 콘텐츠 DB의 연결 대상과 리비전을 확인한다. 등록 검토에서 기존 ID·정렬 텍스처·키 충돌을 확인하고, 정렬 정보가 있는 등록은 공용 편집 잠금 안에서 충돌과 빌보드 리비전을 다시 확인한다. 빌보드 발광 등록은 에셋 API가 같은 DB 트랜잭션에서 대상의 활성 상태와 정수 리비전을 다시 검사한다. 이 경로에는 `/effects/reviewed`를 제공하는 에셋 서비스 또는 해당 기능으로 갱신된 기존 백엔드가 필요하다. 등록 검토에서 서비스의 지원 표시를 확인하므로 구버전은 접수 전에 갱신 안내를 표시한다. 검토 후 서비스가 바뀌거나 응답이 유실되면 접수 결과가 미확인으로 남을 수 있다. 관리도구 밖의 직접 SQL 변경은 공용 편집 잠금의 보호 범위 밖이다. 신규 등록 API에는 서버 측 요청 ID가 없으므로 응답 유실 시 Hermes 접수는 `unknown`이며 기존 원장 확인 없이 새 ID로 다시 등록하지 않는다. 접수의 DB 세대와 저장 시 원장 대기 상태는 현재 원장 반영 완료를 뜻하지 않는다. 실제 사용 맵·이미지 외형·게임 참조는 별도 검수한다.


Hermes가 이펙트 좌표 변경을 제안하면 화면이나 MCP에서 완료 답변을 읽을 수 있다. 화면은 현재 리비전과 프레임 수를 확인한 뒤 초안을 불러오며, 변경 전후 검토와 시각 검수 후 별도 저장이 필요하다. 모델은 조회한 좌표만으로 이미지 외형을 확인했다고 주장할 수 없다.

격리 PostgreSQL·콘텐츠 API·관리 게이트웨이를 함께 사용하는 회귀 검사는 이펙트 좌표와 빌보드 속성의 조회·미리보기·저장·중복 요청·구 리비전 거절을 확인한다. 시험 DB에서 실제 등록된 이펙트 이미지 해시를 확인하고, 빌보드 사용 맵의 충돌 경고와 맵 변경에 따른 재검토를 검사한다. 운영 DB와 실제 배포 검증을 대체하지 않는다. 격리 DB 검사는 에셋 서비스 실행 안내를 따른다.

등록된 스프라이트 시트는 Hermes 화면·MCP와 격리 조회에서 검색하고 원본 해시와 프레임·앵커를 페이지별로 확인한다. 두 번째 페이지부터 첫 응답의 snapshot을 전달하며 이미지 또는 메타데이터 해시가 바뀌면 처음부터 다시 조회한다. 격리 조회는 `management-status.py sprite-catalog '{"query":"walk"}'`와 `sprite-detail`의 path·offset·limit JSON을 사용한다. 기준 시트·이미지 생성 및 원본 갱신은 기존 스프라이트 편집기를 사용한다.

등록 시트의 앵커는 Hermes 화면과 MCP에서 변경 초안을 검토하고 저장할 수 있다. 기존 편집기가 시트 이미지를 다시 패킹하므로 미리보기에서 재패킹된 시트 이미지와 출력 크기·해시, 모든 프레임의 전후 위치 및 앵커 변경을 확인해야 한다. 미리보기 이미지의 SHA-256을 검증한다. 저장은 애니메이션·등록부·프런트 잠금을 갱신하며 시각적 재생 검수가 별도로 필요하다. 미리보기는 임시 시트 출력을 생성하고 응답 유실은 unknown으로 보관한다.

Hermes는 등록된 시트의 프레임 ID와 snapshot을 조회해 앵커 변경을 제안할 수 있다. 화면은 제안을 불러올 때 현재 원본 snapshot을 재확인하며, 실제 재패킹 이미지와 프레임 위치 검토 및 저장은 별도다. 모델에는 픽셀이 전달되지 않으므로 외형·재생에 대한 주장은 별도 검수가 필요하다.

스프라이트 앵커 검토 화면과 MCP는 기존 GIF 생성기로 임시 재생 검수를 제공한다. 선택 시트 전체 프레임을 균일 FPS로 앵커 정렬하므로 실제 클립의 순서·속도나 게임 렌더링과 다를 수 있다. 원본은 변경하지 않지만 임시 시트와 GIF를 생성한다.

앵커 변경 검토에서는 선택 시트에 포함된 등록 클립을 선택해 원래 프레임 순서·지속 시간·반복 여부로도 재생할 수 있다. GIF는 프레임 경계를 10ms 단위로 반올림해 한 주기의 시간 오차 누적을 줄이며 다음 클립 전환과 게임 렌더러는 재현하지 않는다.

Kimodo DWPose MIGraphX 빌드 상태는 Hermes 화면의 모델 준비 영역과 MCP `read_hermes_kimodo_build_status`에서 확인한다. 격리 Hermes에서는 `/runtime/.venv/bin/python /control/management-status.py kimodo-build-status`로 같은 기록을 조회한다. GPU를 초기화하지 않고 최근 빌드 기록만 읽는다. 캐시 유효성과 실제 작업 생존 여부는 확인하지 않는다. 빌드 요청과 캐시 유효성 검사, 상세 로그는 모델 관리에서 확인한다. 모델 관리의 캐시 검사는 공용 GPU 대기열에서 배타적으로 수행한다.

Hermes 화면의 이미지·영상 원본 이력과 MCP `list_hermes_generator_source_history`는 FLUX·Kimodo·DWPose·Wan·번역과 작가 AI의 Hermes 외 작업도 조회한다. 작가 이력은 문서와 요청을 읽지 않고 기록된 단계만 표시한다. 기록 상태만 제공하며 영상의 중단 작업 복구를 실행하지 않는다. 화면과 MCP는 스냅샷을 사용한 페이지 조회를 제공한다. 화면은 한 페이지에 최대 30건을 표시한다. 실제 작업 생존과 결과 품질은 생성기에서 확인한다. 격리 Hermes는 `management-status.py source-history` 뒤에 `{"service":"flux-image","limit":5}`와 같은 JSON을 전달하여 오디오와 이미지·영상의 같은 기록을 읽는다. 다음 페이지에는 `snapshot`과 `next_offset`을 전달한다.

아카이브된 Qwen 이미지·바닥 타일과 폐기된 Magenta·MiniMax 음악도 원본 이력의 기록 상태를 조회할 수 있다. 건물 생성기 호환 경로는 빌보드 생성기의 이력을 공유하며 응답의 `source_service`와 화면에 실제 소유 서비스를 표시한다. 이 연결은 기존 생성·재개 차단을 해제하지 않는다.

음악·효과음, 번역, 작가 AI와 Hermes 작업자도 실행 중 공용 호스트 RAM 감시를 받는다. 사용 가능 RAM이 6 GiB 미만이고 작업자 RSS가 8 GiB 이상이면 해당 작업 프로세스 그룹을 중지하고 실패로 기록한다. 음악·효과음은 작업자 주 프로세스의 RSS를, 번역·작가 AI·Hermes는 같은 프로세스 그룹의 RSS 합계를 사용한다. Hermes는 PID 핸들로 확인한 그룹을 중지하고 모델 서버 종료 뒤 예약을 해제한다. RSS 합계는 공유 페이지를 중복 계산할 수 있으며 별도 프로세스 그룹으로 분리된 자식은 포함되지 않는다. 시스템 OOM 방지를 보장하지 않는다.

음악·효과음, 영상, FLUX 프로필, 번역, 작가 AI의 Hermes 위임 상태에서 원본 오류가 공용 RAM 보호 또는 감시 실패로 기록된 경우 화면과 MCP에 각각 고정된 안내와 `host_memory_guard` 또는 `host_memory_monitor_failed` 코드를 제공한다. 원본 오류 전문은 표시하지 않는다. 감시 대상이 아닌 작업이나 다른 오류, 보호 원인이 기록되지 않은 과거 작업은 이 코드로 분류할 수 없으며 상세 원인은 소유 생성기의 기록에서 확인한다. 실제 작업 종료·GPU 예약 해제와 재요청 가능 여부도 별도 확인해야 한다.

건물 목록 후속 페이지는 같은 검색어와 첫 응답의 `snapshot`·`next_offset`을 사용한다. 콘텐츠 세대 또는 표시할 목록이 바뀌면 재조회를 요구한다. 기존 클라이언트가 snapshot 없이 임의 위치를 조회하는 계약은 유지하지만 페이지 간 일관성을 보장하지 않는다.

건물 공용 앵커 X·Y는 Hermes 건물 목록에서 선택해 초안을 만들고 변경 전후·사용 맵을 검토한 뒤 저장할 수 있다. MCP는 `preview_hermes_building_anchor`, `save_hermes_building_anchor`, `read_hermes_building_anchor_receipt`를 제공한다. 크기·그림자 변경은 기존 건물 관리 화면을 사용한다. 저장 직전 콘텐츠 세대와 현재 속성 및 검토 결과를 다시 확인하고, 응답 유실은 `unknown`으로 남겨 자동 재실행하지 않는다. 실제 이미지 배치와 게임 외형, 원장 반영은 별도 확인한다.

대화의 생성·편집·첨부 영상 제안을 열 때도 세션 전체에서 Hermes 작업 ID의 유일성을 확인한다. 중복이거나, 메시지가 잘린 구버전 응답에서 유일성을 확인할 수 없으면 제안을 열지 않는다. 메시지가 잘리지 않은 구버전 세션은 표시된 전체 메시지에서 확인한다.

운영 이력에서 지시 행을 선택한 뒤 **이 작업을 운영 대화에서 열기**를 누르면 해당 세션과 완료 작업을 선택한다. 작업 ID를 직접 입력하는 **이전 세션 작업 찾기**도 사용할 수 있다. 같은 세션의 완료 작업인지와 전체 세션 내 중복 여부를 확인하고, 제안을 열거나 실행할 때 다시 확인한다. 대화 본문은 최근 20개만 표시하며, 이전 작업의 전체 대화 내용은 운영 이력에서 확인한다. 구버전 게이트웨이에 페이지 조회가 없으면 이전 작업 선택을 지원하지 않는다. 서비스 접수 직접 조회는 응답의 접수 ID를 요청과 비교한다. ID가 없거나 다르면 이력 연결과 FLUX 참조 제안 검토를 중단한다. 이전 게이트웨이가 ID를 반환하지 않는 경우 관리 게이트웨이와 화면을 같은 버전으로 갱신한 후 다시 조회한다.

첨부 이미지·영상 접수 직후에는 응답의 서비스와 작업 ID를 확인하고 같은 접수의 후속 상태 조회에서 동일한 작업 ID를 다시 확인한다. 이력이 없거나 다른 작업을 가리키면 확인 필요로 남기고 자동 재접수하지 않는다. 후속 상태 조회 자체도 실패할 수 있으며 생성기의 실행·품질 검증과 구분한다.

운영 대화의 FLUX 제안은 일반 이미지와 참조 없는 캐릭터·소품·식생·심리스 타일 프로필을 지원한다. 기존 제안에서 `service`를 생략하면 일반 이미지이며, 다른 프로필은 서비스를 명시한다. 심리스 타일은 512×512로 제한하고 각 프로필의 기존 입력 검증·접수·상태 조회를 사용한다. 마네킨·빌보드·건물은 대화의 첨부 이미지 제안에서 첫 참조를 지정해 검토할 수 있다. 이미지별 PNG 크기와 SHA-256을 표시하며 첨부가 바뀌면 다시 검토한다. 표정 생성은 등록된 프리셋과 얼굴 참조 한 장을 대화에서 검토한다. 추가 한국어 지시 등 세부 설정은 전문 화면을 사용한다. 접수 완료는 에셋 채택이나 품질 승인이 아니다.

첨부 이미지·영상 제안을 다시 열 때는 이전 검토가 해제되고 실행 버튼이 비활성화된다. 제안 조회에 실패하면 이전 첨부와 입력도 지우므로 작업 상태를 확인하고 제안을 다시 열어 검토해야 한다.

참조 이미지 생성의 접수 응답이 유실되면 검토 상태를 해제하고 재접수 없이 원 서비스와 접수 기록을 확인하도록 안내한다. FLUX 프로필 결과는 접수 서비스와 작업 ID를 확인하고, 완료 기록의 이미지가 확인되지 않으면 별도로 표시한다.

표정 제안의 **등록된 표정 찾기**는 기존 설정에서 표정 이름과 ID를 검색한다. Codex MCP `list_hermes_expression_presets`도 같은 목록을 제공한다. 격리 에이전트는 `/runtime/.venv/bin/python /control/management-status.py expression-catalog '{"query":"기쁨","limit":10}'`으로 조회한다. 다음 페이지는 `next_offset`과 `snapshot`을 전달하며 목록이 바뀌면 처음부터 조회한다. 이 목록은 실제 표정 품질을 보증하지 않는다.

변경 제안을 다시 열 때 이전 미리보기와 저장 확인이 해제된다. 다시 조회하지 못하면 오류를 표시하며 이전 검토로 저장할 수 없다. 저장 요청 후 응답이 유실되거나 접수 기록이 확인되지 않으면 저장 여부를 단정하지 않고, 해당 원본과 같은 접수 ID의 이력을 확인하도록 안내한다. 열린 대화에서 저장을 시도한 뒤 결과를 다시 조회해도 접수 기록이 없으면 확인 불가로 표시한다. 새로고침 이후에는 화면의 시도 상태가 보존되지 않으므로 기록 부재만으로 원본 상태를 판단하지 않는다.

운영 대화에서 완료 작업을 선택하고 **이 작업의 제안 확인**을 누르면 답변의 단일 제안을 검증해 해당 생성·변경·첨부 영역에 불러온다. 필요한 입력과 확인 절차를 거친 뒤 작업을 진행한다. 이 안내는 접수나 저장을 실행하지 않으며 잘린 답변과 여러 제안은 자동 선택하지 않는다. 접수 전송 뒤 응답이 없거나 확인할 수 없으면 기존 검토를 비활성화하고 같은 접수 ID와 원 서비스 이력으로 결과를 확인한다.

생성 접수와 맵·빌보드·건물·스프라이트·이펙트 편집 및 작가 제안 적용은 원 서비스 처리 중 접수 기록이 바뀌면 완료 기록으로 덮어쓰지 않는다. 결과가 불확실하면 원본과 같은 접수 ID의 이력을 확인한다. 공용 잠금을 사용하지 않는 외부 파일 수정까지 원자적으로 차단하는 기능은 아니다.

폐기 정책상 재개가 금지된 음악·캐릭터 애니메이션 작업은 Hermes에서 우선 실행을 검토하거나 접수할 수 없다. 기존 접수 기록 조회는 유지한다. 이 제한은 Hermes에 적용되며 원 서비스의 모든 직접 명령이 같은 방식으로 차단된다는 뜻은 아니다.


운영 이력의 **생성기 원본 이력**에서 작업 행을 선택하면 해당 도구를 열 수 있다. Kimodo, DWPose, Wan 영상, FLUX 이미지 프로필과 HeartMuLa·Dasheng 오디오는 선택한 작업 ID를 링크로 전달한다. 도구 화면에서 **전달된 작업을 이력에서 찾기**를 눌러야 원본 목록의 유일한 작업을 찾아 선택한다. 목록에서 찾지 못하거나 중복되거나 조회 중 목록이 바뀌면 선택하지 않는다. 찾기를 누르면 기존 도구의 상태 조회가 실행되며 일부 서비스는 중단된 기록을 복구할 수 있다. 지원하지 않는 원본은 도구에서 작업 ID를 직접 찾아야 한다. 접수 기록에서도 확인된 작업에 한해 같은 방식으로 연결한다.

Kimodo 키프레임 목록의 다음 페이지에는 첫 조회에서 반환한 `snapshot`을 전달한다. 기존 호환 호출에서 확인값 없이 이전 페이지를 요청할 수 있지만, 목록 변경 여부를 확인할 수 없다는 안내가 반환된다.

생성기 원본 이력에서 서로 다른 색인 파일이 같은 작업 ID를 가리키면 그 ID를 합치거나 작업 폴더에서 다시 끌어오지 않는다. 해당 ID는 목록에서 제외하고 확인 불가 색인 수에 포함한다. 다른 정상 기록은 계속 조회할 수 있다.

원본 이력의 상태 파일이나 색인 상태에 작업 ID가 들어 있으면 해당 이력 ID와 일치해야 한다. 불일치하면 상태를 확인 불가로 표시한다. ID가 없는 기존 상태 파일은 계속 지원한다.

Hermes 작업과 전용 GPU 서비스의 대기·예약 관측에서도 다른 서비스에 같은 작업 ID가 있으면 이를 별도로 알린다. 같은 ID만으로 다른 서비스를 같은 작업에 연결하지 않으며, 미확인 예약이 함께 있으면 추가로 표시한다.

대기열에서 대상 서비스의 기록이 확인되더라도 다른 서비스에 동일 ID가 함께 있으면 우선 실행 대상의 유일성을 확인할 수 없다고 표시한다. 실제 우선 실행 확인도 대기열 전체에서 ID의 유일성을 요구한다.

관리 서비스 등록 목록에는 Kimodo `migraphx-build-status`가 캐시 확인용 GPU 대기 작업을 추가할 수 있다는 제한과, `migraphx-build`가 요청 ID 기반 중복 방지를 제공하지 않는다는 제한을 표시한다. Hermes의 `hermes-kimodo-build-status`는 GPU 검사 없이 기록만 조회하며 빌드 실행에는 연결하지 않는다.

모델 준비 접수 응답에 `preparation_status`가 있으면 응답 당시 상태를 접수 기록에 보존해 화면과 MCP에서 확인할 수 있다. 이는 접수 시점의 원 서비스 응답이며 현재 준비 상태나 모델 사용 가능성을 보증하지 않는다. 이전 접수 기록에 이 값이 없으면 생략한다.

모델 준비 접수 응답이 유실되거나 형식·서비스·작업 ID를 확인할 수 없으면 화면의 검토 확인을 닫고 결과를 불확실로 표시한다. 같은 접수 ID의 기록과 원 서비스 모델 상태를 확인하며 자동 재접수하지 않는다.

운영 이력의 생성기 원본 이력에서 작업 ID 일부를 영문·숫자·하이픈·밑줄로 입력해 검색할 수 있다. 검색은 ID만 대상으로 하며 입력 지시나 결과 내용은 검색하지 않는다. 검색 조건과 목록 확인값을 다음·이전 페이지에 함께 적용하고, 원본 이력이나 조건이 바뀌면 다시 조회한다. MCP의 `list_hermes_generator_source_history`와 `list_hermes_audio_source_history`는 선택 인자 `query_text`를 제공한다. 새 검색 기능은 해당 서비스와 게이트웨이가 갱신된 뒤 사용할 수 있다.

관리 서비스 목록은 건물 앵커 편집과 건물 신규 등록·폐기, 빌보드 속성 편집과 이미지 크롭·폐기의 지원 범위를 구분한다. 현재 Hermes는 건물 등록·폐기와 빌보드 크롭·폐기를 위임하지 않는다. 에셋 원본·등록부·콘텐츠 DB·소비자 잠금 및 사용 맵은 원 도구와 각 저장소의 소유권 계약에 따라 확인한다.

건물 앵커는 대화에서 제안을 열어 변경 전후와 사용 맵을 확인하고 저장할 수 있다. 건물 목록의 현재 속성과 콘텐츠 세대가 제안과 다르면 다시 조회해야 한다. 저장은 콘텐츠 DB에 적용되며 에셋 원장 동기화와 게임 화면의 실제 외형은 별도로 확인한다. 운영 이력은 해당 대화 접수 ID에 건물 앵커 DB 저장 기록을 연결하며 GPU 작업·예약 대상이 아님을 표시한다. 신규 건물 등록이나 이미지 변경은 이 제안에 포함되지 않는다.

관리 서비스 검색은 명령 ID와 연결된 Hermes 기능뿐 아니라 확인된 차단 사유·조건부 제한의 한국어 설명도 검색한다. 검색 결과는 확인된 제한을 보여 주며 다른 미조사 명령의 실행 가능성이나 권한을 보증하지 않는다.

격리 운영 대화의 Hermes에도 원본 이력 `source-history`의 `query`로 작업 ID 일부를 찾고 같은 검색어·확인값으로 다음 페이지를 조회하도록 안내한다. 모델이 실제로 도구를 선택하는지와 응답의 정확성은 별도 검증이 필요하다.

살아 있는 GPU 대기 티켓이 남아 있으나 해당 작업의 상태 또는 명령 기록이 없거나 상태 값을 확인할 수 없으면 Hermes는 대기열이 비었다고 표시하지 않고 조회 불가로 처리한다. 티켓이 조회 중 사라지거나 실행기가 종료된 경우는 관측 시점에 따라 목록에서 제외될 수 있다.

새 GPU 대기 티켓은 가능한 경우 PID 시작 식별값과 부팅 식별값을 기록한다. 제공된 식별값은 관측·우선 실행·실행 대상 선택에서 확인하며 값이 다르거나 확인할 수 없으면 순서 변경 또는 실행 대상 선택을 거부한다. 두 값 중 하나가 없는 티켓은 기존 동작을 유지하며 실행기 신원을 미확인으로 표시한다. 확인은 조회 시점 기준이며 이후 생존을 보증하지 않는다. 운영 중 실행기를 재시작하지 않았으므로 변경은 해당 실행기가 갱신된 뒤 적용된다.

공용 대기열에 손상된 티켓이나 확인할 수 없는 작업 명령이 있으면 실행 대상을 추정하지 않고 대기한다. 손상된 티켓은 자동 삭제하지 않으며 대기 중 작업의 취소 요청은 계속 처리한다. 운영 이력에는 대기열 조회 불가로 표시될 수 있다.

GPU 우선순위 기록이 손상되었거나 현재 티켓을 찾을 수 없으면 실행기는 순서를 추정하지 않고 대기 상태와 확인 안내를 기록한다. 기록은 자동 변경하지 않으며 대기 취소·일시정지 요청을 계속 처리한다.

GPU 예약 기록의 PID·메모리·선택 필드가 손상됐거나 예약 작업의 명령을 확인할 수 없으면 해당 예약을 삭제하거나 사용 가능 메모리로 판단하지 않는다. 다른 작업은 대기하며 취소할 수 있다.

예약 실행기의 신원 확인이나 기존 예약 정리가 OS 오류로 실패하면 예약을 유지하고 다른 작업은 대기한다. 확인 실패를 실행기 종료로 간주하지 않는다.

이미지·영상·오디오 등 다른 서비스도 대기열 실행기가 사라진 것만으로 하위 GPU 작업 종료를 확인할 수 없다. 이 경우 예약을 자동 회수하지 않고 정리 확인 필요로 표시하여 다른 GPU 작업을 대기시킨다. 일반 생성기 예약도 자동 정리하지 않으며, 운영자가 원 서비스와 별도 GPU 프로세스를 확인한 뒤 운영 이력에서 명시적으로 정리를 요청할 수 있다. 신원을 확인할 수 없는 예약은 계속 유지한다.

운영 이력의 GPU 예약 행을 선택하면 원 서비스가 확인되고 같은 서비스·작업 ID의 예약이 화면에 유일할 때 해당 도구 이력으로 이동할 수 있다. 확인할 수 없는 원 서비스나 중복 예약은 연결하지 않는다. 표시된 ID는 기록 연결일 뿐 하위 GPU 프로세스 종료나 예약 해제를 뜻하지 않는다.

새 이미지·영상·오디오 등 GPU 작업도 가능한 경우 작업자 그룹 리더의 PID·시작값·작업별 토큰을 예약에 기록한다. 실행기 종료 뒤 운영 이력과 MCP는 신원이 일치하는 리더의 생존 여부만 표시하며 PID·토큰은 노출하지 않는다. 기록 실패나 기존 예약은 확인 불가로 남고, 리더 확인은 그룹 전체·별도 그룹 종료를 보증하지 않는다. 이 관측은 프로세스 종료나 예약 해제를 수행하지 않는다.

운영 이력의 GPU 예약 행을 선택하고 **선택한 생성기 예약 신원 확인**을 누르면 해당 서비스·작업 ID의 전체 예약 유일성, 실행기 관측과 작업자 그룹 리더 신원을 다시 확인한다. MCP `inspect_hermes_generator_reservation`도 같은 비파괴 조회를 제공한다. 예약이 중복·손상되거나 원 서비스가 불명확하면 확인하지 않는다. 이 조회는 예약 해제나 프로세스 종료를 하지 않으며 리더 확인은 그룹 전체·별도 그룹의 종료 증거가 아니다. 작가 예약은 기존 작가 예약 검토를 사용한다.

생성기 예약 신원 조회에서 실행기 일치 관측은 PID·시작값·부팅 식별값을 확인한 경우만 표시한다. PID가 존재하지 않으면 일치 실행기 미관측이며, 권한 오류·기록 누락·검증 오류는 확인 불가다. 미관측도 작업자 그룹 종료를 뜻하지 않는다. 새 예약에 가능한 경우 부팅 식별값을 보존하고 이전 예약은 신원 확인 불가로 남을 수 있다.

생성기 예약 신원 조회에서 실행기가 미관측이고 작업자 그룹 리더의 신원이 확인되며 다른 정리 절차가 진행 중이지 않을 때만 `review_ready`와 예약 기준 `review_sha256`을 제공한다. 이는 후속 재검토를 위한 확인값이며 정리 승인이나 실행 명령이 아니다. 작가 외 생성기 예약도 아래의 별도 정리 절차를 지원한다.

작가 예약의 수동 정리는 작업 ID가 전체 GPU 예약에서 유일하고 실행기 PID가 현재 존재하지 않는 경우에만 검토한다. PID 재사용·권한 오류·불완전한 예약 기록은 부재로 간주하지 않는다. 정리 직전과 해제 직전에 다시 확인하며, 확인할 수 없으면 예약을 유지한다.

생성기 예약 신원 확인은 공용 대기열의 등록 작업 루트 또는 오디오·번역·Wan Fun·FLUX 표정의 지정 작업 루트와 실제 경로가 일치할 때만 원 서비스를 인정한다. 다른 서비스나 이전 형식의 경로를 확인할 수 없으면 정리 검토 대상으로 사용하지 않는다.

이전 Qwen 2.1과 Qwen 2.1 원형 작업은 각각의 등록 작업 루트가 확인되면 운영 이력과 예약 신원 조회에서 원 서비스를 구분한다. 이는 기존 작업의 확인·정리 검토 범위만 넓히며 폐기된 생성·재개·우선 실행을 다시 허용하지 않는다. 리더 신원과 별도 GPU 프로세스는 기존 정리 절차에 따라 확인해야 한다.

이전 마네킨·소품·식생·표정·심리스 타일·바닥 타일 생성기도 각자 등록된 작업 루트가 일치할 때 같은 방식으로 원 서비스를 확인한다. 바닥 타일의 중간 경로를 포함해 심볼릭 링크가 있으면 확인하지 않는다. 빌보드 통합 경로는 빌보드 서비스로, 과거 건물 전용 경로는 건물 서비스로 확인한다. 통합 경로가 건물 호환 요청에서 시작됐는지는 구분하지 못한다. 확인할 수 없는 예약은 원 서비스와 GPU 프로세스를 직접 확인해야 한다.

일반 생성기 GPU 예약 정리 명령은 검토 해시와 별도 GPU 프로세스 확인을 요구하고, 작업자 그룹을 강제 종료한 뒤 동일 예약과 실행기 부재를 재확인해 해제한다. 접수 ID로 결과를 조회하며 결과 확인 불가는 자동 재실행하지 않는다. 운영 이력 화면과 MCP에서 검토 및 명시적 확인 후 실행할 수 있다. 이 정리는 별도 그룹에 속한 프로세스의 종료를 보장하지 않는다.

운영 이력에서 예약 정리 접수 ID로 결과를 다시 조회하면 검증된 원 서비스와 작업 ID를 함께 표시한다. 서비스·작업 ID 또는 접수 기록이 손상되었거나 응답을 확인할 수 없으면 완료로 표시하지 않으며, 원 서비스와 GPU 프로세스를 확인해야 한다.

운영 이력의 Hermes 작업 목록은 다른 GPU 서비스에 같은 작업 ID가 있으면 이를 구분해 표시한다. Hermes 대기 기록도 동시에 있을 때는 우선 실행 여부를 확인할 수 없다고 안내한다. 대기열 조회 실패는 대기 기록이 없다는 뜻이 아니다.

격리된 Hermes 대화에서도 `reservation-inspect`에 서비스·작업 ID를 전달해 생성기 예약 신원을 조회할 수 있다. 고정 소켓은 조회만 허용하며 정리 명령은 받지 않는다. 모델이 실제로 조회를 선택하고 해석하는지는 GPU 모델 시험이 필요하다.

서비스 기능 검색에서 맵·캐릭터 캡처의 Hermes 미연결과 헤드리스 브라우저 렌더링·파일 생성·GPU 사용 가능성·중복 접수 제한을 확인할 수 있다. 이는 원 서비스 캡처를 실행하지 않는 조회다.

Codex MCP의 `read_hermes_capture_status`는 요청 ID와 `map-review` 또는 `character-review`를 받아 검수 캡처 접수·작업 상태를 확인한다. 접수와 작업 입력·명령·경로가 일치하지 않으면 작업 상태를 확인 불가로 표시하며, 완료 결과는 지정 캡처 저장소의 PNG를 확인한다. 조회는 캡처를 실행하거나 복구하지 않지만 접수 잠금 경로를 만들 수 있다. 현재 캡처 대기열 접수와 GPU 자원 정책은 운영에 연결되지 않아 이 조회의 제공이 신규 캡처 실행 지원을 뜻하지 않는다.

격리된 Hermes의 `capture-status` 고정 조회에는 `{"service":"map-review","request_id":"request_123"}`처럼 서비스와 접수 ID만 전달한다. 다른 필드와 캡처 실행 요청은 허용하지 않는다. 조회는 기존 접수 기록과 검증된 상태만 반환하며 신규 캡처를 시작하지 않는다.

음악·효과음·번역·Wan Fun·FLUX 표정 대기 작업의 우선 실행 검토와 변경은 서비스명뿐 아니라 지정된 작업 루트가 일치해야 한다. 경로가 확인되지 않으면 우선 실행하지 않는다. 작가 등 다른 독립 서비스에는 이 경로 검증을 적용한 것으로 간주하지 않는다.

운영 이력은 음악·효과음·번역·Wan Fun·FLUX 표정의 대기 및 예약에서 서버가 작업 경로를 확인한 원 서비스만 표시한다. 확인값이 없거나 구버전 게이트웨이인 경우 미확인으로 표시하고 우선 실행·예약 원본 연결과 신원 확인 대상을 선택하지 않는다. 작가 등 별도 경로 검증이 없는 서비스에는 이 확인을 적용한 것으로 간주하지 않는다.

대화 접수와 생성기 원본 이력에서도 음악·효과음·번역·Wan Fun·FLUX 표정의 대기·예약 원 서비스를 경로 확인값과 함께 비교한다. 작업 ID와 서비스 이름만 일치하고 원 서비스 확인값이 없으면 확인 필요로 표시한다. 작가 등 경로 확인을 지원하지 않는 서비스는 기존 표시 기준을 유지한다.

운영 대화에서 선택한 세션은 현재 탭과 브라우저에 기록한다. 도구를 새 탭에서 열어 운영 대화로 돌아올 때 해당 탭에 세션이 없으면 이 브라우저의 최근 선택을 복원한다. 주소에 지정된 세션과 현재 탭의 세션이 우선이며 서버에서 세션 존재를 다시 확인한다.

브라우저 저장소가 차단된 경우에도 주소에 지정한 세션이나 현재 선택으로 대화를 사용할 수 있다. 저장이 허용되지 않은 범위의 탭 간 최근 세션 복원은 제공되지 않는다.

대화의 Kimodo·FLUX·영상·오디오 결과 링크는 실제 원 서비스 화면으로 연결하고 유효한 작업 ID가 있으면 이력 찾기에 전달한다. 도구에서 전달된 작업 찾기를 눌러야 선택되며, 일부 서비스의 상태 조회는 중단 기록을 복구할 수 있다.

첨부 영상·오디오의 결과 이력 링크는 접수 서비스와 작업 ID를 다시 검증하고 불일치하면 표시하지 않는다.

첨부 영상의 기존 접수 서비스나 작업 ID가 불일치하면 제안을 실행 가능한 상태로 열지 않고, 원 서비스와 접수 이력 확인 및 자동 재접수 금지를 안내한다.

대화의 텍스트 기반 이미지·영상·오디오 결과도 접수 서비스와 작업 ID가 제안과 일치할 때만 결과와 원 도구 링크를 표시한다.

대화의 번역·작가 결과도 기존 접수의 서비스와 작업 ID 형식을 확인한 뒤 표시한다. 불일치하면 접수 이력 확인을 안내하고 자동 재접수하지 않는다.

작가 결과 상세와 원본 적용 검토도 접수의 작가 서비스와 작업 ID 형식을 다시 확인한다. 불일치한 접수는 상세나 적용 대상으로 사용하지 않는다.

작가 적용 응답은 완료 상태와 함께 검토한 적용 접수·작가 접수·작업 ID·제안 해시가 모두 일치할 때만 완료로 표시한다. 응답이 다르거나 불완전하면 같은 접수 ID로 결과와 원본을 확인하며 자동 재적용하지 않는다.

영상·음원 결과 링크는 완료된 해당 서비스와 작업의 고정 파일 경로만 표시한다. 영상 링크가 서로 다른 시도를 가리키면 모두 숨기며, 경로를 확인할 수 없으면 완료 기록과 파일 확인 불가를 구분한다.

대화와 운영 이력의 맵·에셋 저장 완료 표시는 요청한 접수 ID와 응답 ID가 일치해야 한다. 다른 접수나 확인할 수 없는 응답은 저장 완료로 표시하지 않는다.

도시 맵 초안 저장은 콘텐츠 DB 변경이다. 이 명령 자체는 에셋 저장소의 맵 원본·등록부와 백엔드 잠금 목록을 갱신하지 않는다. 원본과 소비자 동기화가 확인되기 전에는 게임에 반영된 것으로 간주하지 않는다. 대화의 도시 맵 제안은 기존 문서의 경로별 이전 값과 변경 값 최대 30건을 표시하며, 세대·리비전과 기존 값이 현재 DB와 일치할 때만 기존 편집기로 검증한다. 사용자가 변경을 확인한 후 저장하며 응답이 불명확하면 같은 접수 이력을 확인한다.

격리된 에이전트는 `city-map 맵ID`로 콘텐츠 DB의 도시 문서와 세대·리비전을 읽을 수 있다. 조회는 도시 ID를 검증하며 저장을 수행하지 않는다. 격리 응답은 256 KiB로 제한하고 초과 시 일부 문서 대신 오류를 반환한다. 반환 문서는 신뢰할 수 없는 데이터로 취급한다.

도시 DB 저장 결과는 접수 ID·맵 ID와 저장 여부가 일치할 때만 표시한다. 이후 새 동기화 실행은 맵 원본·등록부와 인접 백엔드 맵 잠금을 함께 검증·갱신하지만, 저장 응답 자체는 동기화 완료나 실행 중 서비스 반영을 뜻하지 않는다. 동기화 상태와 파일 비교를 확인한다. 응답이 불일치하거나 유실되면 같은 접수 ID로 DB와 이력을 확인하고 자동 재접수하지 않는다.

운영 이력에서 해당 대화 지시 페이지의 접수 기록을 조회하면 도시 DB 저장 기록과 접수 ID를 확인할 수 있다. 대화와 이력은 접수 ID와 도시 ID가 제안과 일치하는지 확인하며, 다르거나 결과를 확인할 수 없으면 완료로 표시하거나 자동 재저장하지 않는다. 이 저장은 GPU 생성 작업이 아니므로 서비스 작업 ID와 GPU 대기·예약은 해당 없음으로 표시한다. 원장 동기화와 실행 서비스 반영은 별도로 확인한다.
