# 헤르메스 대화 기반 생성기와 워크플로우 설계

이 문서는 목표 설계와 현재 지원 범위를 함께 기록한다.

GUI·CLI·MCP, 공용 GPU 대기열과 실행 증거를 포함한 전체 구성 및 후속 과제는 [워크플로우 실행 아키텍처](workflow-execution-architecture.md)를 참고한다.

## 목적과 현재 범위

### 운영 대화와 생성기의 관계

운영 대화는 사용자의 의도를 정리하고 도구 탐색, 입력 제안·검토, 접수와 결과 확인을 돕는 작업 공간이다. 생성기는 각 산출물의 입력 검증, 실행과 원본 작업 이력을 담당하는 독립 서비스다. 실제 실행은 공용 명령 게이트웨이와 원 서비스, 필요한 경우 공용 GPU 대기열을 따른다. 대화에서 모든 생성기 기능을 사용할 수 있는 것은 아니다.

| 경로 | 의미와 경계 |
| --- | --- |
| 도구 탐색 | 생성기뿐 아니라 편집·검수·관리 도구도 검색한다. 요청에 이름과 ID를 추가하는 것은 초안 작성이며 접수가 아니다. [도구 목록](catalog/generator-catalog.md)은 기준 시점의 탐색 목록이다. |
| 대화의 개별 제안 | 지원되는 서비스의 입력을 검토하고 해당 서비스의 접수 절차를 따른다. 확인 방식과 첨부·GPU 인계 등 조건은 서비스마다 다르다. MiniMax는 사용자의 명시적인 대화 접수 지시도 지원한다. 현행 절차는 [운영 안내](../generators/hermes_agent/README.md)를 따른다. |
| 다단계 워크플로우 | 별도 카탈로그에 입출력 계약과 어댑터가 등록된 단계만 연결한다. 도구 탐색에 나타나거나 개별 제안이 가능하다는 사실만으로 단계 연결을 지원하지 않는다. |
| 독립 생성기 화면 | 원 서비스에서 직접 접수하고 이력과 결과를 확인한다. 별도 접수는 대화에 자동 연결되지 않으며 서비스와 작업 ID로 원본을 확인한다. |

대화 세션·대화 작업, 원 서비스의 생성 작업, 다단계 실행과 단계는 서로 다른 기록이다. 명시적으로 확인된 연결과 각 ID를 사용하며, 접수·생성 완료·보고서 작성·품질 승인·에셋 등록을 구분한다. 조회 실패나 접수 결과 불명은 확인이 필요한 상태이며 자동 재접수의 근거가 아니다.

사용자는 헤르메스 대화에서 생성기를 선택하고 입력을 함께 작성해 공통 대기열에 접수한다. 작업을 검색하고 우선순위와 결과를 확인하며, 한 작업의 결과를 다른 작업의 입력에 연결해 최종 결과까지 실행한다. 기존 생성기 검증, 원본 작업 이력, 공용 명령 게이트웨이와 GPU 대기열을 재사용한다. 생성 결과의 게임 에셋 채택과 등록은 별도 절차다.

현재 워크플로우 카탈로그에는 번역용 `prompt-translation`, 이미지 생성·수정용 `flux-image`, 효과음용 `sfx-dasheng-audiogen`이 등록돼 있다. 번역문을 이미지 프롬프트로 전달하거나 생성한 PNG를 다음 이미지 단계의 참조 입력으로 전달할 수 있다. 다른 생성기를 연결하려면 입출력 계약과 실행 어댑터를 등록하고 전달 경로를 검증해야 한다.

이 문서는 목표 설계의 기준이며 [헤르메스 운영 안내](../generators/hermes_agent/README.md)와 목표 동작이 충돌하면 이 설계를 우선해 구현과 운영 안내를 정리한다. 운영 안내는 현재 구현·검증 상태를 설명하며 목표가 이미 구현됐다는 뜻은 아니다. 기존 접수·확인·원 서비스 검증은 목표 구현에서 대응 계약을 갖추기 전까지 우회하지 않는다. 운영 안내는 실제 구현과 검증이 끝난 범위부터 갱신한다.

## 사용자 흐름

1. 사용자가 원하는 결과를 설명하면 헤르메스가 등록된 기능과 입출력 종류를 바탕으로 생성기를 추천하고 선택 이유와 대안을 설명한다.
2. 입력 템플릿으로 폼 초안을 만들고 대화에서 확인한 값과 기본값을 구분해 채운다. 필수 누락값은 질문한다. 폼과 대화 수정은 같은 초안에 반영하며 동시 수정 충돌 시 최신 값을 다시 확인한다.
3. 입력·첨부·기본값과 실행 영향을 보여주고 원 서비스의 검증을 거쳐 사용자가 요청한 작업을 접수한다. 초안은 실행하지 않으며 접수된 입력은 고정한다.
4. 생성기 카테고리·생성기·상태·기간·작업·워크플로우로 목록을 필터링한다. 조회 시각, 원 서비스 상태와 확인 불가를 구분한다.
5. 결과 템플릿으로 미리보기·결과 항목·설정·원본 이력 링크를 표시한다. 결과 항목은 다음 작업 입력이나 워크플로우 연결에 사용한다.
6. 우선순위 변경은 대상과 최신 상태를 검토한 뒤 적용한다. 목표는 사용자의 요구에 따른 대기 작업 및 워크플로우 단계의 우선순위 변경이다. 1차 구현은 기존 대기 작업 우선 실행을 사용하며 임의 순위 지정과 의존 대기 단계의 우선순위 반영은 후속 구현에서 규칙을 확정한다. 실행 중 작업은 선점하지 않는다.

## 공통 계약

### 생성기 카탈로그와 템플릿

생성기 ID와 버전, 카테고리, 설명, 실행 어댑터, 입력·출력 스키마와 템플릿 버전을 등록한다. 입력 필드는 이름, 자료형, 필수 여부, 제약, 기본값과 도움말을 가진다. 출력 항목은 안정적인 이름, 자료형, 단일값 또는 목록 여부와 접근 방법을 선언한다. 헤르메스는 카탈로그에서 생성기를 선택하고 불확실한 값은 사용자에게 묻는다. 접수 전 원 서비스 검증을 다시 수행한다. 결과 템플릿은 표시 방법이며 실행 입력을 위한 출력 계약을 대체하지 않는다.

### 작업과 대기열

공통 작업은 작업 ID, 요청 ID, 대화 세션, 생성기 ID·버전·카테고리, 고정된 입력과 템플릿 버전, 우선순위, 생성·갱신 시각, 상태, 원 서비스 작업 ID, 결과 참조와 선택적인 워크플로우 실행·단계 ID를 가진다. 요청 ID는 동일 입력의 재시도에만 사용한다. 접수 결과가 불명확하면 기존 접수와 원 서비스를 확인하고 새 ID로 자동 재접수하지 않는다.

공통 기록은 작업의 논리적 생애주기를 보존한다. 실제 실행 자원과 순서는 기존 스케줄러·GPU 대기열이 결정하며 카테고리별 저장·필터링이 카테고리별 독립 GPU 실행을 의미하지 않는다. 접수, 대기, 실행, 성공, 실패, 취소, 확인 불가를 구분하고 접수 성공을 생성 성공으로 표시하지 않는다. 원본 이력과 공통 기록이 어긋나거나 조회에 실패하면 불일치 또는 확인 불가를 표시한다. 대기열에 항목이 없다는 사실만으로 완료를 추정하지 않는다.

공통 작업 기록은 기존 GPU 티켓을 대체하지 않는다. 워크플로우 실행 조정자는 의존 관계와 접수 준비를 관리하고, 기존 생성기 서비스와 GPU 대기열은 실행·자원 제어의 소유권을 유지한다. 기존 생성기에서 직접 접수된 작업은 신원이 확인된 명시적 연결 전까지 대화나 워크플로우에 자동 편입하지 않는다.

### 결과 항목과 입력 바인딩

결과는 화면 표시뿐 아니라 **이름이 지정된 출력 항목**으로 제공한다. 항목은 생산 작업·시도 ID, 출력 이름, 자료형과 미디어 형식, 불변 결과 참조, 파일 결과의 크기·SHA-256, 생성 시각을 포함한다. 텍스트 등 작은 값은 형식과 크기 제한을 정해 값 또는 불변 참조로 전달한다. 파일은 원 서비스 또는 아래의 워크플로우 관리 저장소에서 검증해 읽고 임의의 로컬 경로나 브라우저 URL을 실행 입력으로 신뢰하지 않는다. 결과 보존 기간과 접근 권한은 실행 전에 확인하며, 만료·누락·해시 불일치는 후속 작업을 차단한다.

생산 어댑터는 원 서비스에서 완료된 특정 시도의 결과를 열거하고 항목의 신원과 해시를 검증한다. 원 서비스가 결과의 불변성과 보존을 보장하지 않으면 워크플로우 관리 저장소에 검증된 바이트를 고정하고 그 불변 참조를 발급한다. 고정 저장소의 소유자·접근 권한·보존 기간·용량·정리 정책은 구현 전에 정하며, 활성 실행이 참조하는 결과는 해제 전 삭제하지 않는다. 고정에 실패하거나 보존을 보장할 수 없으면 연결을 지원하지 않는다. 소비 어댑터는 고정된 바이트를 읽어 해시와 접근 권한을 재검증하고 대상 생성기가 요구하는 입력 형식으로 전달한다. 예를 들어 기존 FLUX의 PNG base64 입력처럼 서비스별 계약을 그대로 따른다. 검증한 바이트 자체를 전달하여 검증 후 원본 교체에 영향을 받지 않게 한다. 지원 조합은 실제 생산·소비 어댑터로 검증한 것만 공개한다.

입력 바인딩은 **대상 단계의 입력 필드 → 생산 단계의 출력 이름**을 명시한다. 출력이 여러 개인 경우 인덱스나 사용자 선택 등 선택 규칙을 지정한다. 정의 시 출력·입력의 자료형, 단수·목록, 미디어 형식과 필수 여부를 검사하고, 실행 직전 결과 존재·권한·해시 및 생성기 입력 제약을 다시 검사한다. 변환이 필요하면 명시적으로 등록된 변환 단계만 사용한다. 암묵적 파일 변환이나 임의 코드 실행은 하지 않는다.

다음은 대화 편집기에 넣어 검토할 수 있는 단계 정의다. 번역 완료 후 사용자가 번역문을 선택하면 이미지 생성기가 그 값을 프롬프트로 받는다.

```json
{
  "steps": [
    {
      "id": "translate",
      "generator": "prompt-translation",
      "inputs": {"text": "숲속의 작은 슬라임", "target_language": "en"}
    },
    {
      "id": "image",
      "generator": "flux-image",
      "bindings": {
        "prompt": {"from_step": "translate", "output": "text", "selection": "user_choice"}
      }
    }
  ]
}
```

선택 결과는 생산 시도와 결과 항목의 불변 참조로 고정하고, 다음 단계에는 검증된 실제 입력값을 전달한다.

## 워크플로우 정의와 실행

워크플로우 정의는 버전이 있는 단계 목록과 방향성 의존 관계를 가진다. 단계마다 생성기·버전, 고정 입력, 결과 입력 바인딩, 사용자 확인 지점과 실패 정책을 기록한다. 저장 전에 단계 ID 중복, 존재하지 않는 출력, 자료형 불일치, 필수 입력 누락과 순환을 거부한다. 필수 입력은 유효한 고정값 또는 유효한 결과 바인딩이 있으면 정의 시 충족된 것으로 보고, 바인딩의 실제 값은 후속 접수 전에 검증한다. 동일 필드의 고정값과 바인딩은 중복 지정 오류로 처리한다. 사용자는 대화에서 그래프와 각 단계의 입력·연결·선택 지점을 검토하고 수정한다.

실행은 정의의 버전과 입력을 고정한 별도 실행 기록으로 만든다. 의존 단계가 성공하고 필요한 결과가 확인·선택·검증된 단계만 실행 가능한 작업으로 공통 대기열에 접수한다. 독립 단계의 동시 실행 가능 여부는 기존 스케줄러가 결정한다. 단계는 의존 대기, 사용자 선택 대기, 접수 중, 대기, 실행, 성공, 실패, 취소, 차단, 확인 불가를 구분한다. 실패·취소·결과 누락 시 의존 단계는 차단하고 이유와 해결 방법을 표시한다. 결과 선택이 필요하면 선택 전까지 후속 작업을 접수하지 않는다.

조정자는 단계 시도의 입력 지문과 고정 요청 ID를 원 서비스 호출 전에 영구 저장하고 조건부 상태 갱신 또는 잠금으로 한 실행자만 접수를 진행하게 한다. 호출 전후 장애와 응답 유실을 구분할 수 없으면 확인 불가로 유지한다. 재시작 시 같은 요청 ID의 접수 기록과 원 서비스 상태를 대조하고 신원이 확인된 경우에만 연결한다. 조회 실패·손상은 미접수가 아니며 자동 재접수하지 않는다. 실제 미접수가 확인된 경우에만 동일 ID와 동일 입력으로 기존 서비스 계약에 따라 재시도한다. 기록 저장과 외부 서비스 호출을 하나의 원자적 트랜잭션으로 가정하지 않는다.

1차 실패 정책은 실패 시 후속 단계 차단이며 자동 재시도나 실패 무시는 제공하지 않는다. 사용자가 명시한 재시도는 새 시도로 기록한다. 사용자의 워크플로우 실행 요청은 검토된 정의와 그 범위의 자동 후속 접수를 승인한 것으로 취급하되, 생성기별 기존 확인 조건과 결과 선택 지점은 유지한다. 입력·연결·영향이 바뀌면 다시 검토한다.

재시도는 새 시도로 기록하고 이전 결과를 덮어쓰지 않는다. 이미 결과에 연결된 후속 단계의 입력을 바꾸지 않으며, 새 결과를 사용하려면 영향받는 후속 단계를 새 실행 또는 새 시도로 명시적으로 다시 만든다. 접수 결과가 불명확한 단계는 기존 요청 ID와 원 서비스 확인 전 자동 재접수하지 않는다. 워크플로우 취소는 아직 접수하지 않은 단계를 중단하고, 접수·실행된 작업은 각 서비스의 취소 계약에 따라 요청한 뒤 실제 종료를 별도 확인한다.

## 생성 결과 보고서 작성

신규 FLUX 생성이 완료되면 Hermes가 검수 결과로 보고서를 작성하도록 연결했다. 자동 접수, 자료 고정, GPU 접수, 보고서 저장·실패 처리 및 완료 기준은 [워크플로우 실행 아키텍처의 보고서 설계](workflow-execution-architecture.md#hermes의-생성-결과-보고서)를 따른다. 보고서 작성은 결과 품질 승인이나 에셋 등록을 뜻하지 않는다.

### 생성폼 입력 이력과 결과 분석의 공통 목표

모든 생성기의 생성폼은 Hermes와 사용자가 각각 작성·수정할 수 있어야 한다. 같은 생성기 입력 계약을 사용하며 작성 주체와 수정 출처를 구분한다. 대화의 제안, 사용자가 직접 작성한 폼, 독립 생성기 화면의 입력 모두 생성 작업과 연결되는 입력 이력의 대상이다. 현재 구현된 세션 폼 저장소나 개별 서비스 기능만으로 이 공통 목표가 모든 생성기에 적용됐다고 보지 않는다.

#### 대화와 우측 패널의 입력 흐름

대화에서 모든 필드를 차례로 묻지 않는다. Hermes는 사용자의 요청과 생성기 입력 계약을 바탕으로 작업에 필요한 핵심 정보와 필수 누락값만 폼 도구로 받는다. 확인된 값은 폼에 기록하고, 유효한 기본값은 그 출처를 표시해 사용한다. 의도를 결정하는 값이나 필수 참조를 추측하지 않으며 필요한 경우에만 추가로 묻는다. 사용자는 대화로 입력을 지시하거나 우측 패널의 전체 폼을 직접 편집할 수 있다.

대화에는 생성기, 핵심 입력과 미충족 항목의 간결한 요약 및 **전체 생성폼 열기** 링크를 제공한다. 링크는 우측 패널에서 해당 폼의 모든 필드, 첨부, 기본값과 현재 버전을 조회·검색하고 수정할 수 있게 한다. 대화와 패널은 같은 폼 ID와 버전을 참조하며, 한쪽에서 저장한 변경은 다른 쪽에 반영한다. 오래된 버전의 수정은 충돌을 알리고 최신 입력을 다시 확인한다. 링크를 열거나 값을 편집하는 것만으로 생성 작업을 접수하지 않는다.

접수 전에는 실제 사용할 전체 입력과 필수 참조를 우측 패널에서 확인할 수 있게 하고 서비스별 기존 확인·접수 절차를 따른다. MiniMax처럼 명시적인 대화 접수 지시를 지원하는 경우에도 접수할 폼과 버전을 확인한다. 접수 후 대화의 링크와 작업 이력은 고정된 해당 시도의 입력을 조회할 수 있어야 한다. 현재 편집 중인 폼과 접수된 버전을 구분해 표시하고, 보고서는 접수 당시의 고정 입력과 실제 적용값을 사용한다. 이 흐름은 목표이며 모든 생성기의 폼 도구·패널 연결이 구현됐다는 뜻은 아니다.

생성폼 입력은 파일로 영속 관리하고 변경할 때마다 이전 내용을 덮어쓰지 않는 버전 이력을 남긴다. 각 버전은 생성기·스키마 버전, 폼 ID·버전, 작성·수정 주체와 시각, 필드 값과 기본값의 출처, 첨부 자료의 안전한 참조·크기·해시를 포함한다. 첨부 원본은 보호하고 분석에 필요한 사본 또는 보존이 보장된 참조를 연결한다. 비밀정보와 무관한 자료는 저장·보고 범위에서 제외한다. 동시 수정은 기준 버전을 검사하고 충돌 시 다시 확인한다.

접수 시 검토된 폼 버전과 실제 전달 입력을 고정하여 서비스·작업 ID와 해당 실행 시도에 연결한다. 이후 폼 편집이나 작업 재시도는 과거 시도의 입력을 바꾸지 않는다. 기본값 적용·변환 등으로 요청과 실제 실행값이 달라지면 양쪽과 차이를 기록한다. 입력 파일이나 첨부의 누락·변조 또는 연결 불명은 확인 필요로 표시하고 현재 폼이나 대화 내용으로 과거 입력을 추정하지 않는다. 파일 위치·보존 기간과 삭제 정책은 기존 서비스 이력 및 보호 규칙에 맞춰 구현 시 정하고, 보고서가 참조하는 자료의 수명과 삭제 영향을 명시한다.

생성 완료 후에는 해당 시도의 고정 입력과 실제 결과를 함께 수집해 이미지·영상·음향 등 결과 유형에 맞는 멀티모달 분석을 수행하고 Hermes가 비교 보고서를 작성하는 것이 공통 목표다. 보고서에는 입력 조건, 실제 적용값, 관찰한 결과와 항목별 비교 근거, 불일치·확인 불가 및 분석 범위를 기록한다. 지원되지 않는 매체나 관찰하지 않은 구간은 확인 불가로 남기며 파일 검사와 내용 관찰, 모델의 해석을 구분한다. 분석 또는 보고 실패는 생성 성공 상태를 바꾸지 않는다. 각 생성기의 자동 연결과 실제 분석 지원은 구현·검증된 범위만 운영 안내에 표시한다.

## 동작 시나리오 사용성 검토

설계 문서를 기준으로 “첨부할 캐릭터를 비 오는 숲에 그려 줘”라는 요청을 따라간 검토다. 아래 판단은 실제 화면 관찰이나 사용자 시험 결과가 아니다.

| 사용자가 하려는 일 | 혼동하거나 막힐 지점 | 화면에서 확인할 기준 |
| --- | --- | --- |
| 요청을 보내고 캐릭터 참조를 추가한다 | 장면을 이미 설명했는데 프롬프트·크기·시드까지 다시 물으면 같은 작업을 반복한다. | Hermes가 장면을 초안에 반영하고 필요한 참조만 폼 도구로 받는다. 첨부 후 누락 안내가 사라지고 전체 폼을 열지 않아도 다음 행동을 알 수 있다. |
| 우측 패널에서 배경만 바꾼다 | 링크가 폼 목록을 열면 대상을 다시 찾아야 한다. 패널을 닫으면 편집 내용의 저장 여부도 모호해진다. | 링크 한 번으로 해당 폼을 열고 필드 검색으로 배경 설명을 찾는다. 저장 상태를 표시하고 대화로 돌아오면 요약에 수정한 배경이 반영된다. |
| 수정한 내용으로 한 번 생성한다 | 대화에 예전 요약이 남아 있으면 어떤 버전이 접수될지 판단하기 어렵다. | 접수 직전에 대상 버전과 변경된 핵심값을 보여 준다. 다른 쪽에서 수정했다면 갱신값을 확인한다. 접수 후 작업 ID와 접수본 링크를 표시한다. |
| 완료 결과가 요청과 맞는지 확인한다 | 생성 완료와 분석 완료가 한 상태처럼 보이거나, 보고서 링크가 최신 초안을 열면 비교 근거를 잃는다. | 생성 완료 후 분석 중에도 결과를 열 수 있다. 보고서에서 해당 시도의 읽기 전용 접수본과 결과를 열고, 캐릭터·배경별 관찰 근거와 확인 불가 항목을 확인한다. |

첫 화면 검증에서는 **패널에서 배경을 수정한 뒤 대화에서 접수하는 구간**을 우선한다. 이때 같은 정보를 다시 입력한 횟수, 링크에서 대상 폼까지의 조작 수, 대화 요약·접수본·보고서가 가리키는 버전을 기록한다. 접수 뒤 초안을 다시 수정한 경우에도 보고서에서 처음 접수한 배경을 확인할 수 있어야 한다.

### 사용성 개선 계획

첫 적용 대상은 기존 접수폼·우측 패널·결과 보고서가 있는 MiniMax 이미지 생성기로 정한다. 먼저 한 생성기에서 작성부터 보고서 조회까지 연결한 뒤, 같은 기준으로 다른 생성기에 적용한다. 아래 표는 앞으로 구현하고 검증할 순서다.

| 순서 | 개선 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 입력과 이력 연결 | 사용자와 Hermes가 같은 폼을 수정하도록 기존 저장 경로를 점검한다. 저장할 때 버전별 입력 파일을 남기고 접수 시 해당 버전을 원 서비스 작업·시도에 연결한다. | 두 작성 경로에서 번갈아 수정해도 각 버전을 다시 열 수 있다. 오래된 버전에서 저장을 시도하면 최신 변경을 확인할 수 있다. |
| 2. 대화 입력 축소 | 요청에서 확인된 값과 생성기 기본값을 채우고 사용자 결정이 필요한 항목만 폼 도구로 받는다. 대화 요약에 해당 폼을 여는 링크를 붙인다. | 빠진 필수값이 한 개면 그 값만 요청한다. 이미 제공한 값의 재입력은 0회이며 링크 한 번으로 우측 패널에 해당 전체 폼이 열린다. |
| 3. 패널 수정과 접수 일치 | 패널에 필드 검색과 저장 상태를 표시한다. 저장하면 대화 요약을 갱신하고 접수 시 검토한 버전을 대조한다. | 패널에서 배경만 바꾸고 대화로 돌아오면 요약과 접수본에 바뀐 배경이 표시된다. 검토 후 다른 편집이 발생하면 바뀐 값을 다시 확인하고 한 건만 접수한다. |
| 4. 결과와 비교 보고서 연결 | 생성 상태와 분석 상태를 각각 표시한다. 보고서에서 해당 시도의 읽기 전용 접수본과 결과를 열고, 요청 조건별 관찰 근거와 확인 불가 사유를 보여 준다. | 접수 후 초안을 다시 바꿔도 보고서는 접수 당시 배경과 실제 이미지를 비교한다. 분석 대기·실패 중에도 생성 결과를 열 수 있다. |
| 5. 생성기별 확대 | 첫 적용 결과를 기록한 뒤 FLUX 이미지, 참조 입력이 필요한 영상 등으로 확대한다. 각 생성기의 필수 첨부·접수 방식·분석 가능한 매체를 확인한다. | 생성기별로 대화 입력, 전체 폼 열기, 버전 보존, 결과 비교를 검사하고 실제 화면·생성·분석을 확인한 범위를 운영 안내에 기록한다. |

첫 적용의 우선 검증은 3단계다. 격리된 작업에서 패널 저장 직후 접수와 두 화면의 동시 수정을 검사한다. 실제 화면에서는 재입력 횟수와 링크 조작 수를 기록하고, 접수본과 보고서의 폼 버전·작업·시도가 일치하는지 대조한다.

MiniMax 적용 검증에는 같은 폼을 사용자가 먼저 작성한 경우와 Hermes가 먼저 작성한 경우를 모두 포함한다. 두 경로에서 누락값만 요청하는지, 패널 수정 후 접수된 버전이 보고서까지 이어지는지, 관찰 실패 시 해당 항목을 확인 불가로 설명하는지 검사한다.

## 화면과 운영 경계

대화에는 편집 가능한 입력폼, 필수값과 검증 오류, 제출 요약, 필터 가능한 작업 목록, 상태·대기 순서·관측 시각, 결과 카드, 워크플로우 단계와 연결을 제공한다. 진행 예상치는 근거가 없으면 계산 중으로 표시한다. 우선순위 변경은 최신 티켓 확인값을 사용하고 상태가 바뀌면 다시 검토한다. 조회·접수·원본 작업·결과 참조를 서비스와 ID로 명확하게 연결하며 서로 다른 서비스의 동일 ID를 합치지 않는다.


## 도입 및 검증

1. 카탈로그·입력 초안과 기존 위임 생성기 한두 개의 어댑터를 만든다. 폼과 대화 동기화, 필수값·기존 검증, 중복 접수를 검증한다.
2. 공통 작업 기록과 결과 템플릿을 연결한다. 카테고리·상태 필터, 서비스별 ID 충돌, 원본 조회 실패와 확인 불가 표시를 검증한다.
3. 기존 우선 실행을 대화에 연결한다. 오래된 티켓, 이미 실행된 작업, 동시 변경과 접수 불명 처리를 검증한다.
4. 실제 입출력 계약을 가진 두 생성기를 선정해 어댑터와 결과 고정·순차 연결을 구현한다. 결과 선택, 타입 불일치, 누락·변조·만료, 실패·취소, 재시도, 접수 전후 장애·동시 조정·프로세스 재시작과 중복 접수 방지를 격리된 모의 서비스에서 검증한다. 선택한 생성기와 형식 호환성, 실제 서비스 검증 여부를 따로 기록한다.
5. 독립 단계와 추가 생성기로 확장한다. 실제 관리 화면에서 브라우저 재연결·폼 수정·결과 연결을 검증하고 GPU 실사용 여부와 범위를 따로 기록한다.

검증은 사용자 작업이나 운영 대기열을 시험 접수·취소하지 않는 격리 환경에서 수행한다. 구현 단계마다 지원 생성기와 미지원 항목을 명시한다.

### 대화 폼에서 최종 결과까지의 통합 검증

2026-11-21에 React 운영 대화 번들, Python 워크플로우 명령 처리기, 임시 폼 저장소와 SQLite 실행 저장소를 연결해 Chrome에서 다음 흐름을 검증했다.

1. 세션 입력 폼에서 번역과 이미지 생성 두 단계를 작성하고 이름을 붙여 v1을 저장했다. 별도 폼으로 복사한 뒤 저장 목록에 두 항목이 표시되는지 확인했다.
2. 등록 검토 표에서 번역 단계의 `text` 출력과 FLUX 이미지 단계의 `prompt` 입력 연결을 확인하고 대기열에 등록했다.
3. 격리된 번역 완료 응답을 기록한 뒤 실행 저장소에서 이미지 단계의 요청을 가져와 `prompt`가 번역 결과인 `forest`와 일치하는지 검사했다.
4. 시험 PNG를 이미지 단계의 결과로 고정하고 대화 화면에서 마지막 등록 실행을 열었다. 결과 조회로 받은 PNG가 브라우저에서 디코딩되는 것을 확인했다.

이 검증은 실제 폼 저장·복사, 워크플로우 등록, 단계 간 입력 전달과 결과 조회 경로를 사용했다. 세션 응답과 생성기 완료 결과는 시험 데이터로 제공했으며, 후속 검증에서는 실제 워크플로우 스케줄러를 별도 스레드로 실행했다. 스케줄러가 새 실행을 발견하고 번역 완료 후 같은 번역문으로 이미지 생성 명령을 한 번 전달했으며, 열어 둔 결과 화면이 자동 갱신되어 최종 PNG를 표시했다. 생성기 응답은 격리된 모의 서비스에서 제공했다. GPU 추론은 이 검증 범위에 포함하지 않았다.

### 효과음 어댑터와 검증 범위

효과음 생성기 `sfx-dasheng-audiogen`은 번역 단계의 `text` 출력을 `prompt`로 받는다. 원 서비스 검증기는 공백만 있는 프롬프트와 4,000자를 넘는 입력을 거부한다. 요청 길이 지정은 지원하지 않으므로 `duration_seconds`는 생략한다. 기존 오디오 위임의 접수·상태 조회·취소에는 모두 서비스 ID가 필요하다.

스케줄러는 서비스·작업·생성 시도가 일치하는 결과를 읽고 16 kHz 모노 PCM16 형식과 파일 해시를 검증한 뒤 실행 DB에 보존한다. 보존 한도는 파일당 4 MiB다. 격리된 스케줄러에서 번역문 전달, 효과음 접수·취소와 카테고리 조회를 검증했다. 격리된 실행 DB에 1초 길이의 시험용 WAV를 보존하고 원본 파일을 삭제한 뒤, Chrome의 대화 화면에서 재생 위치가 파일 끝까지 진행되는 것을 확인했다. 별도 검증에서 AMD Radeon 8060S의 Dasheng 워커가 9.92초 WAV(317,484바이트)를 생성했다. 파일의 SHA-256이 생성기 기록과 일치했고, 같은 WAV를 격리 실행 DB에 보존한 뒤 Chrome 대화 화면에서 재생 시간이 증가하는 것을 확인했다. GPU 생성과 화면 재생은 나누어 검증했으며 청취에 따른 음질 평가는 수행하지 않았다.

## 대화 세션 중심의 입력 관리

Codex·Claude Code처럼 사용자가 대화 기록을 읽은 위치에서 요청을 이어 쓰고, 필요한 생성기를 검색해 현재 요청에 지정한다. 생성기 선택은 초안 편집이며 실행은 요청과 입력을 검토한 뒤 접수한다. 도구 검색·폼·결과 선택은 같은 세션과 입력을 공유한다. 사용성 검토는 세션 전환 후 작성 내용 복원, 검색 후 입력란으로 포커스 복귀, 제안에서 입력 수정과 결과 조회까지의 화면 이동을 기준으로 한다.

세션의 **입력 폼 목록**은 실행 전 입력을 재사용하는 원장이다. 게이트웨이의 비공개 실행 디렉터리 `.local/hermes-workflows/forms/<session_id>/index.json`에 스키마 버전, 세션 ID, 폼 ID별 버전 목록을 기록한다. 버전에는 이름·저장 시각·SHA-256과 복사 원본을 기록하고, 단계·생성기·입력값·결과 연결은 같은 디렉터리의 `<sha256>.json`에 고정한다. 폼 수정은 버전을 추가하고 이전 버전에서 분기하려면 별도 폼으로 복사한다. 폼을 불러오면 현재 편집 초안을 교체하며, 실행 등록은 기존 검토 절차를 거친다.

### 운영 UI 선정 결정

헤르메스 대화, 생성기, 검수 화면은 **assistant-ui와 React 공통 컴포넌트**로 이전한다. UI 운영을 위해 별도 서버 키를 발급·보관·교체하는 구성은 배제한다. 기존 Python 웹 서버가 정적 번들을 제공하고, 생성기 실행과 대기열 스케줄링은 기존 Python 런타임이 담당한다.


### 관리 서버 신규 설치 검증
