# 헤르메스 GPU 양도와 재적재 설계

## 목적과 현재 상태

헤르메스 Qwen 3.8을 GPU에 유지하는 동안 고용량 작업이 필요하면, 사용자는 대상 작업과 헤르메스 모델의 해제·작업 종료 후 재적재 순서를 검토하고 동의할 수 있어야 한다. 취소하면 생성·해제·재적재를 하지 않는다. 대기열 밖의 프로세스는 이 흐름으로 종료하지 않는다.

Qwen 3.8은 세션별 GPU 상주 서버로 실행할 수 있으며, 지원된 생성 작업의 승인된 양도 후 다시 적재한다. 실행 중인 대화를 강제 취소하면 부분 응답과 작업 내용이 사라질 수 있으므로, 기본 동작은 현재 대화가 끝날 때까지 기다리는 것이다. 준비 상태 조회나 파일 다운로드를 GPU 재적재 성공과 혼동하지 않는다.

## 사용자 확인

헤르메스가 지원되는 생성 작업을 제안하면 기존 생성 폼에서 서비스·입력·예상 GPU 사용, 확인된 헤르메스 작업 상태, 해제와 재적재의 순서를 함께 표시한다. 확인된 정보가 없으면 확인 불가를 표시하고 자동 양도를 실행하지 않는다. 확인값은 대상 서비스·입력 지문·세션·재적재 모델을 포함하고 변경 시 무효화한다. 최종 확인 전에는 작업을 접수하거나 현재 작업을 중단하지 않는다. 대화 중 실행이 자연 종료되기를 기다리는 경우에도 기다림을 명시한다.

## 영속 상태와 실행

게이트웨이와 브라우저의 수명과 독립된 양도 기록을 생성하고 공용 GPU 대기열이 상태를 조정한다. 기록은 고유 요청 ID, 확인된 대상 입력 지문, 헤르메스 세션·모델, 대상 서비스·접수 ID·작업 ID, 각 단계와 확인된 종료 결과를 가진다. 입력이 같은 요청만 중복 접수로 처리한다. 사용자가 승인한 대상 외의 작업이나 프로세스를 다루지 않는다.

1. `approved`: 승인과 입력 지문을 영속 저장한다. 기존 대화가 실행 중이면 완료를 기다린다.
2. `waiting_release`: 확인된 헤르메스 작업의 종료와 서버 종료, 해당 예약 해제를 확인한다. PID만으로 재사용된 프로세스를 식별하지 않으며 확인 불가면 중단한다.
3. `submitting` / `running`: 기존 원 서비스 접수 및 상태 조회를 사용한다. 응답 유실 시 영수증을 조회하며 중복 생성하지 않는다. 작업의 성공·실패·취소 여부와 관계없이 확인된 종료와 예약 해제 전에는 재적재하지 않는다.
4. `reload_queued` / `reloading`: Qwen 3.8 재적재를 공용 GPU 대기열에 별도 등록한다. 다른 GPU 작업·예약과 메모리 여유를 다시 확인한다. 상주 프로세스의 GPU 예약과 소유권을 유지하며 중복 재적재를 막는다.
5. `ready`: 모델 서버의 건강 상태와 실제 GPU 적재를 확인한 경우에만 준비 완료로 표시한다. `failed`·`unknown`은 원인과 확인 방법을 표시하고, 접수 여부나 프로세스 신원이 불확실한 단계는 자동으로 재실행하지 않는다.

게이트웨이나 브라우저 재시작 뒤에는 영속 기록·원 서비스의 상태·GPU 예약을 대조해 안전하게 이어간다. 취소는 승인된 대상의 기존 취소 경로를 사용하며 취소 요청과 실제 종료를 구분한다. 파일 손상, 프로세스 신원 불일치, 외부 GPU 작업, 원 서비스 상태 미확인 또는 재적재 실패는 확인 필요 상태로 보존한다. 상주 모델은 별도 해제 명령과 소유권 검증이 필요하며 기존 대화 작업 서버를 임의로 재사용하지 않는다.

재적재 상태가 일시적으로 `unknown`이면 같은 접수 ID를 유지하며 최대 30초 동안 재확인한다. 이후에도 불명확하면 확인 필요로 전환하며, 모델 불일치나 예약 검증 실패는 즉시 확인 필요로 처리한다. 확인 필요 화면에서 기존 재적재의 모델·GPU 예약을 다시 확인하거나, 실패한 시도의 정리를 확인한 뒤 재적재를 한 번 재시도할 수 있다.

실패한 상주 작업의 `status.json`만으로는 재시도 안전성을 증명하지 못한다. GPU 실행기는 실패 상태를 기록한 뒤에야 프로세스 그룹과 예약을 정리할 수 있으며, 실패한 작업에는 상주 서버의 정상 종료 기록이 없을 수도 있다. 새 시도에는 이전 실행기의 종료·작업자 그룹 부재·예약 및 대기열 부재를 일관되게 확인하는 영속 증거가 필요하다.

상주 접수는 명시적으로 지정된 실패 작업에 한해 실행 수명 잠금, 실패 종료 코드, 대기열·예약 부재와 GPU 유휴를 확인한 뒤 새 접수 ID를 허용한다. 같은 새 ID는 중복 적재하지 않는다. 양도 상태에 재시도 번호를 저장한 뒤 고정된 새 ID로 접수하며, 실패 기록과 후속 접수의 연결을 확인해 세션의 모델을 찾는다. 실제 GPU 장치 접근 실패로 종료된 시험 재적재를 별도 스케줄러에서 재시도해 Qwen 준비와 시험 모델 정리를 확인했다.

별도 시험 세션 `2473912689974b3d9a76a326adcf0f5b`에서는 제한된 환경에서 실패한 실제 상주 작업과 시험용 양도 기록을 만든 뒤, 8770의 대화 이력에서 재시도 버튼을 눌렀다. 공용 스케줄러가 Qwen 3.8을 재적재하고 취소 완료 상태로 전환했으며 시험 모델도 정상 해제했다. 실패 상황의 양도 상태는 시험을 위해 직접 구성한 것이므로 사용자 작업 전체를 처음부터 재현한 시험은 아니다.

실행 잠금을 새 접수까지 유지하도록 수정한 뒤 별도 세션 `84d1a2ef744049af9ed2b56eee555070`에서 같은 실제 브라우저 재시도 시험을 반복했다. 공용 스케줄러가 재적재를 완료하고 Qwen 준비 상태와 시험 모델의 해제를 확인했다. 실패 상태는 시험을 위해 구성했다.

### 구현 중인 내부 구성요소

`resident_worker.py`는 공용 GPU 예약으로 실행되는 3.8 서버와 소켓을 유지한다. 해제 요청을 받으면 새 대화의 사용권을 차단하고 기존 사용권과 연결이 끝난 다음 모델을 종료한다. 사용권을 가진 대화는 해제 대기 중에도 필요한 추론 연결을 계속 열 수 있다. `resident_queue.py`는 접수 ID별 중복 실행을 막고, GPU 대기열 잠금 안에서 실행기·작업자 신원을 확인한 상주 서버에만 해제를 요청한다. 준비 완료는 GPU 전체 레이어 적재 기록, 서버 헬스와 소유 프로세스, 공용 예약을 함께 확인한다. 양도 기록에는 승인된 입력 원본과 지문, 대상 상주 작업 ID를 함께 저장한다. 대상 작업의 종료 기록이 먼저 나오고 예약이 아직 남아 있으면 정리가 끝날 때까지 기다린다.

Kimodo 어댑터는 기존 위임 접수 영수증의 입력 해시와 작업 ID를 확인하고, 대상 종료와 예약 부재 및 캐시하지 않은 GPU 유휴 관측을 확인한다. 관리 서비스가 실행되는 동안 스케줄러가 승인 기록을 복구해 단계별로 진행한다. 대상 접수 전에 중단되어 위임 영수증이 없는 경우에는 동일한 멱등 접수 ID로 계속한다. 위임 저장소는 생성 부작용 전에 영수증을 기록하므로, 이미 접수가 시작돼 결과가 불확실한 영수증은 자동 재접수하지 않는다.

접수 불명확으로 확인 필요 상태가 된 뒤 원래 영수증이 `accepted`로 확인되면 사용자는 기존 작업 추적을 복구할 수 있다. 세션·리비전·서비스·입력 지문과 작업 ID를 다시 확인하며 새 생성은 접수하지 않는다. 영수증이 없거나 불명확하면 그대로 확인 필요 상태에 남는다.

확인 절차는 세션·상주 작업 ID·모델·Kimodo 입력 전체의 검토 해시를 계산하며, 명시적 확인 후에도 검토값이 변하지 않았는지 다시 확인한다. 대화 접수기는 같은 세션의 확인된 상주 3.8 모델이 있으면 사용권을 얻는 격리 실행기를 선택한다. 독립 검증이 필요한 코딩 요청도 격리 환경에서 검증하며, 검증을 위해 다른 대화가 공유할 수 있는 상주 서버를 임의로 종료하지 않는다. 실행기 종료 시 하위 작업을 정리하고, 실행기 신원이 사라진 진행 기록은 확인 필요로 표시한다.

대화 입력에서 Qwen 3.8을 직접 선택하면 해당 세션의 상주 서버를 최초 한 번 접수한다. Kimodo·FLUX·Wan Fun·DWPose·VACE·HeartMuLa·Dasheng 생성 폼은 세션의 상주 서버를 검토하고 입력·해제·생성·재적재에 대한 명시적 확인을 받은 경우에만 양도 요청을 저장한다. 접수 ID와 상태는 브라우저를 다시 열어 조회할 수 있다. 참조 이미지를 포함한 양도 입력의 직렬화 크기는 최대 40 MiB다. Animate2의 위임 어댑터는 연결했지만 해당 폼은 메모리 부족 때문에 신규 생성을 보류하고 있다.

한 대화 또는 상주 모델에는 미완료 양도를 하나만 승인한다. 다른 서비스나 다른 입력의 동시 승인도 저장소 잠금 안에서 거부하며, 확인 필요 상태는 중복 생성이나 재적재가 불명확하므로 미완료로 취급한다.

대화의 GPU 양도 이력은 세션별 서버 기록에서 최근 20건을 입력 원본 없이 조회한다. 탭 저장소가 없어도 상태와 복구 가능한 요청을 찾을 수 있으며, 다른 세션 기록은 반환하지 않는다.

승인 응답이 유실되거나 거절된 뒤 해당 ID의 기록이 없으면 사용자는 미접수 요청을 철회할 수 있다. 철회와 승인은 같은 잠금에서 직렬화하며 철회된 ID는 나중에 도착한 승인도 거부한다. 이미 승인된 기록이 있다면 취소하지 않고 그 상태를 반환한다. 실제 두 세션에서 다른 상주 모델과 충돌해 승인이 거절된 뒤 브라우저로 철회·상태 닫기와 재조회 지속을 확인했다.

FLUX 대화 제안은 고정 접수 ID로 중복 접수를 막는다. 그 ID를 철회한 경우에는 기존 제안을 다시 접수하지 않고 상태 표시를 닫은 뒤 독립 생성기에서 새 작업을 요청하도록 안내한다. 일반 내장 생성기에는 현재 대화 세션을 명시적으로 전달한다.

다른 세션의 상주 모델이 이미 대기 또는 실행 중이면 양도를 승인하지 않는다. 상주 모델 접수와 양도 승인 모두 양도 저장소 잠금으로 직렬화하며, 승인이 기록된 동안에는 모든 세션의 신규 상주 접수를 보류한다. 승인 직전에는 같은 잠금 안에서 기존 상주 접수 상태를 다시 확인한다. 이 정책은 여러 모델을 일괄 해제하는 기능이 아니라 경쟁과 무기한 GPU 점유를 방지하는 보수적 제한이다. `needs_attention`도 미완료이므로 해당 양도를 먼저 확인해야 한다.

다른 세션의 기존 상주 모델을 정리하는 해제 요청은 해당 세션의 미완료 양도가 없는 한 허용한다. 전역 신규 접수 보류가 다른 모델의 정리까지 막아 교착되지 않도록 한다.
