# 워크플로우 실행 아키텍처와 구현 계획

이 문서는 생성 접수부터 GPU 실행과 결과 조회까지의 공통 경계와 후속 구현 기준을 정리한다. 2026-11-23 기준으로 기존 문서에서 확인한 범위와 목표를 구분한다. 등록된 서비스나 이 문서의 요구사항만으로 모든 생성기에 적용·검증됐다고 판단하지 않는다. 서비스별 현행 계약은 [클라이언트 가이드](management-clients.md), 생성기별 실행 환경은 각 생성기 README를 따른다.

## 구성과 책임

```text
GUI ───────┐
CLI ───────┼─> 공용 명령 게이트웨이 ─> 작업 서비스 ─> 공용 GPU 대기열 ─> 작업별 실행기
Codex ─ MCP┘                              │                    │              │
Hermes 대화 ─> 입력 초안·사용자 검토 ──────┘                    └─ 예약·잠금   └─ AMD GPU / ROCm
                                          └─ 요청·상태·로그·결과·이력
```

그림은 책임의 논리적 연결이며 모든 MCP 도구가 임의의 생성 명령을 제공한다는 뜻은 아니다. GUI·CLI는 같은 HTTP 명령 계약과 원 서비스 이력을 사용한다. MCP의 Hermes 도구는 같은 게이트웨이의 Hermes 작업과 기록을 사용한다. Hermes는 지원된 생성기의 입력을 제안하며 초안 작성만으로 접수하지 않는다. 확인 방식은 서비스별로 다르며, MiniMax는 사용자의 명시적인 대화 접수 지시도 지원한다. 서비스별 지원 여부와 확인 절차는 [Hermes 생성기 설계](hermes-generator-workflow-design.md)와 [MCP 안내](management-clients.md#hermes-격리-코딩-작업과-mcp)를 따른다.

게이트웨이는 명령 등록·전달을 담당하고, 작업 서비스는 입력 검증·상태와 이력의 소유자다. GPU 대기열은 예약과 실행 순서를 관리하며 작업별 실행기는 해당 생성기의 환경과 입출력 계약을 사용한다. GUI·게이트웨이와 GPU 작업은 독립 수명을 가진다. 기존 URL, 서비스 ID, 접수 ID와 저장 경로는 호환성을 유지한다. 결과를 조회할 수 있다는 사실과 결과 품질의 승인은 별개다.

## 실행과 관측 계약

- 접수 시 서비스와 요청을 검증하고 원 서비스의 접수 ID를 반환한다. GUI와 CLI는 동일한 요청·상태·로그·결과·이력을 조회한다. 응답 유실이나 상태 불명은 확인 불가로 보존하고 새 ID로 자동 중복 접수하지 않는다.
- GPU 실행은 기존 예약과 메모리 조건, 독점 제한을 고려한다. 예약 판단과 우선 실행은 공용 잠금 아래 최신 상태를 재검증한다. 대기 작업 우선 실행은 실행 중 작업을 선점하지 않고 메모리 조건을 유지한다. GPU 관측이 불명확하면 실행 가능이나 종료로 추정하지 않는다.
- 작업별 요청·상태·단계 로그·결과와 종료 원인을 보존한다. 장시간 실행은 진행 상황을 heartbeat로 기록하며, 관측 불가와 실패를 구분한다. 접수·대기·실행·성공·실패·취소와 취소 요청은 원 서비스 상태를 기준으로 구별한다.
- `scripts/workflow.sh`는 준비·진단·서비스 시작·회귀 실행의 공통 진입점이다. `management`, `hermes`, `gpu` 검사 그룹은 등록된 검사 범위이며 실제 GPU·브라우저 또는 전체 저장소 검증을 보장하지 않는다. 검사 실행 ID, 결과, 종료 코드와 로그를 보존한다.

상세한 자원 판정과 운영 방법은 [클라이언트 가이드](management-clients.md), 실행 명령과 진단 한계는 [README](../README.md)를 따른다. 공통 구현의 출발점은 `workflow/common/management_gateway.py`, `workflow/common/gpu_job_queue.py`와 각 `workflow/domains/` 서비스다.

## Hermes 상주 모델과 GPU 인계

지원 생성 폼의 승인된 인계는 대상 입력과 상주 모델을 고정하고, 진행 중인 대화가 끝난 뒤 모델과 예약의 해제를 확인한다. 원 서비스로 생성 작업을 접수하고 실제 종료와 예약 해제를 확인한 후 재적재를 공용 대기열에 접수한다. 다른 예약과 GPU 여유를 다시 확인하며, 관측 불명이나 실패는 확인 필요로 남긴다. 승인 취소는 생성·해제·재적재를 시작하지 않는다. 구현 범위와 시험별 한계는 [GPU 인계 설계](hermes-gpu-handoff-design.md)를 따른다.

세션 Qwen의 대기 작업에 따른 자동 반환은 별도 경로다. 일반 대화 재적재는 대기 요청에 의해 접수되며, 승인 기반 인계와 동일한 동작으로 묶지 않는다. 상주 모델 60초 유휴 유지 정책은 목표이며 현재 세션 Qwen 구현만으로 완료된 것이 아니다. 조건과 실제 검증은 [모델 상주 정책](hermes-model-residency.md)을 따른다.

## Hermes의 생성 결과 보고서

FLUX의 우선 적용과 자동 검수·경로별 전달 기준은 [FLUX Hermes 보고서 설계](flux-hermes-report-design.md)를 따른다.

현재 워크플로우는 실행 단계와 결과 조회, 이미지·음성 미리보기를 제공한다. 신규 FLUX 이미지 작업의 완료 후 검수·보고서 접수와 전달을 구현했다. 다른 생성기와 전체 실행 단위 보고서는 아래 확장 설계를 따른다. 결과 카드나 파일 존재를 보고서 작성으로 간주하지 않는다. 생성기 확대, 모델 유휴 유지 등 기존 문서의 별도 목표는 이 기능의 선행 조건이나 이번 미구현 범위로 취급하지 않는다.

### 사용자 흐름과 범위

1. 지원 생성 작업의 완료와 결과 기록을 확인하면 해당 시도에 대한 자동 검수와 보고서 작성을 접수한다. 워크플로우 단계별 완료와 전체 실행 완료를 구분하고 각각 중복 없이 기록한다. 실패·취소는 생성 성공으로 검수하지 않으며 종료 상태와 원인을 별도로 보고할 수 있다. 지원하지 않는 생성기는 미지원으로 표시한다.
2. 서비스는 세션 소유권과 원 작업·시도 신원을 확인하고 현재 상태, 요청 요약, 단계별 결과와 오류, 검증 가능한 산출물 참조를 읽어 시점이 고정된 자료 묶음을 만든다. 조회 불가·누락은 명시한다. 실행 중인 대상은 최종 보고서로 표시하지 않고 완료 후 다시 요청하도록 안내한다.
3. 버전이 고정된 생성기별 규칙으로 결과를 검사하고, Hermes는 검사 결과와 자료 묶음을 근거로 보고서를 작성한다. 사용자가 같은 대화에서 보고서와 원 작업·결과를 열람한다. 보고서 작성 실패는 생성 작업의 성공·실패 상태를 바꾸지 않는다.
4. 사용자는 명시적으로 새 보고서를 요청할 수 있다. 각 보고서는 대상 시도와 자료 시점에 연결해 별도 보존하며 이전 보고서를 덮어쓰지 않는다. 원 작업의 재시도나 결과 변경은 기존 보고서를 갱신하지 않는다.

### 자료와 보고서 계약

- 공통 목표는 Hermes 또는 사용자가 작성한 생성폼 입력의 불변 파일 이력을 생성 작업·시도에 연결하고, 완료 결과를 그 시도의 입력과 멀티모달로 비교하는 것이다. 입력 파일 버전과 첨부, 실제 적용값 및 누락 처리의 상세 기준은 [생성폼 입력 이력과 결과 분석](hermes-generator-workflow-design.md#생성폼-입력-이력과-결과-분석의-공통-목표)을 따른다. 기존 구현의 지원 범위는 생성기별로 확인한다.
- 입력은 세션 ID, 대상 종류와 ID, 대상 시도 ID, 보고서 요청 ID다. 워크플로우 실행은 단계별 원 서비스·작업·시도 ID와 결과를 함께 고정한다. 직접 접수된 생성 작업은 세션과의 명시적 연결 및 소유권 확인이 가능한 경우에만 허용한다. 확인할 수 없으면 거절한다.
- 자료 묶음에는 관측 시각, 작업 상태, 확인된 입력 요약, 단계·종료 원인, 산출물 이름·종류·안전한 조회 참조 및 가능한 경우 크기·해시를 담는다. 값마다 출처를 식별하고 누락·불명확·조회 실패를 기록한다. 로그는 크기를 제한하고 필요한 부분만 전달하며 경로·비밀정보와 무관한 사용자 데이터는 제외한다.
- 보고서는 제목, 대상 및 시도, 실행 결과, 확인된 산출물, 오류·경고, 확인하지 못한 사항과 원본 조회 참조를 포함한다. 사실과 모델의 해석을 구분하고 근거가 없는 수치나 성공을 만들지 않는다. 이미지·영상·음성을 실제로 검토할 수 없는 경우 내용·품질을 추정하거나 승인하지 않는다. 텍스트와 로그 등 외부 결과는 지시가 아닌 데이터로 취급한다.
- 보고서 기록은 보고서 ID, 요청 ID, 세션·대상·시도, 자료 지문과 관측 시각, 생성 상태, 모델 식별자, 본문 또는 실패 사유, 작성 시각을 보존한다. 동일 서비스·작업·시도·규칙 버전의 자동 접수는 같은 기록을 반환하고 다른 입력의 요청 ID 재사용은 거절한다. 조회 시 세션 소유권을 다시 검사한다.

### 구현 경로와 실패 처리

1. 완료 상태와 결과 기록을 확인하는 기존 조정 경로에 영속적인 검수 접수를 연결한다. 서비스·작업·시도·검수 규칙 버전으로 중복을 방지하고, 재시작 후 미처리 완료 작업을 복구한다. 워크플로우 외 직접 생성도 원 서비스별 완료 관측 어댑터가 연결된 범위에서 처리하며, 모든 서비스에 자동 적용됐다고 가정하지 않는다. `workflow/domains/hermes_agent/`에 결과 자료 수집과 보고서 저장·상태 관리 모듈을 추가한다. 기존 `workflow_run_store.py`의 실행·결과와 원 서비스의 공용 게이트웨이 조회를 재사용한다. 자료 수집은 읽기 전용이며 임의 파일 경로나 브라우저 URL을 신뢰하지 않는다.
2. 생성기별 버전 관리된 규칙과 검사기를 등록한다. 파일 무결성·형식·크기와 생성기별 측정 가능한 조건을 검사하고 각 항목에 통과·실패·확인 불가, 관측값, 기준과 근거를 기록한다. 시각·청취 품질은 실제로 지원되는 검수 방법이 없으면 확인 불가로 둔다. Hermes는 검사 결과를 설명하며 판정을 임의로 바꾸지 않는다.
3. Hermes 서비스와 `workflow/common/management_gateway.py`의 기존 등록 체계에 보고서 요청·상태·조회 명령을 연결하고 `capabilities.py`, GUI 대화 결과 화면, CLI 도움말과 사용 안내를 갱신한다. 명령 이름과 페이로드는 구현 시 기존 계약과 충돌하지 않도록 정한다. MCP 노출은 별도 지원 계약과 권한 검증 후 추가하며 기존 MCP 도구가 지원한다고 가정하지 않는다.
4. 보고서 작성은 기존 Hermes 작업 접수와 공용 GPU 예약을 이용한다. 생성 작업이 끝나기 전에 모델을 임의 해제하거나 GPU를 선점하지 않는다. 보고서 요청·Hermes 작업 ID를 연결해 대기·실행·완료·실패·취소·확인 불가를 추적한다. 접수 응답 유실 시 기존 요청과 작업을 대조하고 불명확하면 자동 재접수하지 않는다.
5. 모델 출력과 자료 지문을 연결해 저장한다. 보고서 작성 실패, 원 결과 삭제·변조, 권한 불일치 또는 조회 실패는 사유와 함께 표시하고 기존 생성 결과를 보존한다. 재시도는 명시적 새 요청으로 기록한다. 생성 결과를 승인하거나 에셋에 등록하지 않는다.

### 완료 및 검증 기준

- 격리된 생성 결과로 단일 작업과 다단계 실행의 보고서를 요청하고, 대상 시도·관측 시각·근거·산출물 참조와 Hermes 본문이 같은 대화에서 조회된다. 실패·취소·부분 완료와 누락 결과는 사실대로 표현된다.
- 완료 이벤트 중복·유실, 재시작 복구, 규칙 버전 변경, 검사 실패·확인 불가, 다른 세션 접근, 결과 해시 불일치·삭제, 원 서비스 조회 실패, 실행 중 대상, 모델 오류, 응답 유실·재시작을 검사한다. 생성 작업의 상태·결과가 보고서 실패로 바뀌지 않고 중복 Hermes 작업이 만들어지지 않아야 한다.
- 생성기 결과의 지시문이 보고서 작성 권한이나 도구 실행을 바꾸지 않는지 검사한다. 미디어 미검토 시 품질 판단을 하지 않는지 확인한다. 실제 GUI에서 요청·대기·보고서 조회와 오류 표시를 확인하며 사용자 운영 작업은 시험에 사용하지 않는다.
- 자동화 검사, 실제 화면 확인, 실제 GPU에서의 Hermes 작성 및 보고서 내용 검토 결과를 각각 기록한다. 문서·모의 응답 또는 결과 카드만으로 완료 처리하지 않는다.
