# Pixal3D 형상 생성 실험 상태

2026-11-22. 입력: `.local/trellis-experiment/masked-views-a-pose-v1/01_front.png`. 8방향 이미지의 카메라 정합이 확인되지 않아 첫 시험은 정면 단일 이미지로 계획했다. 텍스처 베이킹 없이 형상 생성·별도 정점 색상 투영을 목표로 한다.

- 공식 Pixal3D 저장소 `TencentARC/Pixal3D` 모델 리비전 `b0cb2e1b794cab9aa0ac38a95d794a4d9337437f`의 형상 관련 가중치를 `.local/pixal3d-experiment/model-official`에 내려받는 중이며 공식 Hub LFS 해시를 `official-weights-manifest.json`에 기록했다. 다운로드 완료·해시 검증 전에는 사용하지 않는다.
- 공식 DINOv3 `facebook/dinov3-vitl16-pretrain-lvd1689m`은 기존 Hugging Face 로그인에서 HTTP 403을 반환했다. 사용자에게 해당 페이지의 계정 정보 공유 및 라이선스 동의를 직접 검토하고 접근 요청해 달라고 안내했다. 승인 여부와 다운로드는 미완료다. 미러로 권한·조건을 우회하지 않는다.
- ROCm 호환 후보로 격리한 `raven38/pixal3d.cpp` 리비전 `d1b4926452f9e09702b891db5f05acc845e153ed`, ggml `737e88f25d4f62254f3b7a726fd9663036cc94da`. 다른 저장소나 기존 Python 환경을 바꾸지 않았다. 기본 ROCm 10.2 컴파일러는 HIP CMake 파일 누락으로 구성 실패했으며, 시스템을 수정하지 않고 ROCm 10.1 경로를 지정해 HIP/gfx1151 구성을 완료했다. `.local/pixal3d-experiment/build-rocm101`에서 빌드 중이며 컴파일 완료 및 GPU 실행은 미검증이다.
- 로컬 C++ 소스에서 flow의 비유한값을 0으로 치환하는 코드 대신 실패시키고, DINOv3·NAF·sparse decoder 주요 경계에 검사 추가 중이다. NAF GPU 경로가 없을 경우 CPU 추론으로 전환하지 않도록 실패 처리를 추가했다. 아직 컴파일과 시험 전이고 모든 단계에 대한 수치 검사 완성을 뜻하지 않는다.
- NAF 공식 체크포인트는 `.local/pixal3d-experiment/naf/naf_release.pth`에 준비했다. 코드와 체크포인트의 라이선스 적용 범위 및 DINOv3에서 유래한 구성요소 조건은 미확정이다. [NAF 체크포인트 라이선스 문의](https://github.com/valeoai/NAF/issues/13). 비상업 제한이 있는 BRIA RMBG 및 NVIDIA nvdiffrast/nvdiffrec을 사용한 생성·출력은 하지 않는다. Pixal3D 결과물의 전체 상업 이용은 승인되지 않았다.
- 원본 BF16 가중치를 제3자 변환기의 F16 GGUF로 변환할 경우 수치 표현이 달라진다. 출처·해시·변환 차이와 모델 경계별 수치를 확인해야 하며, Q8 양자화 버전을 자동으로 대체하지 않는다.
- GPU 추론은 아직 대기열에 접수하지 않았고 모델도 생성하지 않았다. 이후 라이선스와 접근 권한, 빌드, GPU 전용 실행 및 공용 대기열을 확인해야 한다.

## DINOv3 접근 확인 및 생성 접수

후속 사용자 요청으로 공식 DINOv3 접근을 재확인해 성공했다. `facebook/dinov3-vitl16-pretrain-lvd1689m` 리비전 `ea8dc2863c51be0a264bab82070e3e8836b02d51`의 `model.safetensors`는 공식 LFS SHA-256 `dcb2e45127cccbf1601e5f42fef165eea275c8e5213197e8dcf3f48822718179`와 일치했다. Pixal3D 공식 형상 가중치 5개도 `official-weights-manifest.json`의 크기와 SHA-256을 대조해 모두 일치했다.

ROCm 10.1 HIP용 C++ 실행기의 컴파일과 `--help` 호출은 성공했다. 이는 GPU 추론 검증이 아니다. 공식 Hugging Face DINOv3의 분리된 Q/K/V를 C++ 런타임이 요구하는 합친 QKV 형식으로 변환했으며, Pixal3D 형상 및 DINOv3를 F16/F32 GGUF로 변환했다. 이는 BF16 원본과 수치 표현이 다르므로 수치 동등성·해상도별 GPU 안정성은 미검증이다. NAF는 공식 체크포인트를 안전 가중치 전용 로더로 읽어 변환했다. 변환 결과는 실험용이며 상업 이용 승인이 아니다.

Pixal3D 단일 참조, 시드 42, 해상도 1024, 형상 전용 작업 `.tmp/pixal-experiment/generate-cf685faf62e94f909addf28baa1cf716`을 공용 대기열의 `pixal-experiment`로 접수했다. 실측 전 단독 실행 및 65536 MiB 하한을 사용한다. 접수 직후 다른 GPU 예약으로 가용 예약량이 부족해 대기 중이었다. 실행기는 시작 전 입력과 모델 해시 및 GPU 예약을 확인하고 `--require-gpu --no-texture`로 실행하며 결과 메시의 유한 정점·면 인덱스를 검사한다. GPU 추론·리깅 및 추가 변형·상업 이용 조건은 미검증이다.

DINOv3 변환 추가 검사: 24개 블록의 공식 Q·K·V 가중치와 합친 변환 결과를 각각 정확히 대조하고, Q/V 편향과 K의 0 편향을 확인했다. 이는 변환된 F16 전체 모델의 추론값이 원본과 일치한다는 검증은 아니다. `ldd`에서 로컬 HIP 빌드의 공유 라이브러리 경로가 모두 해석됨을 확인했으며 GPU 연산 검증은 아니다. 접수된 대기열 프로세스 PID 645855가 살아 있고, 확인 당시 Hermes 상주 예약이 있어 단독 실행을 기다렸다. 다른 사용자 작업은 중단하지 않았다.

## ROCm 어텐션·메모리 경로 후속 조사

실제 `generate-87edd...` 생성은 공식 PyTorch 파이프라인이 아니라 GGML 기반 `pixal3d.cpp` HIP 빌드와 F16/F32 변환 가중치를 사용했다. 빌드 캐시에 `GGML_HIP=ON`, `GGML_HIP_NO_VMM=ON`이 있고 당시 로그도 `gfx1151 ... VMM: no`를 기록했다. 이는 GGML 자체 VMM 경로가 비활성인 근거이나 모든 드라이버 수준 가상 메모리나 TLB 문제가 없다는 증거는 아니다. 앞서 다른 PyTorch VAE에서 확인한 expandable segments 재매핑 사례를 이 C++ 생성에 그대로 적용할 수 없다.

해당 포트의 `src/dit.cpp::sdpa`는 기본적으로 `ggml_flash_attn_ext`와 BF16 K/V, F32 누적 요청을 사용하며 `--no-fa`에서 쿼리별 분할 softmax 경로를 제공한다. 포트 소스와 `docs/GGML_FORK_DIFF.md`는 gfx1151의 과거 FP16 누적 편향 및 수정 사례를 설명한다. 수정된 소스가 빌드 이전인 것은 확인했으나 실제 생성 당시 선택된 커널과 누적 정밀도, 이 입력의 수치 동등성은 기록되지 않았다. LR·HR 잠재값의 NaN/Inf는 로그상 0이지만 유한값만으로 정확성을 보장하지 않는다. 공식 PyTorch SDPA를 전환하는 환경변수는 이 GGML 경로를 직접 제어하지 않는다.

여기서 FlashAttention은 이 포트의 GGML 융합 어텐션 연산명이며 NVIDIA 전용 CUDA 패키지나 PyTorch의 Flash SDPA 백엔드가 실행됐다는 뜻이 아니다. HIP 빌드의 `GGML_HIP_ROCWMMA_FATTN=OFF`는 rocWMMA 특화 경로 설정이고 다른 GGML attention 커널까지 모두 비활성이라는 뜻은 아니다. 코드에 TILE/VEC 등 여러 후보가 있으나 해당 실행에서 어떤 경로가 선택됐는지는 `GGML_FA_DEBUG`가 기록되지 않아 확정할 수 없다. 별도로 AMD ROCm에도 FlashAttention 구현이 있으나 지원 여부는 GPU·버전·빌드에 따라 달라진다.

권장 후속 검사는 예약된 단독 GPU 조건에서 같은 Q/K/V와 마스크의 실제 텐서를 확보해 선택 커널·누적 정밀도를 기록하고, 기본 경로와 `--no-fa`를 비교하는 것이다. 서로 다른 난수·입력이나 저해상도 대조만으로 원인을 확정하지 않는다. 유한값 외에도 최대·평균·상대 오차, 반복 실행, 주요 단계의 잠재값 및 렌더를 비교하고 공식 PyTorch/BF16 경로와의 차이도 분리한다. 이 비교는 아직 실행하지 않았고 어떤 임계치도 모델 정확성의 확정 기준으로 설정하지 않았다.

## Hermes 공존 예약 수정

사용자 요청에 따라 공용 대기열을 수정해 Pixal과 Hermes가 함께 있어도 메모리 및 기존 예약 조건이 맞으면 실행한다. Pixal끼리 또는 Pixal과 다른 일반 GPU 생성은 단독 실행을 유지하며 미확인 예약은 차단한다. 65536 MiB 초기 하한은 실측이 없으므로 낮추지 않았다. 선택 로직의 충분·부족 메모리 및 다른 작업 차단 검사는 `workflow.tests.test_pixal_gpu_queue`로 통과했다. 수정 전 접수 기록의 '단독'은 Hermes도 차단하던 당시 상태를 말한다. 수정 후에도 2026-11-22 확인값은 사용 가능 예약량 약 63155 MiB로 하한보다 작아 대기 중이다.

## 생성과 Hermes 양도 결과

사용자 지시에 따라 기존 대기 작업에 대한 명시적 양도를 시작했다. Hermes가 정상 종료된 뒤 작업이 실행되어 `mesh.glb`와 `mesh.ply`를 생성했고, GPU 예약 해제 후 Hermes가 다시 준비 상태가 됐다. 결과는 정점 1,427,127개, 면 2,958,746개의 형상 전용 메시다. 텍스처와 리깅은 없으며 형상 품질, 리깅 적합성, 상업적 이용 조건은 이 결과에 대해 검증하지 않았다.

Pixal 양도 어댑터는 기존 작업과 입력 지문을 확인하고 종료 후 재적재를 추적한다. 현재 양도 시작은 명시적으로 실행해야 하며 메모리 부족을 감지해 모든 대기 작업에 자동 적용하지는 않는다.

## 흰 배경 4방향 실험

후속 요청에 따라 정면·오른쪽·후면·왼쪽 참조를 공통 배율로 1024 정사각 프레임에 배치하고 전경 마스크를 유지했다. 전경을 인식하는 마스크는 유지하되 C++ 실행기의 이미지 조건 입력에서 투명 부분이 검정이 아니라 흰색이 되도록 별도 빌드했다(`RGB * alpha + (1 - alpha)`). 모델의 원래 입력 분포와 다른 실험이며, 순백 RGB 파일을 입력한 것은 아니다. 카메라 배치는 정면·오른쪽·후면·왼쪽, FOV 20도와 mesh_scale 1.0을 가정했으며 실제 참조 카메라와 일치하는지 검증하지 않았다.

공식 `TencentARC/Pixal3D` 리비전 `b0cb2e1b794cab9aa0ac38a95d794a4d9337437f`의 MV 형상 흐름 3개를 받아 공식 LFS SHA-256을 확인한 뒤 F16/F32 GGUF로 변환했다. 작업 `.tmp/pixal-experiment/generate-24daedefa8e4413c8265ffdfb8c336c2`은 완료됐고, 정점 1,173,178개·면 2,381,986개의 형상 메시를 만들었다. Hermes는 작업 후 준비 상태로 복귀했다.

8방향 검수 렌더에서는 앞뒤 양쪽에 얼굴처럼 보이는 형상, 배경의 가는 선, 면처럼 보이는 표면이 확인된다. 검수 렌더러 특성도 영향을 줄 수 있어 실제 메시 검사가 필요하다. 단일 이미지 실험과 배경·참조 수·가중치·카메라 가정을 함께 바꿨으므로 특정 변경의 효과는 분리할 수 없다. 리깅 적합성과 상업 이용 조건은 미검증이다.

## 앞뒤 얼굴 조사와 측면 배치 수정

픽셀별 깊이 버퍼 렌더에서도 두 얼굴이 보여 기존 면 평균 깊이 렌더의 표시 오류만은 아니었다. 4방향 이미지와 시드·카메라를 유지하고 공식 검정 알파 합성으로만 변경한 `.tmp/pixal-experiment/generate-66f8c16f1bb841f795495a2cab42d057`에서도 두 얼굴이 남아 흰 배경만으로는 설명되지 않았다.

기존 `03_right` 이미지의 얼굴은 화면 오른쪽을 향하지만 실행기의 +X 측면 카메라에서는 정면(-Y)이 화면 왼쪽에 투영된다. 이 이미지 방향과 카메라 위치 기준 차이를 반영해 측면을 교환하고 다른 조건을 유지한 `.tmp/pixal-experiment/generate-87edd53f9dbe484a99dea41e78cdb944`에서는 깊이 버퍼 렌더상 후면에 뒷머리와 등이 보이며 두 번째 얼굴은 관찰되지 않았다. 이 비교는 측면 순서 오류가 해당 실패의 주요 원인임을 뒷받침하지만, 다른 시드·참조에서 일반화된다는 뜻은 아니다. 새 메시의 양옆에 분리된 파편이 보여 정리와 리깅 검증이 여전히 필요하다. Hermes 재적재는 준비 상태로 확인했다.

## 4방향 결과 파편 제거와 리깅 전 검사

원본을 유지하고 `workflow/domains/pixal_experiment/clean_disconnected.py`로 연결 성분을 분석했다. 4개 성분 중 본체는 2,417,036면이고, 양옆의 59,580면·58,618면 성분은 본체 최근접 정점까지 각각 전체 대각선의 약 14.4% 떨어져 있었다. 각 성분이 전체 면의 3% 이하이고 거리가 대각선의 10% 이상일 때만 제거해 두 성분을 제거했다. 머리 근처 6면 성분은 가까워 보존했다. 결과 `.tmp/pixal-experiment/rig-check-87edd/cleaned/cleaned.glb`는 2,417,042면이며 GLB 재읽기에서 좌표와 면 인덱스가 유지됐다.

깊이 버퍼 렌더에서는 몸 양옆의 두 성분이 사라졌다. 그러나 trimesh 검사에서 닫힌 메시와 일관된 면 방향 모두 아니었고, 열린 경계 변 54,645개, 비다양체 변 87,905개, 양쪽 면 방향이 충돌하는 2면 공유 변 600,169개를 관측했다. MeshLab 자기 교차 선택은 9,031개 면을 후보로 선택했다. 면 수는 교차 쌍 수가 아니며 도구의 수치적 한계가 있다. 실제 뼈·스키닝·모션 변형은 시험하지 않았고 손과 몸의 연결도 판정하지 않아 리깅 준비 상태로 승인할 수 없다. 정리된 후보는 원본의 대체 승인이 아니다.

## 참조 색상과 면 방향 진단

8방향 참조를 정점 색으로 투영했을 때 앞면에 큰 얼룩이 나타났다. 이미 확인된 면 방향 충돌과 관련성을 확인하기 위해, 정면 추정 측의 바깥 방향과 반대 법선도 색상 샘플에 사용할 수 있도록 `--two-sided` 대조를 수행했다. 이 방식에서 직접 샘플한 정점은 768,974개에서 1,156,031개로 늘었고, 깊이 버퍼 렌더상 얼룩이 크게 줄었다. 법선 방향에 의존하던 투영 방식이 얼룩에 기여했다는 근거이지만, 모든 얼룩의 원인이나 올바른 면 방향을 증명하지는 않는다.

색상 후보 `.tmp/pixal-experiment/rig-check-87edd/colored-two-sided/colored.glb`의 정점 좌표와 면 인덱스는 정리된 입력과 정확히 일치한다. 양면 색 투영은 메시를 수리하지 않는다. 원래 관측된 열린 경계, 비다양체, 면 방향 충돌, 자기 교차 후보와 리깅 미검증 상태는 그대로다. 색상도 카메라 정합이 근사이고 정점 색이지 UV 텍스처가 아니다.

## 공식 모델 카드·후처리 조사 (2026-11-22)

- [공식 README의 다방향 입력](https://github.com/TencentARC/Pixal3D#multi-view-inference)은 같은 물체의 뷰별 카메라 행렬·수평 FOV와 공통 mesh_scale이 담긴 transforms.json을 요구하며, 첫 뷰를 정면으로 둔다. 카메라 파라미터가 없을 때 제공 예시의 90도 간격 배치를 재사용할 수 있으나 각 참조의 실제 크기·프레이밍이 카메라와 일치해야 한다. 현재 참조는 생성된 그림이고 카메라를 추정한 것이므로 실제 일치 여부는 미검증이다.
- [공식 다방향 추론 코드](https://github.com/TencentARC/Pixal3D/blob/master/inference_mv.py)는 알파를 곱해 모델 입력의 투명 배경을 검정으로 만들고, 출력에서는 `remesh=True`, `remesh_band=1`, `decimation_target=1000000`을 사용한다. 100만 면은 공식 출력 목표이지 리깅 적합성을 보장하는 기준이 아니다.
- 이번 로컬 C++ 포트는 `--no-texture`에서 원시 형상을 내보내면서 일반 GLB 경로의 리메시와 간소화를 건너뛴다. 따라서 원시 메시의 오류를 모델 자체의 최종 결과로 단정할 수 없다. 로컬 `--dump-post`는 텍스처 없이도 정리된 리메시 데이터를 별도 바이너리로 출력하지만 그대로 GLB는 아니며 해당 결과는 미검증이다. 형상만 출력하는 경로에 리메시와 후속 간소화를 연결해 같은 입력·시드로 재검사하는 것이 우선이다.
- 후처리 결과를 기준으로 얼굴·손·팔다리 간극과 정점·면 수, 열린 경계, 비다양체, 면 방향 충돌, 자기 교차를 검사한다. 리메시는 얇은 손가락이나 간극을 합칠 수 있어 외형·단면·실루엣 비교가 필요하다. 10만·30만·100만 면 등은 프로젝트가 선택하는 비교 후보일 뿐 공식 권장 리깅 수치가 아니다. 실제 스켈레톤·스킨과 관절 변형·무기 동작은 별도 검증한다.
- [공식 모델 카드](https://huggingface.co/TencentARC/Pixal3D)는 Pixal3D를 MIT로 표기하지만 제3자 구성요소에는 각각의 조건이 적용된다고 명시한다. [DINOv3 모델 카드](https://huggingface.co/facebook/dinov3-vitl16-pretrain-lvd1689m)의 별도 라이선스와 NAF 체크포인트 등 실제 사용 구성요소의 조건은 별도 검토 대상이며, 전체 상업 이용이 검증됐다는 뜻은 아니다.

## 형상 전용 리메시·폴리곤 감소 실험

양옆 파편을 제거한 기존 메시를 보존하고 C++ 포트의 weld, 작은 구멍 메우기, narrow-band DC 리메시(해상도 1024, band 1), CPU QEM 간소화(목표 30만 면)를 형상에만 별도 적용했다. 실험 도우미 소스는 `workflow/domains/pixal_experiment/geometry_repair_trial.cpp`이며 텍스처 모델을 실행하지 않았다. 이는 포트 함수를 이용한 실험으로 공식 구현과 수치 동등성을 검증하지 않았다. 리메시는 4,390,928면을 생성했고 간소화 출력은 140,826정점·287,436면이다.

결과 `.tmp/pixal-experiment/rig-check-87edd/remesh-300k/candidate.glb`의 GLB 재읽기에서 좌표·면 인덱스를 확인했다. 8방향 깊이 버퍼 렌더의 대략적 실루엣 IoU는 각각 0.9765~0.9822다. 이는 얇은 손가락, 손과 몸 간극이나 3D 형태가 온전하다는 증거가 아니다. 이전 메시의 면 방향 충돌 600,169개는 0개, 열린 경계 54,645개는 0개, MeshLab 자기 교차 선택 면 9,031개는 495개로 감소했다. 하지만 비다양체 변 2,359개가 남아 watertight 판정은 거짓이며, 연결 성분 478개 중 최대 280,718면 외에 6,718면이 다른 성분에 있다. 자기 교차 수치는 서로 다른 메시에서 도구가 선택한 면의 수이며 교차 쌍이나 완전 검출 보장은 아니다. 실제 리깅·변형과 손/몸 간극은 검증하지 않았다.

8방향 참조를 양면 법선 가중으로 정점 색상 투영한 후보는 `remesh-300k/colored/colored.glb`다. 이는 근사 투영이며 UV 텍스처가 아니고 구조를 수정하지 않는다. 리깅 준비 통과로 판정하지 않는다.

## 비다양체·자기 교차 수리와 손 간격 비교

면 삭제·구멍 메우기 방식의 첫 후보는 비다양체 변을 0으로 줄였지만 경계 변 2,641개와 자기 교차 선택 면 1,695개가 생겨 채택하지 않았다(`remesh-300k/topology-repair/repair-report.json`).

별도 PyMeshFix 후보 `remesh-300k/meshfix/candidate.glb`는 근접 성분 연결과 작은 성분 강제 제거 옵션을 끈 채 생성했다. 면 수는 287,436개에서 240,862개로 변했고, 색은 수리 전 메시의 최근접 정점에서 복사했다. PyMeshFix 실행은 `MeshFix could not fix everything` 경고를 출력했다. 후속 독립 검사에서는 연결 성분 1개, watertight 참, 면 방향 일관, 경계·비다양체·방향 충돌 변 각각 0개, MeshLab 자기 교차 선택 면 0개였다. 선택 면 0은 모든 교차가 없다는 증명은 아니다.

수리 전후 8방향 정사영 실루엣 IoU는 약 0.99935 이상이다. 정면의 손 높이 5개 표본 행에서는 양손과 몸 사이가 떨어져 보이고 손가락 구간도 관찰됐으며 수리 전후 표본이 같았다. 512px 투영과 수동 지정 영역의 제한된 검사라 3D 전체의 최소 간격이나 손가락 보존, 움직일 때의 충돌을 보장하지 않는다(`meshfix/gap-comparison.json`, `meshfix/hands-comparison.png`). UniRig 필수 의존성이 현재 환경에 없어 뼈·스키닝 및 관절 변형을 실행하지 못했다. 따라서 구조 검사 통과를 실제 리깅 가능 판정으로 바꾸지 않는다. 사용자가 제공한 DINO 약관은 전체 파이프라인 상업 이용의 확정 판단과 별개로 검토해야 한다.
