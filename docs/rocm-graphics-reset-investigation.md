### GNOME 키맵 경쟁 상태 후보 (2026-11-16)

사용자는 충돌 직전 키보드를 사용하지 않았다고 확인했다. 해당 시스템의 입력원은 `[('xkb', 'kr+kr104'), ('ibus', 'hangul')]`, 입력 옵션은 빈 목록이며 활성 GNOME 확장 목록도 비어 있었다. 설치 버전은 GNOME Shell `50.1-0ubuntu1.5`, `libmutter-18-0` 및 `mutter-common` `50.1-0ubuntu2.2`, `libxkbcommon0` `1.13.1-1`이다. 당시 호출 스택과 00:02 프로세스 코어 덤프는 확보되지 않았다.

동일 Ubuntu 26.04·Wayland·두 한국어 입력원과 `xkb_keymap_mod_get_index`의 충돌을 조사한 [Ubuntu 버그 2171283](https://bugs.launchpad.net/bugs/2171283)은 Mutter 입력 스레드와 메인 스레드의 키맵 수명 경쟁을 보고하며, [Mutter upstream 변경 709ef343](https://github.com/GNOME/mutter/commit/709ef343)을 수정으로 제시한다. 단일 입력원은 위험을 줄일 수 있는 임시 우회로 제시됐을 뿐 수정 보증은 아니다. 별도 [Ubuntu 버그 2152175 보고](https://bugs.launchpad.net/bugs/2152175)는 키보드를 사용하지 않은 때의 유사한 충돌을 기록한다. 호출 스택이 없는 이 시스템의 이번 충돌이 해당 버그와 같은지 확정할 수 없다. 키 입력이 없더라도 키맵 갱신이 발생할 가능성은 이 후보와 양립하지만 실제 트리거는 미확인이다.

로컬 APT 후보 버전은 `50.1-0ubuntu2.5`이며 해당 버전으로 올리면 이 결함이 수정된다는 보장은 없다. 충돌 당시의 오류 주소와 함수 위치는 기록했으나 직접 비교할 코어 덤프가 없어 근본 수정 검증은 미완료다. 활성 세션의 입력원을 변경하면 한영 입력과 키보드 배치에 영향을 주고 변경 중 세션이 재종료될 수 있으므로 현 설정을 유지했다. 입력원을 줄이는 실험은 한글 입력 유지와 복원 계획을 확보한 뒤 별도로 수행한다. 앞선 AMDGPU ring timeout 장애는 이 GNOME 키맵 충돌과 별개로 남아 있다.

사용자 요청에 따라 기존 입력원 목록을 로컬 `.tmp/gnome-input-backup/`에 저장하고 GNOME `sources`를 `[('ibus', 'hangul')]`로 변경했다. 적용 직후 IBus 엔진 `hangul`과 기존 GNOME Shell 프로세스 유지, 최근 커널 로그에 새 충돌이 없음을 확인했다. 설정의 `current` 값과 IBus 엔진/최근 사용 기록은 서로 달라 변경 전 화면에서 선택된 입력원을 확정하지 못했다. 실제 한글·영문 입력과 장시간 재발 방지는 사용자 확인 및 별도 관찰이 필요하다. 이는 키맵 갱신 빈도를 줄이려는 임시 우회이며 Mutter 패치 또는 AMDGPU 장애 해결로 간주하지 않는다. 복원은 `gsettings set org.gnome.desktop.input-sources sources "[('xkb', 'kr+kr104'), ('ibus', 'hangul')]"`이다.

## 2026-11-19 ROCm SDK 교차 시험 중 화면 오류

31.70 DKMS와 Secure Boot 활성 환경에서 기존 ROCm 10.0용 PyTorch 2.13에 ROCm 10.2 SDK를 교차한 첫 65프레임 VAE 실행 중 23:23:57 AMDGPU `gfx_0.0.0` 큐 timeout이 기록됐다. 커널은 ChatGPT의 그래픽 스레드를 표시했고 GPU 코어 덤프를 생성했으며, 23:23:58 ring reset 성공과 장치 복구를 기록했다. 직후 ChatGPT 로그에 GL 컨텍스트 손실과 GPU 프로세스 재시작이 나타났고 사용자는 화면 표시가 깨졌다고 보고했다. 재부팅 후 화면 깨짐이 사라졌다고 확인했다. 덤프는 재부팅 전에 확보하지 못했고 현재 최초 결함 명령·호출 스택과 물리 GPU 상태는 확인할 수 없다. 로그의 프로세스 표시는 최초 원인이라는 증거가 아니며 교차 SDK, 31.70 드라이버, 그래픽 클라이언트 및 다른 부하 중 어느 것이 원인인지 이 기록만으로 판정하지 않는다.

이후 같은 드라이버에서 별도로 준비한 공식 `torch 2.15.0+rocm10.2.0`·ROCm 10.2 SDK·torchvision 0.29.2 조합은 5프레임 사전 검증과 65프레임 VAE의 False·True 각 2회를 완료했고, 각 실행 중 커널 로그 감시에서 새로운 timeout·fault·reset은 감지되지 않았다. 제한된 단일 입력과 짧은 실행이므로 리셋이 해결됐거나 장시간 화면 안정성이 입증된 것은 아니다. 잠재값의 기존 기준과의 차이는 [ROCm NaN 사례집](rocm-nan-cases.md)에 별도 기록한다.
