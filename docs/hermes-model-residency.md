# Hermes 모델 유휴 유지 정책

이 문서는 공용 모델 서버를 구현할 때 적용할 정책이다. 현재 작업별 모델 서버는 작업 종료 시 해제되며, 이 문서와 `model_residency_policy.py`만으로 상주 기능이 켜지지는 않는다.

상주 모델은 가능한 한 유지한다. 생성 작업은 먼저 공용 대기열에서 기존 예약과 사용 가능한 GPU 메모리를 확인하고, 충분하면 상주 모델과 함께 실행한다. 부족하면 실행 중 작업의 자연 종료와 예약 반환을 기다리는 등 상주 모델을 유지할 수 있는 실행 기회를 우선 고려한다. 그래도 필요한 메모리를 확보할 수 없고 반환 후 작업 실행이 가능하며 안전한 해제 조건이 확인된 경우에만 상주 모델 반환을 최후 수단으로 검토한다. 실행 중인 대화를 강제 종료하거나 소유권이 확인되지 않은 프로세스를 종료하지 않는다. 반환은 스케줄러의 자원 관리이며 별도 사용자 동의를 받지 않는다. 생성 자체에는 필요한 사용자 승인이 적용된다.

이 문단은 목표 정책이다. 모든 생성기와 기존 양도 경로가 이를 아직 따르는 것은 아니며, 구현 현황은 [GPU 양도 설계](hermes-gpu-handoff-design.md)에 구분한다.

- 성공적으로 끝난 요청의 모델은 후속 요청이 없어도 기본 60초 동안 유지한다. 운영자가 설정할 수 있는 상한은 300초이며 0초는 유지를 끈다.
- 같은 모델 프로필의 후속 요청만 정상 상태와 예약 신원을 다시 확인한 뒤 재사용한다. 세션 문맥, 작업 공간, 요청 데이터는 매 작업마다 분리한다.
- 다른 모델의 요청, 다른 서비스의 실행 대기, 메모리 압박, GPU 예약 또는 서버 상태 확인 불가, 서비스 종료 시 유휴 모델을 반납한다. 실행 중인 요청은 선점하지 않는다.
- 유지 시간 동안 모델 프로세스와 GPU 메모리는 독립된 상주 예약으로 계속 기록한다. 모델이 실제로 종료됐다는 확인 전에 예약을 지우지 않는다. 다른 생성기의 자원 판단에서 상주 모델을 제외하지 않는다.
- 상주 서버의 프로세스·부팅 신원을 검증하고, 종료나 재시작 후 신원이 불확실하면 자동 재사용하지 않는다. 모델 준비·교체·다운로드와 독립 검증에는 기존 사용 잠금과 GPU 배타 규칙을 계속 적용한다.
- 유휴 진입·재사용·반납 사유·반납 확인 실패를 관측 가능하게 기록하고, 대기열에는 실행 중 작업과 상주 모델을 구분한다. 오류 발생 시 확인되지 않은 메모리 해제를 성공으로 표시하지 않는다.

실제 적용에는 작업 실행기 밖에 공용 서버 관리자를 두고, 기존 작업별 GPU 예약을 상주 예약으로 안전하게 이전한 뒤 후속 작업에 다시 연결해야 한다. 서버 교체·종료 경합, 프로세스 장애 복구 및 다른 생성기의 대기 공정성을 검증하기 전에는 단순히 작업별 모델 종료를 지연하지 않는다.

## 세션 Qwen과 공용 대기열의 현재 구현

위 항목은 목표 정책이며 아래는 별도로 구현된 세션별 Qwen 동작이다. 모델이 없어도 대화 요청을 저장하고 공용 GPU 대기열에서 적재할 수 있다. 양도 스케줄러는 대기 중인 대화 없이 유휴 GPU에 모델을 주기적으로 선적재하지 않는다. 기존에 명시적으로 승인한 GPU 양도는 그 양도의 저장된 절차를 따른다.

공용 대기열에 생성 작업이 기다릴 때 상주 예약의 신원과 예약이 확인되며, 해당 모델을 반환한 뒤 선행 생성 작업을 실행할 여유가 있다고 판단되면 정상 반환을 요청한다. 상주 예약이 둘이면 둘의 신원을 확인하고 한 번에 하나씩 반환한다. 반환 직전 GPU 잠금 아래에서 조건을 재확인한다. 진행 중인 대화의 사용권과 연결이 끝날 때까지 서버는 종료하지 않으며, 예약 해제 여부와 생성 작업의 실제 실행 가능성은 종료 뒤 다시 확인한다. 같은 상주 접수에 연결된 대화가 아직 시작되지 않았거나, 준비된 상주 모델의 다른 대화가 생성 작업보다 앞서면 반환을 보류한다. 반환 후 일반 대화의 재적재는 대기 요청에 의해서만 공용 대기열에 접수된다.

다른 세션의 Qwen 적재가 자원 부족으로 기다리고 반환 후 실행 가능해지는 경우에도 같은 절차를 적용한다. 같은 세션의 중복 상주 접수나 일반 Hermes 작업을 이 반환 사유로 취급하지 않는다. 실제 두 세션 시험에서 두 번째 Qwen은 호스트 메모리 보호 조건으로 대기했고, 첫 대화 완료와 상주 모델 반환 뒤 적재되어 두 대화 모두 `확인`으로 완료됐다. 두 모델의 동시 상주는 시험하지 않았다.

현재 자동 반환은 상주 예약이 둘을 넘거나 다른 GPU 예약이 함께 있는 경우, 관측이 불확실한 경우에는 실행하지 않는다. VRAM과 공유 GTT 모두에서 상주 프로세스 그룹의 관측 RSS를 반환 가능량 추정에 포함한다. RSS에는 공유 페이지가 포함될 수 있으므로 실제 회수량을 보장하지 않으며, 작업 실행 전 실제 여유를 다시 확인한다. 두 상주 모델의 반환은 모의 메모리와 파일 잠금을 사용하는 검사로 검증했으며 실제 두 모델로는 아직 검증하지 않았다. 위 60초 유지와 전체 유휴 반환 정책이 모두 구현된 것으로 해석하지 않는다.

실제 Qwen 3.8 시험 세션 `f389116db5d44d508c7dcbaae45eb0ad`에서 대화 실행 중 GPU 연산 없는 독점 예약 시험 `verify_8a5b4db2a9674f89b1bc913d798542e9`을 공용 대기열에 접수했다. 모델이 반환 대기로 전환된 동안 대화가 계속 실행되어 `확인`으로 완료됐고, 상주 모델 종료 후 시험 예약이 완료됐다. 이어 같은 세션의 새로운 대화 접수로 Qwen의 GPU 재적재와 예약 신원을 확인하고 두 번째 대화도 `확인`으로 완료했다. 시험 상주 모델은 정상 종료하고 GPU 예약 반환을 확인했다. 시험 예약은 실제 생성 모델이 아니므로 자동 반환 뒤 실제 생성의 종단 간 검증은 별도로 남는다.

이후 같은 시험 세션의 대화와 5프레임 실제 VACE 작업 `2026-11-23_10-09-39-3a47ff8f`을 공용 대기열에 접수했다. Qwen이 반환 대기 상태인 동안 대화가 정상 완료됐고, Qwen 종료 뒤 VACE가 GPU 예약을 얻어 5개 프레임과 MP4를 생성했다. 프레임 무결성과 기록된 SHA-256을 확인했다. 결과의 시각적 품질은 검수하지 않았다.

대화 생성과 반환을 서비스 잠금으로 직렬화한 뒤 같은 세션의 실제 Qwen 대화 `2026-11-23_10-27-40-146f587f`와 GPU 연산 없는 독점 예약 `verify_guard_2c671946640c4ddebf0028bb3f792e37`을 시험했다. 대화가 실행 중인 동안 반환이 보류됐고, 대화가 `확인`으로 완료된 뒤 Qwen이 정상 종료되고 독점 예약이 완료됐다. 시험 작업들의 GPU 예약은 정리됐다.
