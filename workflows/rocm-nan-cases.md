# ROCm NaN 사례집

2026-11-15 기준. 실행 기술 기록이며 모델·입력 텐서·영상·로그는 Git에 등록하지 않는다. 공통 절차는 [ROCm 추론 가이드](rocm-inference.md)를 따른다. 커밋 제목이 아니라 실제 diff와 검증 기록으로 해결 범위를 판단한다.

## 운영 전환 맥락

이 작업들은 최근 며칠 전까지 CUDA에서 정상 동작했으며, ROCm으로 전환한 후 이 사례집의 문제가 관측됐다. CUDA 운영 중에는 해당 NaN 문제를 경험하지 못했다. 따라서 전환으로 달라진 GPU·커널·라이브러리와 실행 환경은 우선 조사 대상이다. 다만 기존 운영 경험만으로 CUDA와 ROCm에서 모든 입력·모델 리비전·설정이 동일했거나 특정 구성 요소가 원인임이 증명되지는 않는다. 사례별 최초 비유한 경계와 동일 입력 재현을 통해 원인을 분리한다.

## HeartMuLa — 커널 경로 한정 우회

근거: Git `68a3f7bb` (`fix(music): ROCm 음악 생성과 재생 안정화`), `generators/music/heartmula/runtime.py`, 당시 AGENTS.md 변경.

기본 SDPA와 같은 입력의 수학 SDPA 결과가 달랐으므로 코드북 디코더에만 수학 경로를 적용했다. 메타 모델 로딩 이후 비영속 RoPE 버퍼 초기화와 생성 점수 유한값 검사를 보강했다. 할당 옵션을 False로 해도 NaN이 관측됐으므로 메모리 할당 설정을 공통 해결책으로 삼지 않는다. 모든 음악 모델이나 다른 GPU의 검증으로 확대하지 않는다.

## Wan Fun Control — VAE 조건과 할당 설정

근거: Git `a7d11326` (`fix: Wan Fun ROCm VAE 수치 안정성 개선`), `generators/wan_fun/worker.py`와 관련 테스트.

VAE 인코딩 직후와 모델 해제 이후 조건 텐서의 지문·유한 여부를 기록한다. 일반 GPU VAE를 FP32로 사용하고 디코딩 시 다시 적재하며, `PYTORCH_ALLOC_CONF=expandable_segments:False`를 초기화 전에 설정하고 이전 환경변수의 중복 재정의를 제거했다. 여러 조치가 함께 포함돼 단일 변경의 인과를 증명하지는 않는다. OOM을 CPU 추론이나 자동 타일 대체로 숨기지 않는다.

주의: `1c427908`의 제목에도 수치 안정성이 있지만 실제 diff는 모션 프레임 배분·UI·테스트다. VAE 수정 근거는 `a7d11326`이다.

## VACE — 지연과 NaN을 구분

근거: Git `ec21e9a1`, `generators/wan_vace/numerical_guard.py`, `official_runtime.py`, `official_full_precision.py`, `workflows/rocm-inference.md`.

실제 65프레임 BF16 self-attention 형상은 `[1,40,28080,128]`이었다. 연속 배치 적용 후 첫 호출은 복사 포함 약 0.961초, 첫 스텝 약 177초였고 이전 실행의 첫 스텝은 약 618초였다. 조건과 프로파일링 차이가 있어 엄밀한 단일 변수 벤치마크로 취급하지 않는다. 해당 실행은 20스텝을 완료했고 어텐션 Q·K·V 및 출력 3,840회, 전문가 출력·스텝 잠재값 각 20회가 유한했다. 긴 실행과 사용률 100%만으로 NaN을 추정하지 않는다. 유한값 통과와 영상 품질 승인은 별도다.

## Animate2 — 어텐션 이전에 손상된 입력

환경: Radeon 8060S, PyTorch `2.13.0+rocm10.0.0`, HIP `7.15.26333`, BF16, 5프레임·2스텝·시드 42. 환경 문자열은 당시 실행값이며 호환성 인증을 의미하지 않는다.

- 실패 작업 `2026-11-15_21-52-37-4228cda4`: 첫 참조 추출 호출, 마스크 없음, Q/K/V 각각 `[1,3016,40,128]`. 각각 15,441,920개 중 7,720,960개가 NaN. 토큰 0–1507은 유한하고 1508–3015는 전부 NaN이었다.
- 실제 Q/K/V·출력·마스크 행을 해당 시도의 `attention-input.safetensors`에 보존했다. 첫 유한 Q 행과 전체 K/V를 같은 GPU에서 재생했을 때 기본·수학 SDPA 모두 128개 NaN을 반환했다. 커널 교체로 비정상 입력이 복구되지 않는다.
- 정상 비교 작업 `2026-11-15_21-56-28-bb041bf8`: Flex Q `[1,4608,40,128]`, K/V `[1,7680,40,128]`. `attention-sample.safetensors`와 JSON에 블록 마스크·함수·클로저를 보존했다. 첫 유효 행에서 기본·수학 SDPA 모두 유한했고 Flex 대비 최대 절대 차이는 각각 0.0009765625, 0.00390625였다. 한 행의 비교이며 전체 커널 정확도 검증은 아니다.
- 후속 VAE·첫 블록 계측에서는 NaN을 다시 포착하지 못했다. VAE, 정규화, 투영 중 최초 발생 지점은 아직 미확인이다. 계측 동기화가 실행 조건을 바꿀 가능성도 별도 검증해야 한다.
- VAE 출력·스케줄러 예측/입출력·최종 프레임을 검사해 손상 결과를 완료로 저장하지 않도록 했다. 적용 후 `2026-11-15_22-04-19-061c2fa1`은 5프레임·2스텝을 약 93.3초에 완료했다. 해당 실행에서 GPU 오류는 관측되지 않았다. 짧은 성공 한 번으로 간헐적 NaN이나 이전 그래픽 큐 타임아웃이 해결됐다고 선언하지 않는다.

## 외부 사례와 비교

2026-11-15 확인. 아래는 외부 사용자의 보고이며, 이 저장소에서 재현하거나 동일 원인임을 확인한 사례가 아니다. CUDA와의 비교 여부도 구분한다.

- **ESMFold2 어텐션** — AMD MI300A, ROCm 6.2, PyTorch 2.5에서 어텐션 이후 NaN이 발생했고, 보고자는 Flash·memory-efficient SDPA를 끄고 수학 SDPA를 사용해 우회했다고 기록했다. ROCm 6.4와 PyTorch 2.9 조합에서도 해결됐다고 보고했다. HeartMuLa의 경로 한정 우회와 유사하지만 동일 커널 결함을 증명하지 않는다. 보고자의 ROCm 한정 주장과 별개로 이 사례집에서 CUDA 동일 입력 비교는 확인하지 않았다. [ESMFold2 이슈 #322](https://github.com/Biohub/esm/issues/322)
- **긴 시퀀스의 BF16 비전 어텐션** — gfx1100, PyTorch 2.9.1 ROCm 빌드에서 약 14,200~14,688 토큰 이상일 때 NaN과 비결정적 출력이 발생했다는 보고다. 작성자는 NVIDIA GPU가 없어 CUDA 직접 비교를 하지 못했다고 명시했다. 형상과 길이를 재현 조건에 포함할 근거이지 VACE의 지연을 NaN으로 판정할 근거는 아니다. [ROCm 이슈 #6416](https://github.com/ROCm/legacy-rocm-build/issues/6416)
- **큰 입력의 VAE 디코더** — RX 7800M, ROCm 환경의 Stable Diffusion 업스케일링에서 큰 입력에 대해 VAE 출력의 NaN·Inf가 보고됐다. MIOpen/HIP 관련성은 작성자의 추정이며 최초 원인과 CUDA 비교는 확정되지 않았다. Wan Fun의 VAE 조건값 검사를 뒷받침하는 참고 사례이지 FP32의 보편적 해결을 증명하지 않는다. [ROCm 라이브러리 이슈 #1571](https://github.com/ROCm/rocm-libraries/issues/1571)
- **동적 VRAM과 앞선 단계의 손상** — ComfyUI의 AMD ROCm 사용자는 검은 이미지의 원인을 처음 VAE로 추정했다가 계측 후 샘플러 출력과 일부 캐시 가중치에 이미 NaN이 있었다고 정정했다. 페이지 재사용 관련 설명은 보고자의 가설이다. Animate2에서도 최종 손상 위치가 아닌 최초 비유한 경계를 찾아야 한다는 참고 사례이며, 동일 메모리 문제가 확인된 것은 아니다. [ComfyUI 이슈 #15452](https://github.com/Comfy-Org/ComfyUI/issues/15452)

PyTorch는 ROCm Flash Attention에서 AOTriton과 Composable Kernel 백엔드 선택을 제공하며 실제 사용 가능 여부는 빌드에 따른다. GPU·버전·형상에 따라 선택 경로가 달라질 수 있으므로 CUDA에서 관측되지 않은 이유를 확인하려면 동일 입력과 설정에서 실제 경로와 결과를 비교해야 한다. [PyTorch 백엔드 구현](https://github.com/pytorch/pytorch/blob/main/torch/backends/cuda/__init__.py)

### Animate2 Wan VAE 실측

Radeon 8060S `gfx1151`, PyTorch `2.13.0+rocm10.0.0`, HIP `7.15.26333`, BF16, 시드 42에서 Animate2의 고정 VAE 가중치·런타임을 사용했다. 64×64 합성 단일 프레임을 인코딩·디코딩하며 VAE 내부 SDPA의 실제 Q/K/V를 가로채 같은 텐서와 의미로 수학 경로 1회, 기본 경로 3회를 비교했다. 진단 코드는 로컬 `.tmp/rocm-vae-check/check.py`에 있으며 생성 입력은 실제 사용자 영상이 아니다.

인코더와 디코더 양쪽의 Q/K/V는 `[1, 1, 64, 384]`, stride `[73728, 73728, 1152, 1]`이고 모두 유한했다. 기본 출력 세 번과 수학 출력도 유한했지만, 기본 첫 출력의 수학 출력 대비 평균 절대 오차는 각각 **2.10054**, **0.23022**, 기준 평균 절대값 대비 비율은 **6.21445**, **1.01458**이었다. 각 경계에서 동일 입력의 기본 출력 3회는 서로 일치하지 않았다. 인코딩·디코딩 최종 텐서의 유한값 검사도 통과했다. 디코더 입력은 기본 경로로 얻은 인코딩 결과이므로 독립적인 전체 VAE 정확도 비교는 아니다.

별도 합성 BF16 Q/K/V `[1,1,1024,384]`, `[1,1,4096,384]`도 모두 유한했지만 기본 첫 출력의 수학 대비 평균 절대 오차는 각각 0.24160, 0.02107, 상대 평균 오차는 5.94883, 1.0이었다. 동일 입력의 기본 출력 3회는 일치하지 않았다. 따라서 **우리 Animate2 VAE의 해당 실행에서도 유한하지만 크게 다른 기본 SDPA 결과가 재현됐다.** 이는 외부 사례와 같은 증상이지 내부 커널의 동일 근본 원인이나 다른 Wan 구현·모든 형상의 실패를 증명하지 않는다. 실제 사용자 입력·대표 해상도, CUDA 비교, 선택된 정확한 커널과 해당 빌드의 수정 포함 여부는 미검증이다. 수학 경로를 적용한 전체 생성의 품질·성능·회귀 검증도 아직 수행하지 않았다.

### Animate2 VAE 한정 수학 SDPA 적용 후 검증

VAE 인코딩·디코딩에만 수학 SDPA를 선택하도록 우회했으며 Transformer 어텐션은 기존 경로를 유지한다. 관련 범위·예외 복구 단위 검사 7건은 통과했다. 실사용 입력과 같은 참조 이미지·동작 영상, 832×480, 5프레임·2스텝·시드 42로 공용 대기열에서 실행한 작업 `2026-11-15_22-44-40-e6540e10`은 유한값 검사를 통과하고 완료됐다. 결과 기록에서 VAE 수학 경로를 확인했다. 총 약 93.22초, 5초 간격 샘플 기준 작업자 GPU 메모리 피크 46,777 MiB였다. 이전 같은 요청의 완료 실행은 약 93.32초, 피크 46,771 MiB였다. 실행별 환경·측정 오차가 있어 이 수치는 엄밀한 성능 벤치마크가 아니다.

**품질 실패:** 생성된 5개 프레임을 시각 검수한 결과 심한 색상·배경 손상과 인물 외형 불일치가 관측됐다. 이전 완료 실행의 첫 프레임은 참조 인물과 유사하게 보였으나, 실행 간 비교만으로 수학 SDPA 변경이 품질 차이의 원인임을 입증할 수 없다. ## 재발 방지와 신규 사례 기록 기준

1. 입력 전처리·단위·dtype·shape·stride·마스크·캐시·시드와 GPU/ROCm/PyTorch/모델 리비전, 할당 설정을 기록한다.
2. VAE/인코더 → 모델 입력 → Q/K/V → 어텐션 출력 → 스케줄러 → 최종 결과에서 최초 비유한 경계를 찾는다. 발견 시 원본을 보존하고 실패 처리한다. NaN 치환으로 통과시키지 않는다.
3. 유한한 입력에서만 커널 원인을 분리한다. 동일 마스크·길이·scale·causal·dropout 의미로 GPU 기본/수학 경로를 비교한다. 패딩의 전부 가려진 행과 실제 사용 행을 구분한다.

5. 사례 상태를 `관측`, `원인 분리`, `우회 적용`, `회귀 검증`, `미해결`로 명확히 적는다. 커밋 해시·실패/검증 작업 ID·증거 파일명·검증하지 않은 조건을 남긴다. 재현 데이터는 작업 저장소에 보관하며 존재·해시를 확인한 범위만 보고한다.

추가 계측 결과와 스크립트는 기존 `.tmp/test/animate2-vae-origin/2026-11-16_10-45-00/`에 보존했다. 기존 운영 경로의 `expandable_segments:False`와 VAE math 설정을 유지한다. 원인 분석에는 첫 잠재 프레임과 두 번째 프레임의 차이, 시간 캐시·연산 스트림 및 계측 영향을 구분하는 추가 실험이 필요하다.

### VAE 최초 실행 전 메모리 상태와 캐시 할당 비교

보존한 동일 영상 텐서와 VAE BF16, math SDPA, `expandable_segments:True` 조건을 독립 프로세스의 최초 실행에서 비교했다. 모델 로드 후 256 MiB를 할당하고 0으로 채운 뒤 해제한 실험군과 할당하지 않은 대조군 모두 3/3회에서 두 번째 잠재 프레임의 96,512개 값이 NaN이었다. 추가 처리는 할당·동기화·실행 순서를 동시에 바꾸므로 단순한 초기화 부족만으로는 관찰을 설명할 수 없다는 제한적인 결과다.

같은 True 조건에서 `PYTORCH_NO_HIP_MEMORY_CACHING=1` 설정군과 미설정군을 독립 프로세스로 번갈아 세 쌍 비교했다. 미설정군은 3/3회 NaN, 캐시 비활성화군은 3/3회 유한했다. VAE 실행 전 `torch.cuda.memory_reserved()`는 미설정군 272 MiB, 비활성화군 0으로 캐시 사용에 차이가 있었다. 캐시 비활성화는 할당과 가상 메모리 분할·재사용·할당 시점을 함께 바꿀 수 있어 특정 구현이나 드라이버, 최초 연산을 근본 원인으로 확정하지 못한다. 결과는 `warm-*-*.json`과 `cache-*-*.json`에 보관했다. 짧은 VAE 단독 진단이며 운영 환경의 캐시 비활성화 검증은 아니다. 기존 `expandable_segments:False` 완화를 유지한다.

### HIP 명령 완료 대기 진단

같은 True 조건에서 HIP 명령 완료 대기를 독립 프로세스 3회씩 비교했다. 아무 직렬화가 없는 기준군은 3/3회 96,512개 NaN이었다. `AMD_SERIALIZE_KERNEL=1`(커널 투입 전 대기)도 3/3회 실패했고 `=2`(투입 후 대기)와 `=3`(전후 대기)은 각각 3/3회 유한했다. 복사 명령은 `AMD_SERIALIZE_COPY=1`이 3/3회 실패하고 `=2` 및 `=3`은 각각 3/3회 유한했다. 각 값의 의미는 [AMD HIP 디버깅 문서](https://rocm.docs.amd.com/projects/HIP/en/docs-7.2.1/how-to/debugging.html)를 따른다.

명령 완료 대기에 따른 실행 순서·타이밍·메모리 재사용 영향이 강한 후보임을 보여 주지만, 전역 직렬화는 전체 명령 흐름과 소요 시간을 바꾸므로 특정 경쟁 상태나 오류 커널의 증명은 아니다. 이는 진단용 별도 프로세스 설정이며 운영 환경에 적용하지 않았다. 결과는 `serialize-*-*.json`, `svar-*-*.json`, `copy-*-*.json`에 있다.

같은 True 조건에서 VAE 실행 중 `torch.cuda.synchronize()`를 국소적으로 추가해 encoder 각 호출 후, 입력 합성곱 후, 각 down block 후, mid block 후, 출력 합성곱 후를 각각 비교했다. 각 방식은 독립 프로세스에서 1회 실행했으며 모두 96,512개의 NaN이 남았다. down block 후 동기화는 총 22회였다. 앞서 HIP의 모든 커널·복사 제출 후 기다린 실험과는 대기 위치·명령·순서가 다르다. 각각 1회 관측만으로 특정 블록이나 메모리 복사를 원인에서 배제할 수 없으며 측정 범위를 좁히는 자료로 사용한다. 결과는 `sync-*.json`에 있다.

### GPU 실행 추적과 외부 보고

PyTorch profiler로 같은 VAE 최초 인코딩을 설정별 1회 수집했다. `expandable_segments:True`에서는 최종 NaN 96,512개가 유지됐고 CPU 측 HIP API 추적에 `hipMemCreate` / `hipMemMap` 각 504회, `hipMemUnmap` / `hipMemRelease` 각 444회, `hipMemSetAccess` 85회가 기록됐다. `False` 출력은 유한했고 해당 API는 모두 0회였다. 양쪽 모두 `hipMemcpyAsync` 46회와 `hipLaunchKernel` 735회가 기록됐다. 모델 로드 이후 VAE 단독 구간이며 API 횟수는 프로파일러와 실행 조건에 따라 달라진다.

True 추적에서 map 504회 중 308회의 호스트 API 구간은 적어도 한 GPU 커널 실행 시간과 겹쳤고 unmap 444회에는 같은 중첩이 없었다. GPU 이벤트 수집 범위와 시간 측정에 의존하며 서로 무관한 할당과 커널의 중첩도 포함하므로 잘못된 접근, 의존성 누락 또는 특정 map 호출의 결함을 입증하지 않는다. 추적은 `torch-vae-trace.json`과 `torch-vae-false-trace.json`에 보관했다. 시스템 `rocprofv3`는 Python 시작 시 LLVM analysis 중복 등록 오류로 실행 전에 종료됐다.

[AMD HIP 6.4 가상 메모리 문서](https://rocm.docs.amd.com/projects/HIP/en/docs-6.4.1/how-to/hip_runtime_api/memory_management/virtual_memory.html)는 가상 메모리 매핑 해제·해제 함수가 `hipFree`와 달리 메모리 해제 시 동기화를 제공하지 않는다고 설명한다. 이 문서는 설치된 HIP 7.15보다 오래된 버전의 일반 API 설명이다. 따라서 호출자가 GPU 사용 완료를 어떻게 보장하는지 살피는 근거가 되지만, PyTorch 할당기의 별도 동기화나 이번 실행의 특정 해제가 잘못됐다는 증거는 아니다. 앞서 기록된 호스트 API와 GPU 작업의 시간상 중첩만으로는 같은 할당의 GPU 사용 중 해제 여부를 확정할 수 없다.

외부 [PyTorch #187343](https://github.com/pytorch/pytorch/issues/187343)은 ROCm expandable segments에서 `hipErrorIllegalAddress`가 발생한 별도 보고로 Ubuntu 26.04와 커널 7.0 사례가 있다. 이 시스템의 커널도 `7.0.0-43-generic`이지만 해당 보고는 NaN이나 같은 GPU의 재현이 아니며 커널 측 원인 추정도 확정되지 않았다. [PyTorch #195202](https://github.com/pytorch/pytorch/issues/195202)는 다른 GPU `gfx1201`의 BF16 학습에서 expandable segments와 관련된 NaN을 보고해 이 시스템의 gfx1151 추론과 조건이 다르다. 동일 장애로 단정하지 않고 최소 재현과 기기별 검증의 참고 자료로 사용한다.

설치된 PyTorch가 보고하는 소스 리비전 `6596a0dea537c1c78520c73cc6678214781a9d06`에 해당하는 [공식 할당기 소스의 `unmapHandles`](https://github.com/pytorch/pytorch/blob/6596a0dea537c1c78520c73cc6678214781a9d06/c10/cuda/CUDACachingAllocator.cpp)를 확인했다. 이 소스는 매핑 해제 전에 세그먼트 스트림이 지정돼 있으면 해당 스트림을, 없으면 장치를 동기화한 뒤 ROCm에서 `hipMemUnmap`과 `hipMemRelease`를 호출한다. 따라서 HIP API 자체의 동기화 부재만으로 PyTorch가 동기화를 생략한다고 주장할 수 없다. 배포물에 적용된 별도 패치 여부나 실제 실행 시 해당 분기의 적용·다른 스트림 의존성까지 소스 확인만으로 입증하지 않으며, 이번 NaN의 원인도 미확정이다.

실제 True 실패 프로파일에는 `hipStreamSynchronize` 58회와 `hipMemUnmap` 444회가 기록됐고, False 성공 프로파일에는 해당 스트림 동기화와 매핑 해제가 기록되지 않았다. True의 각 스트림 동기화가 끝난 뒤 같은 호스트 스레드에서 다음 `hipMemUnmap`이 시작되기까지의 간격은 58회 모두 1ms 미만이었다(최대 약 0.024ms). 이는 소스에 나타난 해제 전 동기화 경로와 부합하는 관측이지만, 시간과 스레드만으로 각 호출의 동일 할당 관계나 동기화 대상 스트림이 올바른지 입증하지 못한다. 프로파일러가 포착하지 않은 작업도 배제하지 않는다.

이 58개 동기화와 각각 이어진 같은 스레드의 첫 매핑 해제는 프로파일러의 `External id`도 모두 일치했다. 다만 기록된 동기화 API 인자에는 스트림 핸들이 없고 `External id`는 GPU 스트림 번호가 아니므로, 이 정보는 같은 프로파일 범위 내 호출이라는 보조 근거일 뿐 실제로 동기화한 스트림과 메모리 사용 스트림의 일치 여부를 결정하지 못한다.

시스템 `rocprofv3`의 LLVM 중복 등록 오류와 별도로, PyTorch 가상환경의 `_rocm_sdk_core`에 포함된 `rocprofv3`는 해당 PyTorch import 및 HIP 추적을 시작할 수 있었다. 이 프로파일러를 이용한 True VAE 단독 1회에서는 NaN이 재현되지 않았다. 산출된 JSON은 약 404MiB였고 UTF-8 디코딩 오류로 일반 JSON 파싱이 실패해 동기화 대상 스트림 인자를 확인하지 못했다. 따라서 프로파일러 계측이 재현을 억제했을 가능성이 있고 이 실행으로 실패 당시 스트림 의존성을 판정할 수 없다. 결과와 감시 기록은 `wheeltrace-*`, `rocprof-wheel-vae/`에 있다.

위 JSON의 디코딩 오류는 일부 커널 이름 문자열에 포함된 비 UTF-8 바이트에서 관찰됐다. 손상된 문자를 대체하고 제어문자를 허용하는 관대한 파싱으로 구조를 읽었을 때, 해당 실행의 HIP API 기록에는 `hipStreamSynchronize` 61회와 `hipMemUnmap` 444회가 있었고 동기화 인자로 기록된 스트림 값은 모두 0이었다. 손상된 문자열을 복구한 검증된 JSON은 아니며, 이 실행은 최종 출력이 유한했으므로 이 수치를 NaN 실패 실행의 스트림 인자로 확대할 수 없다. 값 0은 해당 호출의 스트림 인자이고 다른 GPU 작업이 모두 이 스트림에서 완료됐다는 뜻도 아니다.

같은 환경과 입력의 True 조건에서 가상환경의 `rocprofv3 --hip-trace`를 독립 프로세스로 두 번 추가 실행했을 때도 두 번 모두 최종 잠재값이 유한했다. 앞선 프로파일 실행까지 3/3회 유한하며 비계측 True 실행은 별도 대조에서 3/3회 NaN이었다. 실행 시점과 프로파일 계측이 다르므로 특정 계측 기능이 원인이라고 단정하지 않지만, 이 프로파일 방식이 실패 추적을 얻기 위해서는 재현율 검증이 필요함을 보여준다. GPU 감시 기록과 결과는 `wheelrepeat-*`, `rocprof-wheel-repeat-*/`에 있다.

이후 같은 시점에 비계측과 `rocprofv3 --hip-trace`를 독립 프로세스로 번갈아 두 쌍 비교했다. 비계측은 2/2회 각각 NaN 96,512개였고 프로파일 실행은 2/2회 유한했다. 실행 순서는 두 쌍 모두 비계측 다음 프로파일로 고정되어 있고 시도 횟수가 적어 다른 시간 의존 변수를 완전히 배제하지 못한다. 프로파일링이 현재 재현을 방해한다는 근거를 강화하지만, 내부 어느 동작이 결과를 바꾸는지는 미확정이다. 결과와 감시 기록은 `wheelpaired-*`, `rocprof-paired-*/`에 있다.

프로파일된 True 실행의 잠재값을 별도로 두 번 보존해 False 기준과 비교했을 때 둘 다 유한했지만 두 잠재 프레임 모두에서 값 차이가 났다. 첫 프레임의 평균 절대 차이는 각각 약 1.672와 0.060, 두 번째는 약 0.695와 0.491이었다. 첫 번째·두 번째 프레임의 각 96,512개 값 중 매번 90,000개 이상이 달랐다. False 기준은 같은 모델·입력의 별도 실행이며 독립적인 정답은 아니다. 이 결과는 프로파일로 NaN이 사라져도 잠재값이 동일하거나 정확하다는 뜻이 아님을 보여준다. 원인과 계측 영향은 미확정이며 비공개 결과는 `wheelnumeric-*`, `rocprof-numeric-*/`에 있다.

같은 프로파일러와 동일 입력을 `expandable_segments:False`로 두 번 실행한 대조에서는 두 잠재값이 모두 유한했고, 비계측 False 기준과 비트 단위로 일치했다. 이 입력과 두 실행에 한해 프로파일러 사용 자체가 항상 수치를 바꾸는 것은 아니며, 앞선 True 조건의 수치 차이를 해석하는 대조 자료다. 다른 입력이나 모든 프로파일 설정으로 일반화하지 않는다. 비공개 결과와 감시 기록은 `wheelfalse-*`, `rocprof-false-*/`에 있다.

위 프로파일 산출물을 잘못된 문자열 대체·제어문자 허용 방식으로 읽어 HIP 반환값을 비교하면, True 두 실행 각각 `hipMemCreate`·`hipMemMap` 523회, `hipMemSetAccess` 104회, `hipMemUnmap`·`hipMemRelease` 444회, `hipStreamSynchronize` 61회의 기록된 반환값은 모두 0이었다. False 두 실행에서는 해당 VMM 호출은 기록되지 않았고 `hipStreamSynchronize` 3회의 반환값이 모두 0이었다. 관대한 파싱의 한계가 있고, 반환 성공은 해당 API 호출이 기록상 오류를 반환하지 않았다는 의미일 뿐 메모리 내용·비동기 연산 또는 드라이버의 정확성을 증명하지 않는다. 이 프로파일 실행은 NaN 대신 유한한 수치 차이가 난 사례다.

같은 네 추적의 전체 HIP API 기록에서 True 두 실행은 각각 `hipMalloc` 3회·`hipFree` 0회, False 두 실행은 각각 62회·29회였고 `hipMemcpyAsync` 46회와 `hipLaunchKernel` 750회는 네 실행 모두 같았다. 앞선 VMM 호출 수와 함께 할당 경로의 차이를 확인하지만, 전체 호출 횟수가 같다는 사실은 커널 인자·순서·연산값이 같거나 수치 차이가 메모리 할당에서 발생했다는 증명이 아니다. 기록은 모델 로딩을 포함하는 프로파일 범위이며 잘못된 문자열을 대체한 파싱 결과다.

True 수치 차이 추적과 False 기준 추적 각 1회의 `hipLaunchKernel` 750개에 기록된 grid·block 차원, 공유 메모리 크기, 스트림 인자의 순서는 모두 일치했다. 함수 주소와 텐서 포인터는 독립 프로세스에서 다르므로 이 비교에 넣지 않았고 커널 함수·인자 내용·실제 GPU 실행 완료 순서는 검증하지 않았다. 관대한 JSON 파싱과 프로파일 계측의 한계도 그대로 적용된다. 따라서 제출 형상 차이만으로 두 결과의 수치 차이를 설명할 수는 없다.

### VAE 두 번째 encoder 호출과 블록 입력 보존

동일 VAE `_encode`의 순서를 진단 코드에서 재현하며 첫 encoder, 두 번째 encoder, 두 출력의 결합 및 `quant_conv` 직후의 유한값 검사를 지연 수집했다. True 3회 모두 첫 encoder 출력은 유한하고 두 번째 encoder 출력 `[1,32,1,58,104]` 전체 193,024개가 NaN이었다. 저장된 CPU 텐서도 같은 상태였고 결합·quant_conv 이전에 이상이 있었다. False 3회는 전 단계 유한했다. 단일 프레임 입력에서도 실패한 별도 실험이 있으므로 전체 결함이 반드시 두 번째 encoder 호출에만 한정된다는 의미는 아니다.

같은 실행에서 encoder의 `down_blocks.2`와 `.3` 출력을 참조로 유지한 비교는 True 3/3회 두 번째 호출의 `.2` 출력이 유한하고 `.3` 출력이 비유한이었다. False 3/3회는 모두 유한했다. 진단 참조가 텐서 수명과 할당 패턴을 바꿀 수 있으므로 비계측 실행에서의 최초 연산으로 확정하지 않는다.

별도 True 실행에서 두 번째 `down_blocks.3` 호출 전에 주 입력, 두 시간 캐시, 블록 파라미터를 GPU에서 복사해 보존했다. 저장된 주 입력·캐시·파라미터는 모두 유한했고 블록 출력은 비유한이었다. `block3-1708174.safetensors`의 SHA-256은 `f4ef4e4897a9105d65a46a32f614e11fe27d26b45ef5ae81691c48fd54552c07`이다. 동일 값·캐시·가중치로 residual 블록만 독립 재생했을 때 첫 True 실행은 첫 회 NaN, 이후 두 회는 유한했고 False는 3회 유한했다. 그러나 뒤이은 독립 True 프로세스 3개에서는 각각 3회 모두 유한해 단독 블록 NaN의 재현성은 확보하지 못했다. safetensors 저장 시 입력은 연속화되어 원래 stride·할당 상태와 다르다. 개별 하위 연산 출력을 유지한 별도 6회 역시 최종 NaN을 없애 최초 하위 연산을 판정하지 못했다. 원시 입력·캐시 보존은 후속 재현 자료이며, 메모리 상태와 계측 영향을 구분하는 추가 작업이 필요하다.

추가 True 실패 실행에서 두 번째 `.3` 블록의 입력 stride `[37060608,96512,9265152,416,1]`과 두 시간 캐시 stride `[9265152,96512,96512,416,1]`, `[18530304,96512,96512,416,1]`를 해당 실행에서 직접 기록했다. 주 입력·캐시·가중치는 유한하고 블록 출력은 비유한이었다. 값과 가중치는 `block3-1722658.safetensors`에 보관했으며 SHA-256은 `17298c37709327b3aab4bc37319e6e7eb753cb3b2fb4a89eda2932e2a371bc24`다. safetensors 파일 내 값은 연속화되어 있으므로 독립 재생 시 기록된 stride를 복원해야 하며 원래 GPU 가상주소·할당 이력은 복원되지 않는다.

같은 실패 실행에서 저장한 `block3-1722658.safetensors`를 사용해 주 입력과 두 시간 캐시의 위 stride를 GPU에서 `empty_strided`와 값 복사로 복원하고 잔차 블록 단독으로 재생했다. 독립 프로세스를 각 설정별로 3회 실행하고 매번 블록을 3회 호출한 결과 True·False 모두 9회 전부 유한했다. 데이터·stride·모델 가중치·캐시 값은 같지만 원래 스토리지 오프셋, GPU 가상 주소, 이전 할당 이력과 명령 순서는 복원하지 않았다. 따라서 이 범위에서 stride만으로 실패가 결정된다는 가설은 지지되지 않으며, 같은 블록이 단독으로 항상 정상이라는 증명도 아니다. 결과는 `stride-True-*.json`, `stride-False-*.json`에 있다.

### 잔차 블록 내부 입력 및 동기화 경계

`down_blocks.2`와 `down_blocks.3`의 개별 내부 출력만 참조하는 진단을 각각 새 True 프로세스에서 수행했다. 두 번째 encoder 호출의 `.2` 출력과 `.3.conv_shortcut` 출력은 유한했으며 `.3.conv1` 출력은 비유한이었다. `.3.norm1` 출력을 참조한 실행에서는 최종 NaN 자체가 재현되지 않아 별도 실행 결과를 동일 실행상의 최초 오류 순서로 연결할 수 없다.

같은 실행에서 `.2`와 `.3.conv1` 출력을 보존하고 conv1 호출 직전의 주 입력과 시간 캐시 참조도 보유한 교차 비교에서는 True 3/3회 두 입력이 유한하고 conv1 출력이 비유한이었다. False 3/3회는 모든 확인 출력이 유한했다. 예시 `stage-failure-1745292.safetensors` SHA-256은 `625f3c30183d27374dbab464e7e44a70be213f85685676390272ae279a8c9acc`다. 입력은 실행 전 복제가 아닌 참조 보유 방식이므로 비동기 처리 도중의 값 보존을 완벽히 입증하지 않는다. 연산 직전 GPU 복제를 추가한 비교에서는 True 3/3회 conv1 출력까지 유한했지만 두 번째 encoder 최종 출력의 NaN은 남았다. 복제가 할당 이력과 타이밍을 변경할 수 있어 이 비교만으로 원인을 확정할 수 없다.

동일 입력의 별도 True 프로세스에서 `.3` 하위 연산 후 GPU 동기화를 각 1회 비교하자 `norm1` 후 동기화는 유한했고 `conv_shortcut`, `conv1`, `norm2`, `conv2` 후는 각각 NaN이었다. 후속 교차 비교에서 동기화 없는 기준은 3/3회 실패, `norm1` 뒤 동기화는 3/3회 유한, 같은 블록의 활성화 함수 호출 뒤 동기화도 3/3회 유한했다. 여기서 활성화 함수는 두 차례 호출되므로 두 곳에서 기다렸다. `norm1` 첫 호출에서만 기다리면 3/3회 실패했고 두 번째 호출에서만 기다리면 3회 중 2회 유한, 1회 실패였다. 동기화는 전역 스트림·할당 순서를 바꾸므로 `norm1`이나 그 다음 conv1의 커널이 근본 원인이라는 증거는 아니다. 운영 코드에 이 진단 동기화를 추가하지 않았다. 결과는 `convinput-*.json`, `convclone-*.json`, `target-*.json`, `norm-repeat-*.json`, `occurrence-*.json`에 남겼다.

### 합성곱 단독 재생과 할당 이력 대조

기존에 저장한 `stage-failure-1745292.safetensors`의 두 번째 `conv1` 주 입력·시간 캐시와 같은 모델 리비전에서 보존한 `block3-1722658.safetensors`의 `conv1` 가중치·바이어스를 사용해 `WanCausalConv3d`만 재생했다. 주 입력과 캐시의 원래 stride도 복원했다. 별도 프로세스 True·False 각 3회에서 매 프로세스 세 번씩 실행한 18개 출력은 모두 유한했다. 원본 저장 출력은 비유한이었다. 값·형상·stride와 가중치를 복원해도 원래 GPU 주소·주변 할당과 명령 이력은 복원되지 않으므로, 이 관찰은 입력 또는 단일 합성곱만으로 안정적 재현이 안 된다는 뜻이다.

동일 VAE 입력의 메모리 할당 이력을 True·False 독립 프로세스에서 각 3회 교차 수집했다. True는 3/3회 비유한, False는 3/3회 유한했다. True 각 실행에서는 `segment_map` 85회와 `segment_unmap` 58회, False에서는 두 기록 모두 0회였다. 첫 True 이력에서 두 번째 encoder의 해당 형상 합성곱 실행 중 약 249.8 MiB 임시 할당의 해제 요청·해제 완료 뒤, 약 260 MiB 영역의 `segment_unmap`과 동일 가상 주소·크기의 `segment_map`이 뒤따르고 동일 임시 주소가 다시 할당됐다. 같은 합성곱 크기 후보 중 이 순서가 나타나는 패턴은 True 세 실행에서 모두 관측됐다. 이력은 PyTorch 할당기의 호스트 측 이벤트이며 `free_completed`는 GPU 커널 데이터 사용의 안전성이나 실제 물리 페이지의 상태를 독립적으로 증명하지 않는다. 주소 재매핑과 NaN의 인과, 특정 드라이버 결함, 임시 할당의 역할은 아직 확정되지 않았다. 세부 자료는 `allocator-{True,False}-*.pickle`과 `history-{True,False}-*.json`이다.

### GPU 복제 명령과 동기화 범위

실패가 유지된 기존 PyTorch profiler 기록에서 `hipMemcpyAsync` 46회는 모두 HIP `hipMemcpyDeviceToDevice`(kind 3)였고, 호스트 연산 트리에서는 모두 `aten::clone` 안에 있었다. 이 중 7회는 `aten::constant_pad_nd`도 상위 호출에 포함됐다. 이는 프로파일러가 수집한 해당 실행 범위만의 관측이며 모든 복제나 NaN 원인 복사를 식별한 것은 아니다.

별도 진단 프로세스에서 Python의 GPU 5차원 `Tensor.clone()` 반환 직후만 동기화하자 호출 48회 중 48회 대기한 설정은 True 조건에서 3/3회 유한했다. 동기화하지 않은 교차 대조군은 3/3회 96,512개 NaN이었다. 1~24번째 호출만 기다린 3회는 모두 NaN, 25~48번째 호출만 기다린 3회는 모두 유한했다. 후반을 다시 나누면 25~36번째 대기 3회는 모두 유한, 37~48번째 대기 3회는 모두 NaN이었다. Python 수준 `Tensor.clone`만 추적했으며 C++ 내부의 다른 clone·복사 호출 전체를 포괄하지 않는다. 번호는 이 고정 입력과 런타임의 호출 순서에 한정하고 동기화는 전역 대기·할당 시점도 바꾸므로 특정 복제 호출이 결함이라는 증거로 해석하지 않는다. 결과는 `clone-sync-*`, `clone-range-*`, `clone-range2-*`에 보존했다.

25~30번째와 31~36번째를 비교하던 별도 실행 도중 다른 GPU 작업이 시작된 것을 확인했다. 진단 프로세스가 이미 종료된 것을 확인했으며 해당 `clone-range3-*` 결과는 부하가 겹친 구간과 그렇지 않은 구간을 명확히 구분할 수 없어 대조 결론에 사용하지 않는다. 기존 사용자 작업은 중단하지 않았다. 진단용 동기화는 운영 코드에 넣지 않았다.

다른 GPU 프로세스를 실행 전·실행 중·직후에 감시하고 겹치면 진단 프로세스만 종료하는 절차로 다시 비교했다. 25~30번째 복제 후 동기화는 3/3회 유한, 31~36번째는 3/3회 NaN이었다. 이를 다시 나눈 25~27번째 대기는 3/3회 NaN, 28~30번째 대기는 3/3회 유한했다. 이 두 비교의 감시 기록에는 다른 GPU 프로세스가 없었다. 이어 개별 호출 비교에서 겹침 전에 끝난 첫 세 실행은 28번째·29번째만 대기할 때 각각 NaN, 30번째만 대기할 때 유한했지만 각각 1회여서 결론을 낼 수 없다. 이후 다른 GPU 프로세스가 나타나 두 차례 진단만 자동 중단됐고 사용자 작업은 유지했다. 반복·대조 검증과 실제 호출 위치 확인이 남아 있다. 검증 도구의 감시는 주기적 표본이므로 표본 사이의 매우 짧은 작업까지 완전히 배제한다고 주장하지 않는다. `isolated*-*.json`과 `isolated*-runner-events.jsonl`에 원본 기록이 있다.

### 두 번째 encoder의 30번째 Python clone 위치

동일한 고정 입력의 Python 5차원 GPU `Tensor.clone()` 호출 위치를 프로세스별로 기록했다. 28·29번째는 두 번째 encoder 호출의 `encoder.down_blocks.1` 잔차 블록에서 각각 첫 번째·두 번째 합성곱용 시간 캐시를 만드는 코드였고, 30번째는 `encoder.down_blocks.3`의 `norm1`과 활성화 후 첫 번째 합성곱에 들어가기 직전 시간 캐시를 만드는 clone이었다(`autoencoder_kl_wan.py` 360행). 이는 고정된 런타임 리비전·입력에서 Python 직접 호출을 센 것이며 내부 C++ clone 전체의 30번째라는 뜻이 아니다.

`torch.cuda.synchronize()`를 30번째 Python clone 직후 한 번만 넣고 호출 위치를 함께 기록한 교차 실험에서, 동기화 없는 기준 3/3회 NaN, 전장치 동기화 3/3회 유한이었다. 같은 위치의 `torch.cuda.current_stream().synchronize()`는 완료된 2회 중 1회 NaN·1회 유한이었고 그 대조군은 2/2회 NaN이었다. 세 번째 쌍 시작 중 다른 GPU 프로세스가 감지돼 진단만 종료했다. 각 조건의 횟수가 적고 동기화·Python 프레임 기록이 타이밍·할당 상태를 바꿀 수 있어, 해당 clone 자체의 결함이나 단일 스트림 밖의 특정 경쟁 상태를 입증하지 않는다. 결과는 `mapmodule-*`, `mapstream-*` 및 대응하는 감시 이력에 있다. 전장치 동기화는 진단에서만 사용하고 운영 정책의 근거로 확대하지 않는다.

추가 오프라인 이력 분석에서 True 독립 실행 3개의 각 58회 `segment_unmap`은 이력 수집 시작 이후 `alloc`됐고 아직 `free_completed`되지 않은 블록 주소 범위와 겹치지 않았다. 수집 시작 전의 기존 할당, PyTorch 관리 밖의 메모리, 이미 `free_completed`됐지만 GPU에서 아직 사용 중인 메모리는 이 검사 범위에 포함되지 않는다. 따라서 할당기 장부상의 직접적인 활성 블록 해제 증거는 찾지 못했지만 비동기 수명·매핑 문제를 배제하지 않는다.

기존 실패 PyTorch GPU 추적을 오프라인으로 대조한 결과 `[1,96,2,232,416]`, stride `[37060608,96512,9265152,416,1]`인 `aten::clone`은 1건이며 Python 위치 확인에서 얻은 30번째 `down_blocks.3` 시간 캐시 복제의 형상·stride와 일치했다. 이 clone의 HIP API는 `hipMemcpyAsync`, GPU 간 복사 kind 3, 37,060,608바이트였다. ### 캐시 복제 직후 호스트 지연 비교

동일한 실제 입력·BF16 VAE·math SDPA와 `expandable_segments:True`를 사용하고 독립 프로세스로 대조군과 실험군을 번갈아 세 쌍 실행했다. 앞에서 확인한 30번째 Python 캐시 clone 직후 GPU 동기화 없이 호스트에서 `time.sleep(0.010)`만 호출한 실험군은 3/3회 유한했고, 같은 계측을 하되 존재하지 않는 49번째 clone에서 지연하도록 지정한 대조군은 3/3회 각각 96,512개 NaN이었다. 두 군 모두 실제 clone은 48회였다. 결과 파일의 `synchronized_clones`는 진단 스크립트가 물려받은 필드 이름이며 이 실험에서는 GPU 동기화 횟수가 아니라 호스트 지연 호출 횟수다. 측정 완료를 위한 최종 동기화는 양쪽 모두 동일하게 수행했다.

이 결과는 해당 위치에서 GPU 완료를 명시적으로 기다리지 않는 시간 지연만으로도 관찰된 실패를 바꿀 수 있음을 보여준다. 지연 중 GPU 작업이 자연스럽게 끝났는지, 호스트 할당 순서나 드라이버 내부 상태가 어떻게 변했는지는 측정하지 않았으므로 완료 의존성·메모리 매핑·스케줄링 중 어느 것이 원인인지 입증하지 않는다. 지연은 운영 코드에 적용하지 않았다. `hostdelay-*-*.json` 및 `hostdelay-runner-events.jsonl`에 결과와 GPU 프로세스 감시 기록을 남겼다. 감시는 주기적 표본으로 매우 짧은 외부 작업을 완전히 배제하지 못한다.

같은 위치에서 요청 지연을 0.1ms, 1ms, 5ms로 바꾼 후속 실험에서는 각 조건을 독립 프로세스로 두 번씩 수행했다. 지연 없는 대조군과 0.1ms·1ms는 각각 2/2회 NaN이었고 5ms는 2회 중 1회 유한, 1회 NaN이었다. 앞선 10ms 3/3회 유한 결과와 함께 보면 지연 길이에 따른 변화가 관찰되지만, 실행 횟수가 적고 `sleep`의 실제 대기 시간과 GPU 완료 시각을 측정하지 않아 임계 시간이나 인과관계를 결정할 수 없다. 각 대조군 다음 0.1ms·1ms·5ms 순서로 실행했으므로 시간에 따른 다른 상태 변화의 영향도 배제하지 않는다. 결과와 감시 기록은 `delayrange-*-*.json`과 `delayrange-runner-events.jsonl`에 있다.

같은 clone 직후 현재 스트림에 GPU 이벤트를 기록하고 호스트가 비차단 조회하는 별도 대조 실험을 세 쌍 수행했다. 대조군은 `sleep(0)`을 호출했고 실험군은 10ms를 요청했다. 이벤트 기록 전까지의 스트림 작업 완료 여부는 지연 전과 후 모두 6/6회 미완료로 조회됐다. 실제 호스트 대기 측정은 대조군 약 0.10~0.12ms, 실험군 약 10.12~10.15ms였다. 대조군은 3회 중 2회 NaN·1회 유한, 실험군은 3/3회 유한이었다. 이벤트 기록과 조회 자체가 타이밍을 바꿀 수 있고 이벤트는 앞선 스트림 작업 전체의 완료를 나타내므로, 개별 복사만 완료됐는지 또는 다른 스트림과 드라이버 내부 상태가 어떠했는지는 이 관측으로 알 수 없다. 따라서 10ms 지연이 현재 스트림 전체를 완료시켜 NaN을 없앴다고 설명할 수 없으며 근본 원인도 여전히 미확정이다. `eventprobe-*-*.json`과 `eventprobe-runner-events.jsonl`에 결과와 GPU 감시 기록을 보관했다.

별도로 앞서 저장한 True 실패 및 False 성공 프로파일 각 1회를 다시 분석했다. 후보 복사의 호스트 `hipMemcpyAsync` 호출 시점부터 해당 GPU 복사 시작 전까지 수집된 GPU 커널은 True 9개·실행 시간 합 8.565ms, False 10개·합 10.399ms였으며 모두 profiler stream 1이었다. 이 커널 중에는 BF16 복사·원소별 연산과 SiLU가 있었다. 두 값은 관측 구간에서 시작한 커널의 실행 시간 합이며 앞서 진행 중이던 커널이나 프로파일러에 나타나지 않은 작업은 포함하지 않는다. 별도 이벤트 실험의 10ms 미완료 상태를 직접 설명하거나 같은 타이밍을 보장하지 않으며, 대기 시간만으로 실패를 판단할 수 없다는 기존 결론을 보강하는 참고 관측이다.

후보 30번째 Python clone 직전과 직후 중 한 곳에서만 호스트가 10ms 대기하는 비교를 독립 프로세스에서 세 쌍 수행했다. 직전 지연과 직후 지연은 각각 3/3회 유한했고 실제 clone은 매회 48개였다. 해당 clone을 제출하기 전에 지연해도 결과가 바뀔 수 있으므로 후보 복사의 완료만이 지연 효과의 필수 조건이라고 볼 수 없다. 이 비교 자체에는 지연 없는 동시 대조군이 없고 앞선 별도 실험의 대조 결과와 실행 시점도 다르며, Python 코드 경로와 GPU·할당 타이밍이 바뀐다. 최초 비정상 연산이나 근본 원인은 여전히 확정하지 못한다. 결과와 다른 GPU 작업 감시 기록은 `delayposition-*-*.json`, `delayposition-runner-events.jsonl`에 보관했다.

이후 같은 진단 코드에서 지연 없음·복제 직전 10ms·복제 직후 10ms를 한 묶음으로 세 번 순차 비교했다. 지연 없음은 3/3회 각각 NaN 96,512개였고 두 지연 조건은 각각 3/3회 유한했다. 각 조건이 독립 프로세스이며 실행 순서는 매번 고정이다. 따라서 앞선 결과가 단지 별도 시점의 대조군과 비교한 차이일 가능성은 줄었지만, 지연에 따른 기존 GPU 작업 진행·호스트 할당·스케줄링을 분리하지 못하며 해당 복제 연산의 결함을 입증하지 않는다. 결과와 GPU 감시 기록은 `positioncontrol-*-*.json`, `positioncontrol-runner-events.jsonl`에 있다.

30번째 clone을 호출하기 직전에 현재 스트림에 이벤트를 기록하고 비차단 조회한 다음 `sleep(0)` 또는 10ms 호스트 지연 후 다시 조회하는 대조 실험도 세 쌍 실행했다. 두 조건 모두 지연 전후 이벤트는 6/6회 미완료였으며, 대조군 3/3회는 NaN 96,512개, 지연군 3/3회는 유한했다. 실측 호스트 대기는 각각 약 0.12~0.13ms와 10.12~10.14ms였다. 이벤트가 나타내는 선행 스트림 작업 전체는 지연 뒤에도 완료되지 않았으므로 이를 모두 완료한 효과라고 설명할 수 없다. 이벤트 앞의 개별 GPU 작업이 얼마나 진행됐는지, 메모리 매핑이나 다른 스트림 상태는 관측하지 못했고 이벤트 계측 자체도 실행에 영향을 줄 수 있다. 결과와 감시 기록은 `precloneevent-*-*.json`, `precloneevent-runner-events.jsonl`에 있다.

### 유한한 출력의 수치 비교

동일 입력·모델·BF16·math SDPA로 운영 설정 `expandable_segments:False`와 진단용 `True` 및 30번째 clone 직후 10ms 호스트 지연을 독립 프로세스에서 번갈아 세 쌍 실행하고 VAE 잠재값을 CPU 파일로 보존했다. 여섯 출력 모두 유한했다. False 세 출력은 서로 완전히 일치했으며 True 지연 세 출력은 첫 번째 잠재 프레임이 서로 같았으나 세 번째 실행의 두 번째 프레임은 첫 번째 실행과 최대 절대 차이 1.72265625, 평균 0.22979였다.

같은 쌍의 False와 True 지연을 비교하면 첫 잠재 프레임은 모두 정확히 일치했고, 두 번째 프레임은 세 쌍의 최대 절대 차이가 각각 2.125, 2.125, 3.046875, 평균 절대 차이는 각각 약 0.48171, 0.48171, 0.57615였다. 두 번째 프레임의 96,512개 값 중 각각 95,736개, 95,736개, 95,631개가 달랐다. 따라서 **NaN이 없다는 것만으로 True 지연 결과의 수치 일관성이나 정확성을 보장할 수 없다**. False 출력이 절대적인 정답이라는 증명은 아니며, 이 비교만으로 차이를 유발한 연산을 특정할 수 없다. 호스트 지연은 운영 완화로 채택하지 않는다. 결과와 보존 텐서, GPU 작업 감시 기록은 `latentcompare-*`에 있으며 입력에서 파생된 비공개 데이터이므로 외부에 공개하지 않는다.

추가로 encoder `down_blocks.2` 출력 참조를 유지해 같은 두 조건을 세 쌍 비교했다. 첫 번째 호출 출력은 세 쌍 모두 정확히 일치했지만 두 번째 호출 출력은 True 지연 측이 세 쌍 모두 유한한 상태에서 False와 달랐다. 두 번째 호출 출력 37,060,608개 중 각각 37,012,378개, 36,961,462개, 36,948,174개가 달랐고 평균 절대 차이는 약 2.09, 1.45, 1.28이었다. 최종 잠재값은 True 지연에서 2/3회 유한, 1/3회 비유한이었다. 참조 유지가 텐서 수명과 할당 상태를 바꾸므로 이전 비계측 실행의 정확한 오류 위치를 확정하지 않지만, 이 계측 조건에서는 이전에 NaN 후보로 관찰한 `down_blocks.3`보다 앞선 `.2` 출력에서 이미 수치 차이가 있음을 보여준다. False가 절대 정답이라는 증명은 아니다. 비공개 파생 텐서와 감시 기록은 `latentstage-*`에 있다.

별도 세 쌍에서는 `.2` 대신 더 앞선 `down_blocks.1`의 출력 참조를 유지했다. 첫 번째 호출은 세 쌍 모두 정확히 일치했고 두 번째 호출은 2/3쌍에서 일치했으나 나머지 한 쌍에서는 True 지연 출력이 유한함에도 148,242,432개 중 147,936,095개가 달랐다(최대 절대 차이 6.734375, 평균 약 0.64253). 같은 세 쌍의 True 지연 최종 잠재값은 1회 유한·2회 비유한이었다. 이 계측 실행 중 하나에서는 `.1` 출력에서부터 수치 차이가 발견됐지만, 앞선 `.2` 계측과는 참조 유지 대상이 달라 같은 실행의 최초 차이로 연결할 수 없다. 기준 False의 절대 정확성과 개별 연산 원인 역시 입증하지 않는다. 비공개 파생 텐서와 감시 기록은 `latentearlier-*`에 있다.

다시 별도 세 쌍에서 `down_blocks.0` 출력 참조를 보유해 비교한 결과, 첫 번째와 두 번째 호출 출력은 각 쌍 모두 완전히 일치했다. 그럼에도 True 지연 최종 잠재값은 1회 유한·2회 비유한이었고, 유한한 1회도 False 최종값과 달랐다. 이 계측 조건에선 `.0` 출력 시점까지 관찰한 값이 같지만 참조 보유 대상이 다른 `.1` 실험과 하나의 실행으로 합칠 수 없으며, `.0` 내부 임시값이나 시간 캐시까지 같다는 의미는 아니다. 결과와 감시 기록은 비공개 `latentfirst-*`에 있다.

같은 실행에서 `.0`과 `.1`의 출력 참조를 둘 다 유지한 세 쌍 비교에서는 첫 번째 호출의 두 블록 출력이 모두 일치했다. 두 번째 호출은 2/3쌍에서 두 블록이 모두 일치했으나, 나머지 한 쌍은 `.0`부터 유한한 값이 달랐다(148,242,432개 중 147,810,060개, 최대 절대 차이 약 9.10, 평균 약 0.445). 해당 쌍의 `.1` 출력도 달랐다. True 지연 최종 잠재값은 세 쌍 모두 유한했으나 모두 False와 차이가 있었다. 두 출력 참조를 동시에 유지하면 메모리 수명이 바뀌므로 다른 계측 실험과 결과가 달라질 수 있다. 이 결과는 `.0` 출력이 항상 일치한다는 해석을 반박하지만 최초 원인 연산이나 기준 출력의 절대 정확성을 확정하지 못한다. 비공개 파생 텐서와 감시 기록은 `latentjoint-*`에 있다.

별도 세 쌍에서 encoder 입력 합성곱 `conv_in`과 `down_blocks.0`의 출력을 동시에 참조로 보유했다. 두 호출의 두 출력은 각 쌍 모두 False와 True 지연 간 완전히 일치했지만 True 지연 최종 잠재값은 세 번 모두 유한하면서 False와 달랐다. 이 계측 조건에서는 관찰한 두 경계에 차이가 없었으나, 참조 보유가 다른 위 `latentjoint` 실험의 `.0` 차이를 배제하지 않으며 내부 시간 캐시와 임시값의 동일성은 확인하지 않았다. 비공개 파생 텐서와 감시 기록은 `latentinput-*`에 있다.

첫 잔차 블록 `down_blocks.0`과 그 내부 `conv1` 출력을 함께 보유한 세 쌍 비교에서는 첫 호출이 모두 정확히 일치했다. 두 번째 호출은 한 쌍에서 두 출력이 일치했고, 두 쌍에서는 `conv1` 출력부터 유한한 값이 달랐다. 해당 두 쌍의 `conv1` 출력 평균 절대 차이는 약 0.620과 0.622였고 최대 절대 차이는 약 8.33과 8.28이었다. 이 두 쌍의 블록 출력도 달랐다. `conv1`의 입력·시간 캐시를 이 실험에서 실행 직전 보존하지 않았으므로 합성곱 입력이 같았는지 확인하지 못했고, 이 연산 자체를 최초 원인으로 확정할 수 없다. 계측에 따른 할당·수명 변화의 영향도 남는다. 비공개 파생 텐서와 GPU 감시 기록은 `latentconvfirst-*`에 있다.

후속 세 쌍에서는 같은 `conv1` 호출 직전의 주 입력·시간 캐시 참조까지 함께 보유했다. 저장해 비교한 첫 호출의 주 입력과 두 번째 호출의 주 입력·캐시, `conv1` 출력 및 블록 출력은 세 쌍 모두 False와 True 지연 간 완전히 일치했다. 그럼에도 True 지연의 최종 잠재값은 모두 유한하면서 False와 달랐다. 여기서 보유한 입력은 사전 복제가 아닌 참조이며 GPU 완료 후 CPU에 복사했으므로 연산 순간의 값을 독립적으로 보증하지 않는다. 추가 참조가 할당·수명을 바꾸므로 앞선 차이가 발생한 실행의 입력을 복원한 것도 아니다. 이 관측은 해당 계측 조건의 비교이며 `conv1`이 항상 정확하다는 증명이 아니다. 비공개 결과와 감시 기록은 `latentconvinput-*`에 있다.

같은 경계에서 후속 세 쌍은 참조 대신 GPU `empty_like`와 비동기 `copy_`로 합성곱 직전 주 입력·캐시를 별도 보존했다. 저장된 입력·캐시와 해당 `conv1` 및 블록 출력은 세 쌍 모두 False와 True 지연 간 일치했다. True 지연의 최종 잠재값은 1회 유한하나 False와 다르고 2회 비유한이었다. 별도 복사로 값을 더 일찍 보존했지만 GPU 할당·복사 명령과 수명을 추가한 다른 실행이며 앞선 `conv1` 차이 실행의 원본을 재현한 것은 아니다. 복사 시점과 실제 사용 시점의 동시성 문제도 이 비교만으로 완전히 배제하지 못한다. 비공개 결과와 감시 기록은 `latentconvcopy-*`에 있다.

블록 최종 출력 참조만 제거하고 같은 주 입력·캐시 사전 복제와 `conv1` 출력 보유를 반복한 세 쌍 중 한 쌍에서는 두 번째 호출의 True 지연 주 입력부터 False와 달랐다(148,242,432개 중 147,124,692개, 평균 절대 차이 약 0.295). 해당 캐시는 일치했고 `conv1` 출력도 유한한 값이 달랐으며 최종 잠재값은 비유한이었다. 나머지 두 쌍은 해당 입력·캐시·출력이 모두 일치했지만 최종 잠재값은 유한하면서 False와 달랐다. 차이가 난 쌍에서는 합성곱에 들어가기 전부터 이미 관찰된 값이 달라 입력 차이와 합성곱 자체의 영향을 분리해야 한다. 비동기 복사와 참조 보유가 실행을 바꾸며 입력의 수명·동시성까지 입증하지는 않는다. 비공개 자료와 감시 기록은 `latentconvonly-*`에 있다.

위에서 실제 수치 차이가 났고 최종 잠재값이 비유한이었던 True 지연 실행의 보존 주 입력·캐시를 고정 모델 가중치와 함께 같은 GPU에서 `conv1` 단독으로 재생했다. True와 False 할당기 각각 독립 프로세스 3개, 프로세스별 3회 모두 유한했고 해당 True 실행에서 보존한 합성곱 출력과 비트 단위로 일치했다. 이 입력에 대한 해당 실행의 출력 차이는 독립 재생에서도 그대로 관찰되며, 관찰된 주 입력 차이가 출력 차이를 설명하는 데 부합한다. 다만 원래 GPU 주소·할당 이력·비동기 상태는 복원하지 않았고 입력 생성의 최초 오류 원인이나 다른 조건에서의 합성곱 결함을 배제하지 못한다. 결과와 감시 기록은 `divergentreplay-*`에 있다.

같은 차이 실행의 보존 주 입력을 시간축별로 오프라인 비교하면 네 슬라이스 각각 값의 약 98.99%, 99.27%, 99.34%, 99.38%가 False와 달랐고 평균 절대 차이는 약 0.276, 0.276, 0.313, 0.316이었다. 합성곱 출력도 네 슬라이스 각각 약 99.76% 이상 값이 달랐다. 이는 관찰된 차이가 단일 시간 슬라이스에만 집중되지 않았다는 결과이지, 최초 오류 위치·메모리 손상 원인 또는 각 픽셀의 시각적 영향을 결정하지 않는다.

고정된 모델 코드의 첫 잔차 블록은 합성곱 입력을 만들 때 먼저 `norm1`, 다음 SiLU를 적용한다. `WanRMS_norm`은 BF16 입력을 FP32로 변환해 채널 방향 `F.normalize`를 수행한 뒤 BF16으로 되돌리고 스케일과 가중치를 곱한다. 따라서 BF16 모델이라는 사실만으로 이 구간의 모든 중간 연산이 BF16인 것은 아니다. SiLU는 전 구간에서 일대일 함수가 아니고 BF16 반올림도 있으므로 이미 저장된 활성화 결과만으로 이전 정규화 값을 유일하게 복원할 수 없다. 차이가 난 동일 실행의 정규화 입력·출력을 별도로 보존하지 못했으므로 FP32 정규화, 형변환, SiLU 중 최초 차이 연산은 정할 수 없다.

후속 세 쌍은 첫 블록의 `norm1` 호출 직전 입력도 별도 GPU 복사해 보존했다. 한 쌍에서는 두 번째 호출의 정규화 입력부터 유한값 차이가 있었다(148,242,432개 중 128,489,638개, 평균 절대 차이 약 0.161). 그 실행의 후속 합성곱 주 입력과 출력도 달랐고 시간 캐시는 일치했다. 나머지 두 쌍은 관측한 정규화 입력과 합성곱 경계가 일치했지만 최종 잠재값은 유한하면서 달랐다. 해당 첫 블록의 주 입력은 encoder 입력 합성곱의 출력이므로 차이가 발생한 쌍은 `norm1` 이전부터 살펴봐야 한다. 다만 GPU 복사와 참조 보유로 실행 상태가 변하고 입력 합성곱의 실제 호출 입력·캐시를 동시에 보존한 것은 아니어서 최초 원인 연산을 확정하지 못한다. 비공개 결과와 감시 기록은 `latentnorminput-*`에 있다.

보존된 실제 5프레임 BF16 VAE 입력 전체를 CPU에서 다시 검사한 결과 비유한 값은 없었고 최솟값 -1, 최댓값 1로 모든 값이 `[-1, 1]` 안에 있었다. 이 입력의 NaN이 입력 자체의 비유한 값이나 해당 범위 밖 값에서 직접 전달된 것은 아니라는 확인이며, 입력 내용과 연산 경로가 결함을 유발하는 가능성까지 배제하지 않는다.

실제 영상의 픽셀 내용이 재현에 필요한지 확인하기 위해 같은 `[1,3,5,464,832]` BF16 형상의 0 입력과 동일 VAE 가중치·math SDPA를 사용했다. ROCm 관련 외부 환경 변수를 제거하고 독립 프로세스에서 할당기만 바꾼 세 쌍에서 False는 3/3회 유한, True는 3/3회 두 번째 잠재 프레임의 96,512개가 NaN이었다. 이어 비공개 입력 파일을 아예 읽지 않고 GPU에서 같은 크기의 0 텐서를 생성한 세 쌍도 동일한 결과였다. 따라서 이 시스템·형상·모델 조건에서는 특정 영상의 픽셀 내용이 NaN 재현에 필수적이지 않다. 0 텐서의 생성 위치와 실제 입력의 로딩 경로는 달라 할당 이력이 동일하다는 뜻은 아니며, 모델 가중치와 시스템 환경은 여전히 필요하다. 결과와 감시 기록은 `zeroinput-*`, `synthetic-*`에 있다.

동일 VAE 구조를 시드 42의 무작위 가중치로 초기화하고 0 입력을 사용하는 별도 세 쌍에서도 False는 3/3회 유한, True는 3/3회 두 번째 잠재 프레임 96,512개가 NaN이었다. 이어 모델 가중치와 설정 파일을 읽지 않고 고정된 diffusers 리비전의 `AutoencoderKLWan()` 기본 구조만 생성한 세 쌍도 동일했다. 이 조건에서 비공개 영상과 다운로드 모델 파일은 재현에 필요하지 않다. 무작위 초기화는 실제 가중치와 할당 이력이 다르므로 양쪽에 동일한 근본 원인이 있다고 확정하지 않으며, 구조·입력 형상·소프트웨어·GPU 의존성은 남는다. 결과와 감시 기록은 `randomweight-*`, `standalone-*`에 있다.

기본 구조의 인스턴스 생성 후 디코더와 디코더용 `post_quant_conv`를 GPU로 옮기기 전에 제거한 0 입력 세 쌍에서도 False는 3/3회 유한, True는 3/3회 두 번째 잠재 프레임 96,512개가 NaN이었다. 이 합성 조건에서 디코더 가중치의 GPU 상주가 필수는 아니다. 인스턴스 생성 자체는 기존 기본 구조 전체를 CPU에 초기화했으며 제거로 할당 이력도 달라지므로 실제 모델 실패와 동일한 근본 원인으로 확정하지 않는다. 결과와 감시 기록은 `encoderonly-*`에 있다.

같은 합성 조건에서 VAE의 기본 채널 수를 96에서 48로 줄인 별도 세 쌍은 True·False 모두 3/3회 유한했다. 채널 수 변경은 모든 후속 형상·연산·할당 크기를 함께 바꾸므로 원래 NaN이 특정 메모리 크기나 커널 때문이라고 단정할 수 없으며, 유한값만 확인한 것으로 두 설정의 수치 일치 여부는 검사하지 않았다. 재현 축소 시 구조 변경 자체가 현상을 없앨 수 있다는 관측이다. 결과와 감시 기록은 `narrowvae-*`에 있다.

채널 수 48 조건을 별도 세 쌍 재실행하면서 잠재값을 보존해 비교했다. True 출력은 모두 유한했으나 False와 비트 단위로 일치하지 않았고, 193,024개 값 중 각각 192,885개·192,412개·192,341개가 달랐다. 평균 절대 차이는 약 0.133·0.121·0.087이었다. False도 독립 정답으로 검증된 것은 아니지만, 이 축소 모델에서 NaN이 사라진 사실이 두 할당기 설정의 수치 동등성을 뜻하지 않음을 확인했다. 비공개가 아닌 합성 결과와 감시 기록은 `narrowvalue-*`에 있다.

같은 보존 결과의 반복 실행끼리 비교하면 False 세 결과는 정확히 일치했다. True의 첫 번째 결과는 두 번째·세 번째 결과와 각각 평균 절대 차이 약 0.088·0.068이고 193,024개 중 각각 192,423개·192,733개가 달랐다. 입력과 무작위 시드는 같지만 각 실행은 별도 프로세스이므로 이 조건에서는 True의 유한값이 반복 간에도 일정하지 않았다. 이것만으로 비결정성의 정확한 원인이나 False의 절대 정확성을 증명하지 않는다.

초기화 변동 가능성을 확인하려고 같은 코드·시드로 채널 수 48 VAE를 CPU에서 별도 여섯 프로세스로 다시 생성하고 인코더와 `quant_conv` 상태를 이름 순서와 함께 SHA-256으로 계산했다. 할당기 설정별 각 세 실행의 해시는 모두 `1e0ba0285ed1fba356ad1c62d29a37018262d8d2cad79cc6f1369889fc9db811`로 같았다. 다만 이는 후속 CPU 초기화 확인이며 앞선 GPU 실행의 가중치 바이트를 직접 저장해 비교한 것은 아니고, GPU 전송 후 값이나 다른 실행 상태의 동일성을 보증하지 않는다.

이어 별도 세 쌍에서 CPU 초기화 값을 BF16으로 변환한 참조와 GPU 전달 직후 다시 CPU로 가져온 인코더·`quant_conv` 텐서 86개를 비교했다. 두 할당기 설정의 여섯 실행 모두 불일치와 비유한 값이 없었고 BF16 상태 해시도 같았다. 이 측정은 모델 전달 직후의 별도 실행으로, CPU 참조 보유와 동기 복사가 할당·시간을 바꾸며 앞선 출력 차이 실행에서 이후 가중치가 바뀌지 않았음을 증명하지 않는다. 결과와 감시 기록은 `transfercheck-*`에 있다.

같은 축소 모델을 세 쌍 다시 인코딩한 직후 각 실행의 인코더·`quant_conv` BF16 상태 해시를 계산했다. 여섯 해시는 모두 앞선 전달 검사의 BF16 참조 해시 `067baa12ddea91cc097127844cacb388bf6f50852ef2540a7f4ba0e80cc11f05`와 일치했지만, True·False 잠재값은 매 쌍 유한하면서 193,024개 중 각각 192,357개·192,394개·188,673개가 달랐다. 인코딩 종료 후 검사한 상태가 같더라도 중간 시점의 일시적 메모리 변화나 검사 과정의 영향을 배제할 수 없으며 원인 연산을 특정하지 못한다. 결과와 감시 기록은 `postweights-*`에 있다.

같은 `postweights` 결과의 반복 간 비교에서 False 세 출력은 정확히 일치했고 True 첫 출력과 나머지 두 출력의 평균 절대 차이는 약 0.0086·0.0531이었다. 즉 인코딩 후 가중치 해시가 같은 별도 실행들에서도 True 잠재값은 반복마다 달랐다. 가중치가 실행 중 일시적으로 변했는지나 다른 원인이 있는지는 이 검사로 결정할 수 없다.

축소 모델 `narrowvalue`와 `postweights` 각 세 쌍의 잠재값을 시간축별로 재검사한 결과, 여섯 쌍 모두 첫 번째와 두 번째 잠재 프레임 양쪽에서 True와 False가 달랐다. 첫 프레임 평균 절대 차이는 약 0.018~0.148, 두 번째는 약 0.033~0.137이었다. 이는 합성 축소 조건의 유한 수치 차이가 두 번째 잠재 프레임에만 국한되지 않는다는 관측이며, 각 인코더 청크 내부에서 처음 달라진 연산을 가리키지는 않는다.

축소 모델 첫 인코더 블록 출력 참조를 보유한 별도 세 쌍에서는 두 청크의 첫 블록 출력이 모두 True와 False 간 일치했지만 최종 잠재값은 세 쌍 모두 유한하면서 달랐다. 이 계측 조건에서 관찰한 첫 블록 이후에 차이가 남았지만 참조 보유로 할당·수명이 달라지므로 비계측 실행에서 최초 차이가 반드시 첫 블록 이후였다는 뜻은 아니다. 결과와 감시 기록은 `narrowblock-*`에 있다.

첫 블록 대신 두 번째 블록 출력만 보유한 별도 세 쌍에서도 두 청크의 해당 출력은 모두 정확히 일치했고, 최종 잠재값은 모두 유한하지만 설정 간 달랐다. 이는 이 계측 조건에서 두 번째 블록 출력 이후의 차이가 남았다는 뜻이다. 첫 블록을 보유한 실험과 다른 실행이므로 두 관측을 같은 실행의 연속적인 최초 경계로 결합할 수 없다. 결과와 감시 기록은 `narrowblock1-*`에 있다.

세 번째 블록 출력만 보유한 별도 세 쌍에서는 첫 청크 출력이 모두 일치했다. 두 번째 청크 출력은 두 쌍에서 일치했으나 나머지 한 쌍에서 유한한 값이 11,560,727개 달랐고 평균 절대 차이는 약 0.095였다. 최종 잠재값은 세 쌍 모두 유한하면서 달랐다. 앞선 블록 보유 실험과 계측 방식이 서로 달라 이 블록을 최초 차이 발생 연산으로 확정할 수 없고, 정상 기준의 절대 정확성도 입증하지 않는다. 결과와 감시 기록은 `narrowblock2-*`에 있다.

축소 모델에서 두 번째와 세 번째 블록 출력을 같은 실행에서 보유한 세 쌍 중 한 쌍은 첫 청크의 두 번째 블록 출력이 정확히 일치하지만 그 직후 세 번째 블록 출력의 유한값 4,632,575개가 달랐다(평균 절대 차이 약 0.103). 세 번째 블록은 이 구성에서 공간 축소를 수행하는 `WanResample`이다. 나머지 두 쌍은 해당 두 블록 출력이 일치했지만 세 쌍 모두 최종 잠재값은 유한하면서 달랐다. 입력 출력 참조는 실행 후 비교했으며 독립 복제·완료 순서와 내부 연산을 확인하지 않았고, 참조 보유가 수명·할당을 바꾼다. 따라서 `WanResample` 내부 특정 연산의 결함이나 최초 원인이라고 확정하지 않는다. 결과와 감시 기록은 `narrowjoint-*`에 있다.

공간 축소 호출 직전 주 입력을 별도 GPU 텐서로 비동기 복사하고 인접 두 블록 출력도 보유한 후속 세 쌍에서는 첫 청크 입력 복사본이 모두 설정 간 일치했으나 공간 축소 출력은 세 쌍 모두 유한하면서 4,632,575개가 달랐다(평균 절대 차이 약 0.103). 두 번째 청크의 해당 입력과 출력은 모두 일치했고 최종 잠재값은 세 쌍 모두 달랐다. 입력 복사는 같은 실행의 더 이른 보존 근거지만 추가 할당·복사와 출력 참조가 실행 상태를 바꾸며 GPU 주소·가중치 사용 시점·동시성까지 입증하지 않는다. `WanResample` 내부의 최초 비정상 연산이나 실제 모델 NaN과 동일한 원인도 아직 확정하지 못한다. 결과와 감시 기록은 `narrowcopy-*`에 있다.

공간 축소 내부의 제로 패딩과 2D 합성곱 출력도 참조로 보유한 세 쌍에서는 첫 청크의 복제 입력과 패딩 출력이 모두 설정 간 일치했다. 그중 두 쌍에서는 바로 다음 2D 합성곱 출력부터 유한한 값 4,632,575개가 달랐고, 나머지 한 쌍은 해당 출력도 일치했다. 첫 두 쌍의 최종 잠재값은 각각 유한·비유한, 나머지 한 쌍은 유한하지만 False와 달랐다. 패딩 출력과 합성곱 출력은 참조 보유 후 동기화해 비교했으므로 합성곱이 읽는 순간의 입력·가중치와 GPU 메모리 안정성은 독립적으로 입증하지 않는다. 이 계측 조건에서 관측 경계를 2D 합성곱 출력까지 좁힌 것이며 특정 커널 결함이나 실제 모델 NaN의 최초 원인으로 단정하지 않는다. 결과와 감시 기록은 `narrowinside-*`에 있다.

차이가 난 위 두 True 실행의 첫 2D 합성곱 출력은 각 채널의 BF16 편향값을 공간 전체에 반복한 값과 4,632,576/4,632,576개 모두 정확히 일치했다. 비교한 False 출력은 단 한 개 값만 편향과 같았다. 보존된 True 패딩 입력의 18,592,560개 중 18,530,302개와 동일 시드로 재생성한 합성곱 가중치 20,736개 전부가 0이 아니었다. 따라서 보존 출력에서는 합성곱 기여가 사라진 것처럼 보이지만, 실제 커널이 읽은 입력·가중치나 중간 버퍼를 연산 순간에 독립 확인한 것은 아니므로 0 입력 읽기, 가중치 읽기, 커널 실행, 출력 덮어쓰기 중 어느 것이 원인인지는 확정할 수 없다. 세 번째 True 실행은 False와 동일한 출력이었다.

같은 2D 합성곱 호출 직전 패딩 입력과 합성곱 가중치를 각각 별도 GPU 텐서로 비동기 복제하는 계측을 추가한 세 쌍에서, 첫 청크의 두 복사본은 모두 True와 False 간 정확히 일치했다. 이 중 True 2회는 합성곱 출력 4,632,576개 전부가 편향 반복값과 정확히 일치했으나 나머지 1회는 False 출력과 일치했다. 세 쌍의 최종 잠재값은 모두 유한하면서 설정 간 달랐다. 연산 전 독립 복제로 입력·가중치의 관측 근거는 강화됐지만, 복사와 실제 합성곱 사이의 비동기 메모리 상태·바이어스 소비·중간 버퍼와 추가 계측의 영향은 남으므로 커널이나 드라이버의 특정 결함으로 확정할 수 없다. 결과와 감시 기록은 `narrowconvpre-*`에 있다.

그중 편향만 남은 True 실행의 합성곱 직전 복제 입력과 복제 가중치를 이용해 2D 합성곱을 같은 GPU에서 독립 재생했다. 시드로 재생성한 편향을 사용하고 True·False 각각 9회 실행한 결과 모두 유한하고 원래 False 출력과 정확히 일치했으며 편향만 남은 원래 True 출력과는 달랐다. 같은 보존 값으로 단독 실행하면 합성곱 기여가 계산된다는 관측이지만, 본 실행의 실제 메모리 주소·할당 이력·비동기 상태와 연산 순간의 입력·가중치 상태는 복원하지 못한다. 따라서 차이를 일으킨 커널·할당기·드라이버의 특정 결함으로 확정하지 않는다. 결과와 감시 기록은 `convprecandidate-*`에 있다.

진단용으로 같은 축소 모델의 해당 2D 합성곱 편향만 0으로 설정하고 입력·가중치 복제 계측을 수행한 세 쌍에서는, 복제된 주 입력과 가중치는 모두 설정 간 일치했지만 True 첫 청크 합성곱 출력은 3/3회 전부 0이었다(각 4,632,576개). False 출력은 세 쌍 모두 달랐다. True 최종 잠재값은 1회 유한·2회 비유한이었다. 편향을 제거해도 관찰된 합성곱 기여 소실 형태가 남지만, 이 변경은 모델과 명령·할당 이력을 바꾸는 합성 실험이다. 입력·가중치가 실제 커널에 읽힌 시점과 버퍼 상태를 증명하지 못하므로 특정 커널·드라이버 결함을 확정하거나 운영 코드에 편향 변경을 적용하지 않는다. 결과와 감시 기록은 `narrowzerobias-*`에 있다.

동일한 편향 0·입력과 가중치 복제 계측에 합성곱 호출 직전 전장치 동기화를 추가한 별도 세 쌍에서는 첫 청크 합성곱 출력이 모두 False와 정확히 일치해 위 전체 0 현상이 관찰되지 않았다. 그러나 True 최종 잠재값은 세 쌍 모두 유한하면서 False와 달랐다. 동기화는 모든 선행 GPU 작업뿐 아니라 할당·재사용·타이밍을 바꾸므로 어느 의존성이나 연산이 원인인지 결정하지 못하고 전체 수치 정확성도 보장하지 않는다. 운영 코드에는 이 진단 동기화를 적용하지 않았다. 결과와 감시 기록은 `narrowsync-*`에 있다.

전장치 동기화 대신 합성곱 직전 현재 스트림만 동기화한 별도 세 쌍에서도 첫 청크 합성곱 출력은 모두 False와 정확히 일치했지만, 최종 잠재값은 세 쌍 모두 유한하면서 False와 달랐다. 이 비교는 해당 계측 조건에서 현재 스트림 대기만으로도 관찰된 전체 0 현상이 나타나지 않았음을 보여주지만, 대기가 호스트 타이밍과 할당 재사용에도 영향을 주므로 특정 스트림 의존성 결함을 입증하지 않는다. 다른 GPU 스트림·드라이버 작업의 상태도 측정하지 않았다. 결과와 감시 기록은 `narrowstream-*`에 있다.

같은 위치에 GPU 동기화 없이 호스트 `sleep(0.01)`만 추가한 세 쌍도 첫 청크 합성곱 출력은 모두 False와 일치했다. 그러나 True 최종 잠재값은 2회 유한하면서 False와 다르고 1회 비유한이었다. 호스트 지연 중 GPU 작업이 완료됐는지 측정하지 않았으며, 지연과 동기화 모두 호스트 제출·할당 타이밍을 바꾸므로 두 방식이 같은 원리로 작동했다고 결론 내릴 수 없다. 진단용 지연을 운영에 적용하지 않는다. 결과와 감시 기록은 `narrowdelay-*`에 있다.

이 중 첫 쌍의 True 실행에서 공간 축소 전에 복제한 입력과 같은 시드로 재생성한 가중치를 사용해 `WanResample`을 단독 재생했다. True·False 각각 9/9회 모두 유한했고 해당 쌍의 False 출력과 정확히 일치했으나 True 보존 출력과는 평균 절대 차이 약 0.103이었다. 독립 재생은 원래 GPU 주소·할당 이력과 비동기 상태를 복원하지 않았고, 원래 실행 중 입력 복사와 실제 소비 시점 사이의 메모리 안정성도 완전히 입증하지 못한다. 따라서 합성 입력 값과 가중치만으로는 관찰된 출력 차이를 재현하지 못했으나, 특정 연산 또는 메모리 구성요소의 결함으로 단정하지 않는다. 결과와 감시 기록은 `resamplecopy-*`에 있다.

그 차이 실행의 보존된 동일 첫 청크 입력과 시드 42로 재생성한 `WanResample` 가중치를 사용해 공간 축소만 같은 GPU에서 독립 실행했다. True·False 각각 독립 프로세스 3개에서 3회씩, 총 18회가 유한했고 모두 보존된 False 출력과 정확히 일치했지만 보존된 True 출력과는 평균 절대 차이 약 0.103이었다. 독립 재생은 모델 전체의 원래 GPU 주소·선행 할당 이력·비동기 상태를 재현하지 않는다. 또한 보존 입력은 해당 실행에서 사전 복제하지 않은 참조여서 실제 연산 순간과 완전히 동일했다는 증거는 아니다. 따라서 이 특정 수치 차이는 단독 입력과 가중치만으로 재현되지 않았지만 원래 실행의 부정확한 연산 또는 보존 시점 문제를 구별하지 못한다. 결과와 감시 기록은 `resamplereplay-*`에 있다.

같은 합성 모델에서 실제 `_encode` 순서에 맞춰 첫 청크 인코더, 두 번째 청크 인코더, 결합, `quant_conv`의 유한값을 지연 수집한 세 쌍에서는 True 3/3회 첫 인코더 출력은 유한하고 두 번째 인코더 출력부터 비유한이었다. 결합과 `quant_conv` 결과도 비유한이었으며 False는 모든 단계가 유한했다. 즉 이 합성 실행의 최상위 관측 경계도 실제 모델 실험처럼 결합·`quant_conv` 이전이다. 유한값 검사 커널과 단계 참조가 실행 상태를 바꾸므로 내부 최초 연산이나 실제 모델과의 동일 원인은 확정하지 않는다. 결과와 감시 기록은 `synthstage-*`에 있다.

별도 합성 실행에서 `down_blocks.2`와 `.3` 출력을 참조로 유지한 세 쌍은 True 3/3회 두 번째 청크의 `.2` 출력이 유한하고 `.3` 출력이 비유한이었다. False는 두 블록과 최종 인코더 출력이 모두 유한했다. 다만 True 세 번째 실행은 첫 청크의 두 블록 출력이 유한했음에도 첫 인코더 최종 출력이 비유한이어서, 두 번째 청크 `.3`이 전체 실행의 최초 비정상 연산이라는 뜻은 아니다. 두 출력 참조와 검사로 메모리 상태가 바뀌며 실제 모델과 동일한 결함이라는 입증도 아니다. 결과와 감시 기록은 `synthblocks-*`에 있다.

합성 모델의 두 번째 청크 `.3` 블록 직전에 주 입력·시간 캐시·무작위 파라미터를 GPU 복제로 보존하고 블록 출력도 저장한 세 쌍에서는 True 2회에 보존 입력·캐시·파라미터가 모두 유한하지만 블록 출력이 비유한이었다. True 나머지 1회와 False 3회는 최종 출력이 유한했다. 별도 복제와 참조가 메모리 상태를 바꾸므로 전체 실행의 최초 비정상 연산이나 복사 시점의 동시성 문제를 확정하지 않는다. 두 실패 후보는 모델·영상 파일 없이 생성됐으며 `synth-block3-2220545.safetensors`, `synth-block3-2221859.safetensors`에 보존했다. 결과와 감시 기록은 `synthcapture-*`에 있다.

첫 번째 합성 실패 후보의 보존 입력·두 캐시·파라미터와 기록된 stride를 GPU에서 복원해 블록만 독립 실행했다. True·False 각각 독립 프로세스 3개에서 3회씩 호출한 결과 총 18회 모두 유한했다. 저장된 실패 출력 자체는 비유한이다. 이 후보의 값과 기록된 stride만으로는 독립 재생에서 비유한 출력이 재현되지 않았고, 원래 GPU 주소·스토리지 오프셋·선행 할당 이력과 비동기 상태는 복원하지 않았다. 따라서 단독 블록이 일반적으로 정상이라는 결론이나 특정 메모리 결함의 증거는 아니다. 결과와 감시 기록은 `synthreplay-*`에 있다.

모델 파일 없는 동일 기본 구조·시드·0 입력의 공간 크기를 `[1,3,5,232,416]`으로 줄여 세 쌍을 비교했다. False는 3/3회 유한했고 True는 3회 중 2회 두 번째 잠재 프레임 24,128개가 NaN, 1회 유한했다. 원래 공간 크기보다 작은 입력에서도 문제가 관찰됐으나 반복 안정성이 낮아졌고, 입력 크기 변경은 메모리 할당·커널 선택 등도 바꾸므로 원인이나 임계 크기는 확정할 수 없다. 결과와 감시 기록은 `halfsize-*`에 있다.

공간 크기는 원래대로 두고 프레임 수만 1로 줄인 모델 파일 없는 0 입력 `[1,3,1,464,832]` 세 쌍에서는 False가 3/3회 유한했고 True는 2회 유한·1회 NaN 112개였다. 단일 encoder 청크만 사용하는 별도 조건에서도 NaN이 관찰됐으므로 재현에 반드시 두 번째 시간 청크가 필요한 것은 아니다. 다만 1/3회 관측이며 입력 형상과 할당 이력이 달라 5프레임 실패와 같은 최초 연산이나 원인을 증명하지 않는다. 결과와 감시 기록은 `oneframe-*`에 있다.

차이가 난 `latentnorminput-1-true_delay`의 호출 기록에서는 첫 블록의 캐시 clone이 26·27번째, 진단용 10ms 지연 대상은 뒤쪽 블록의 30번째 clone이었다. 즉 Python 측 명령 제출 순서에서 관찰한 초기 블록 경계는 지연 코드보다 앞선다. 그러나 GPU는 비동기로 실행되므로 그 경계의 복사·연산이 실제로 호스트 지연 전에 끝났다고 단정할 수 없으며, 이 기록만으로 지연과 초기 수치 차이의 인과관계를 결정하지 못한다.

후속 세 쌍에서는 첫 블록의 두 번째 정규화 입력 복사 뒤 같은 GPU 스트림에 이벤트를 기록하고 30번째 clone의 10ms 지연 전후에 비차단 조회했다. True 지연 세 실행 모두 해당 이벤트는 지연 전부터 완료 상태였지만, 이 계측 실행들에서는 보존된 정규화 입력과 합성곱 경계가 False와 일치했고 최종 잠재값만 유한한 값으로 달랐다. 따라서 이 실행에서 초기 입력 복사가 지연 전에 완료됐다는 것은 확인했지만, 초기 입력 차이가 실제 발생한 이전 실행의 완료 시점은 여전히 알 수 없다. 이벤트 자체가 타이밍에 영향을 줄 수 있으며 다른 스트림의 작업 상태도 대변하지 않는다. 비공개 결과와 감시 기록은 `latentboundaryevent-*`에 있다.

이 차이 실행에서 사용한 실제 원본 영상의 두 번째 청크와 첫 프레임을 각각 encoder `conv_in`의 주 입력과 시간 캐시로 구성하고 고정 가중치로 해당 합성곱을 같은 GPU에서 독립 재생했다. False·True 할당기 각각 독립 프로세스 3개에서 3회씩, 총 18회 결과는 모두 유한하고 False 실행에서 보존한 `norm1` 입력과 비트 단위로 일치했다. 차이가 났던 True 지연 실행의 보존 `norm1` 입력과는 모든 재생이 최대 절대 차이 9.75, 평균 약 0.161이었다. 모델 코드상 첫 청크의 시간 캐시가 첫 프레임이므로 이를 재구성한 실험이지만, 차이 실행의 `conv_in` 호출 당시 캐시를 직접 보존한 것은 아니며 GPU 주소·할당 이력·비동기 상태도 재현하지 않았다. 따라서 그 실행에서 실제 호출 입력·캐시·합성곱·후속 보존 복사 중 어디가 최초로 달라졌는지는 여전히 미확정이다. 결과와 감시 기록은 `encoderreplay-*`에 있다.

별도 세 쌍에서 encoder `conv_in` 호출의 주 입력·시간 캐시까지 GPU 복사해 보존한 결과, 두 호출에서 저장된 해당 입력·캐시와 후속 정규화 입력·`conv1` 경계가 모두 False와 True 지연 간 일치했다. 그럼에도 True 지연 최종 잠재값은 세 번 모두 유한하지만 False와 달랐다. 따라서 이 계측 조건에서는 앞선 정규화 입력 차이가 재현되지 않았고, 추가 복사의 할당 및 실행 순서 영향 때문에 앞선 실행에서 encoder `conv_in`이 최초 차이를 만들었다고 추론할 수 없다. 비공개 결과와 감시 기록은 `latentencoderinput-*`에 있다.

위 입력 보존 세 쌍의 파일을 원본 영상 텐서와 직접 대조했다. False·True 지연 각 세 실행 모두 첫 호출 주 입력은 원본 첫 프레임, 두 번째 호출 주 입력은 원본의 다음 네 프레임, 두 번째 호출 캐시는 원본 첫 프레임과 비트 단위로 일치하고 모두 유한했다. 이는 앞선 독립 입력 합성곱 재생에서 캐시를 원본 첫 프레임으로 구성한 방식이 이 여섯 계측 실행과 일치함을 확인한다. 정규화 입력 차이가 난 별도 실행의 당시 캐시까지 동일했다는 증거는 아니다.

또 다른 세 쌍에서는 encoder `conv_in` 출력 참조와 첫 `norm1` 입력의 GPU 복사본을 같은 실행에서 보유했다. 각 실행에서 합성곱 두 번째 출력과 정규화 입력 복사본이 정확히 일치했고, 두 경계 모두 세 쌍에서 False와 True 지연 간에도 일치했다. True 지연의 최종 잠재값은 두 번 비유한, 한 번 유한하지만 False와 달랐다. 이 계측 조건에서는 합성곱 출력과 보존 복사 사이의 차이가 관찰되지 않았지만, 출력을 참조해 수명을 연장했으므로 앞서 보존값이 달랐던 다른 실행의 복사 정확성이나 최초 원인 연산은 확정하지 못한다. 비공개 결과와 감시 기록은 `latentencoderout-*`에 있다.

같은 조건에 첫 블록 `norm1` 출력 참조를 추가한 별도 세 쌍에서는 두 호출의 `norm1` 출력, 합성곱 입력·캐시·출력이 모두 설정 간 일치했다. 그럼에도 True 지연의 최종 잠재값은 2회 비유한, 1회 유한하지만 False와 달랐다. 이전 실험에서 입력 차이가 난 실행과는 별도이며 정규화 출력 보유가 텐서 수명과 타이밍을 바꾸므로 이전 차이가 발생하기 시작한 정확한 연산을 판정하지 못한다. 비공개 결과와 감시 기록은 `latentnorm-*`에 있다.

이 중 False 실행에서 보존한 첫 블록 두 번째 `conv1`의 유한한 주 입력·캐시와 고정 모델 가중치를 이용해 합성곱만 같은 GPU에서 독립 재생했다. 각 할당기 설정별 독립 프로세스 3개에서 각 3회 호출한 결과, True와 False 모두 9/9회 유한했고 보존된 False 합성곱 출력과 비트 단위로 일치했다. 입력은 파일에 저장된 연속 텐서이며 독립 재생에서 GPU 가상주소·선행 할당 이력·비동기 실행 상태는 원래와 다르다. 이는 해당 입력과 단독 연산만으로는 차이가 재현되지 않았다는 결과다. 앞서 수치 차이가 난 실행의 입력을 보존한 것은 아니므로 그 차이의 직접 원인을 배제하거나 단독 연산의 일반적인 정확성을 증명하지 않는다. 결과와 감시 기록은 `firstreplay-*`에 있다.

보존된 False 결과를 오프라인에서 재검토한 결과, 위 다섯 가지 중간 출력 참조 방식 각각에서 세 독립 실행의 저장된 모든 중간 출력과 최종 잠재값이 비트 단위로 일치했다. 또한 중간 출력을 보유하지 않은 기존 `latentcompare`와 다섯 참조 방식의 최종 잠재값도 서로 일치했다. 동일 GPU·입력·소프트웨어·BF16 조건에서 기존 완화의 재현성을 뒷받침하지만, 독립적인 고정밀 정답과의 일치나 다른 입력·기기에서의 정확성을 입증하지는 않는다.

현재 워커의 할당기 환경변수 우선순위, VAE math SDPA 적용 및 예외 후 복원, 스케줄러·출력 프레임의 비유한 값 거부를 포함하는 `tools.review.tests.test_wan_animate2_generation` 단위 테스트 10개를 다시 실행해 모두 통과했다. 이는 정책과 오류 처리의 회귀 검사이며 실제 GPU의 전체 활성값 정확성이나 시각 품질을 증명하지 않는다.

재현의 환경변수 영향을 점검하기 위해 자식 프로세스에서 `AMD_`, `HSA_`, `HIP_`, `PYTORCH_`, `MIOPEN_`, `ROCR_` 접두사의 기존 환경 변수를 제거하고 `PYTORCH_ALLOC_CONF`만 True 또는 False로 설정해 동일 입력·BF16 VAE·math SDPA의 독립 실행을 세 쌍 비교했다. False는 3/3회 유한했고 True는 3/3회 두 번째 잠재 프레임의 96,512개가 NaN이었다. 동일한 프로세스 환경에서 지정된 접두사의 외부 설정이 필수 재현 조건은 아니라는 관측이며, 그 외 런타임·드라이버 설정이나 시스템 상태까지 같다는 증명은 아니다. 결과와 GPU 감시 기록은 `cleanenv-*`에 있다.

워커 소스의 설정 호출은 이 파일이 직접 가져오는 모델·PyTorch 의존성보다 앞에 있다. 다만 이미 GPU가 초기화된 다른 Python 프로세스에 이 모듈을 뒤늦게 가져오는 경우까지 설정이 소급 적용된다는 뜻은 아니다. 또한 유한값 검사는 NaN·무한대가 아닌 잘못된 유한값을 검출할 수 없으므로 위 수치 비교를 대체하지 못한다. 운영 완화의 의미는 확인된 실행 조건에서 `expandable_segments:True`를 사용하지 않도록 하는 것이며 모든 하드웨어와 입력에 대한 정확성 보증은 아니다.

65프레임 완료 작업의 참조 이미지와 출력 프레임 0·8·16·24·32·40·48·56·64를 한 화면에서 다시 육안 확인했다. 선택한 프레임에서는 갈색 머리와 회색 상의·짙은 하의가 대체로 유지되고 앉기와 일어서기 동작을 확인할 수 있었다. 다만 일부 자세와 손·팔의 세부 표현은 참조와 차이가 있고, 9개 표본의 축소 이미지 검토이므로 나머지 프레임의 시간적 깜박임·세부 품질·모션 충실도나 사용자 승인까지 보증하지 않는다. 검토용 비공개 조합 이미지는 임시 경로 `quality-contact.jpg`에 보관한다.

추가로 65개 출력 프레임을 모두 작은 축소 이미지로 나열해 확인했다. 모든 칸에 인물이 나타나고 서기·앉기·다시 서기 순서가 이어지며 전체 화면이 검게 되거나 캐릭터가 완전히 사라진 칸은 보이지 않았다. 이 크기의 정지 이미지 검토로 세부 얼굴·손 품질과 재생 시 깜박임을 판정할 수는 없고, 사용자의 품질 승인을 대신하지 않는다. 조합 이미지는 비공개 `all65-contact.jpg`에 보관한다.

5프레임·2스텝 짧은 완료 작업은 전체 5개 출력 프레임을 축소 조합해 육안 확인했다. 확인한 이미지에서 캐릭터와 의상이 표시되고 전면이 흰색인 정상 영상 형태였으며 전면 검정 화면이나 명백한 출력 누락은 보이지 않았다. 2스텝·5프레임 결과이므로 긴 동작 품질이나 프레임 간 미세한 깜박임·사용자 품질 승인으로 확대하지 않는다. 비공개 조합은 `short-quality-contact.jpg`에 있다.

대표 길이 실행 시간 07:34:07~08:53:26의 접근 가능한 사용자 저널 983행과 커널 저널 3행을 추가 확인했다. GNOME Shell 충돌·Xorg 치명 오류 및 AMDGPU 재설정·링 시간 초과·GPU fault에 해당하는 검색 결과는 없었다. 저널의 접근 범위와 검색 표현에 제한이 있고, 기존 모니터도 화면 응답성을 지속 측정하지 않았으므로 이 확인은 그 시간 동안 화면이 정상적으로 표시됐다는 직접적인 증명은 아니다.

추가로 축소 합성 모델의 공간 축소 합성곱 입력을 GPU에 복사한 직후 현재 스트림에 이벤트를 기록하고, 호스트에서 10ms 대기하기 전후의 완료 상태를 조회한 세 쌍을 비교했다. False·True 양쪽의 두 청크 모두 이벤트는 대기 전후 미완료였으며, True에서는 3회 중 2회 첫 합성곱 출력 전체가 0이었고 나머지 1회는 False와 일치했다. 편향을 0으로 바꾼 진단 조건이며 최종 잠재값은 모두 유한했지만 설정 간 값은 달랐다. 이벤트는 앞선 스트림 작업 전체의 완료 여부만 나타내고 개별 입력 복사나 합성곱의 실행 시점은 나타내지 않는다. 이벤트 추가 자체도 실행에 영향을 줄 수 있으므로 대기가 문제를 해결한다거나 최초 원인이 특정 커널이라고 판단할 수 없다. 비공개 결과와 감시 기록은 `narrowdelayevent-*`에 있다.
