# ROCm NaN 사례집

2026-11-15 기준. 실행 기술 기록이며 모델·입력 텐서·영상·로그는 Git에 등록하지 않는다. 공통 절차는 [ROCm 추론 가이드](rocm-inference.md)를 따른다. 커밋 제목이 아니라 실제 diff와 검증 기록으로 해결 범위를 판단한다.

## 운영 전환 맥락

이 작업들은 최근 며칠 전까지 CUDA에서 정상 동작했으며, ROCm으로 전환한 후 이 사례집의 문제가 관측됐다. CUDA 운영 중에는 해당 NaN 문제를 경험하지 못했다. 따라서 전환으로 달라진 GPU·커널·라이브러리와 실행 환경은 우선 조사 대상이다. 다만 기존 운영 경험만으로 CUDA와 ROCm에서 모든 입력·모델 리비전·설정이 동일했거나 특정 구성 요소가 원인임이 증명되지는 않는다. 사례별 최초 비유한 경계와 동일 입력 재현을 통해 원인을 분리한다.

## HeartMuLa — 커널 경로 한정 우회

근거: Git `68a3f7bb` (`fix(music): ROCm 음악 생성과 재생 안정화`), `generators/music/heartmula/runtime.py`, 당시 AGENTS.md 변경.

기본 SDPA와 같은 입력의 수학 SDPA 결과가 달랐으므로 코드북 디코더에만 수학 경로를 적용했다. 메타 모델 로딩 이후 비영속 RoPE 버퍼 초기화와 생성 점수 유한값 검사를 보강했다. 할당 옵션을 False로 해도 NaN이 관측됐으므로 메모리 할당 설정을 공통 해결책으로 삼지 않는다. 모든 음악 모델이나 다른 GPU의 검증으로 확대하지 않는다.

## Wan Fun Control — VAE 조건과 할당 설정

근거: Git `a7d11326` (`fix: Wan Fun ROCm VAE 수치 안정성 개선`), `generators/wan_fun/worker.py`와 관련 테스트.

VAE 인코딩 직후와 모델 해제 이후 조건 텐서의 지문·유한 여부를 기록한다. 일반 GPU VAE를 FP32로 사용하고 디코딩 시 다시 적재하며, `PYTORCH_ALLOC_CONF=expandable_segments:False`를 초기화 전에 설정하고 이전 환경변수의 중복 재정의를 제거했다. 여러 조치가 함께 포함돼 단일 변경의 인과를 증명하지는 않는다. OOM을 CPU 추론이나 자동 타일 대체로 숨기지 않는다.

주의: `1c427908`의 제목에도 수치 안정성이 있지만 실제 diff는 모션 프레임 배분·UI·테스트다. VAE 수정 근거는 `a7d11326`이다.

## VACE — 지연과 NaN을 구분

근거: Git `ec21e9a1`, `generators/wan_vace/numerical_guard.py`, `official_runtime.py`, `official_full_precision.py`, `workflows/rocm-inference.md`.

실제 65프레임 BF16 self-attention 형상은 `[1,40,28080,128]`이었다. 연속 배치 적용 후 첫 호출은 복사 포함 약 0.961초, 첫 스텝 약 177초였고 이전 실행의 첫 스텝은 약 618초였다. 조건과 프로파일링 차이가 있어 엄밀한 단일 변수 벤치마크로 취급하지 않는다. 해당 실행은 20스텝을 완료했고 어텐션 Q·K·V 및 출력 3,840회, 전문가 출력·스텝 잠재값 각 20회가 유한했다. 긴 실행과 사용률 100%만으로 NaN을 추정하지 않는다. 유한값 통과와 영상 품질 승인은 별도다.

## Animate2 — 어텐션 이전에 손상된 입력

환경: Radeon 8060S, PyTorch `2.13.0+rocm10.0.0`, HIP `7.15.26333`, BF16, 5프레임·2스텝·시드 42. 환경 문자열은 당시 실행값이며 호환성 인증을 의미하지 않는다.

- 실패 작업 `2026-11-15_21-52-37-4228cda4`: 첫 참조 추출 호출, 마스크 없음, Q/K/V 각각 `[1,3016,40,128]`. 각각 15,441,920개 중 7,720,960개가 NaN. 토큰 0–1507은 유한하고 1508–3015는 전부 NaN이었다.
- 실제 Q/K/V·출력·마스크 행을 해당 시도의 `attention-input.safetensors`에 보존했다. 첫 유한 Q 행과 전체 K/V를 같은 GPU에서 재생했을 때 기본·수학 SDPA 모두 128개 NaN을 반환했다. 커널 교체로 비정상 입력이 복구되지 않는다.
- 정상 비교 작업 `2026-11-15_21-56-28-bb041bf8`: Flex Q `[1,4608,40,128]`, K/V `[1,7680,40,128]`. `attention-sample.safetensors`와 JSON에 블록 마스크·함수·클로저를 보존했다. 첫 유효 행에서 기본·수학 SDPA 모두 유한했고 Flex 대비 최대 절대 차이는 각각 0.0009765625, 0.00390625였다. 한 행의 비교이며 전체 커널 정확도 검증은 아니다.
- 후속 VAE·첫 블록 계측에서는 NaN을 다시 포착하지 못했다. VAE, 정규화, 투영 중 최초 발생 지점은 아직 미확인이다. 계측 동기화가 실행 조건을 바꿀 가능성도 별도 검증해야 한다.
- VAE 출력·스케줄러 예측/입출력·최종 프레임을 검사해 손상 결과를 완료로 저장하지 않도록 했다. 적용 후 `2026-11-15_22-04-19-061c2fa1`은 5프레임·2스텝을 약 93.3초에 완료했다. 해당 실행에서 GPU 오류는 관측되지 않았다. 짧은 성공 한 번으로 간헐적 NaN이나 이전 그래픽 큐 타임아웃이 해결됐다고 선언하지 않는다.

## 외부 사례와 비교

2026-11-15 확인. 아래는 외부 사용자의 보고이며, 이 저장소에서 재현하거나 동일 원인임을 확인한 사례가 아니다. CUDA와의 비교 여부도 구분한다.

- **ESMFold2 어텐션** — AMD MI300A, ROCm 6.2, PyTorch 2.5에서 어텐션 이후 NaN이 발생했고, 보고자는 Flash·memory-efficient SDPA를 끄고 수학 SDPA를 사용해 우회했다고 기록했다. ROCm 6.4와 PyTorch 2.9 조합에서도 해결됐다고 보고했다. HeartMuLa의 경로 한정 우회와 유사하지만 동일 커널 결함을 증명하지 않는다. 보고자의 ROCm 한정 주장과 별개로 이 사례집에서 CUDA 동일 입력 비교는 확인하지 않았다. [ESMFold2 이슈 #322](https://github.com/Biohub/esm/issues/322)
- **긴 시퀀스의 BF16 비전 어텐션** — gfx1100, PyTorch 2.9.1 ROCm 빌드에서 약 14,200~14,688 토큰 이상일 때 NaN과 비결정적 출력이 발생했다는 보고다. 작성자는 NVIDIA GPU가 없어 CUDA 직접 비교를 하지 못했다고 명시했다. 형상과 길이를 재현 조건에 포함할 근거이지 VACE의 지연을 NaN으로 판정할 근거는 아니다. [ROCm 이슈 #6416](https://github.com/ROCm/legacy-rocm-build/issues/6416)
- **큰 입력의 VAE 디코더** — RX 7800M, ROCm 환경의 Stable Diffusion 업스케일링에서 큰 입력에 대해 VAE 출력의 NaN·Inf가 보고됐다. MIOpen/HIP 관련성은 작성자의 추정이며 최초 원인과 CUDA 비교는 확정되지 않았다. Wan Fun의 VAE 조건값 검사를 뒷받침하는 참고 사례이지 FP32의 보편적 해결을 증명하지 않는다. [ROCm 라이브러리 이슈 #1571](https://github.com/ROCm/rocm-libraries/issues/1571)
- **동적 VRAM과 앞선 단계의 손상** — ComfyUI의 AMD ROCm 사용자는 검은 이미지의 원인을 처음 VAE로 추정했다가 계측 후 샘플러 출력과 일부 캐시 가중치에 이미 NaN이 있었다고 정정했다. 페이지 재사용 관련 설명은 보고자의 가설이다. Animate2에서도 최종 손상 위치가 아닌 최초 비유한 경계를 찾아야 한다는 참고 사례이며, 동일 메모리 문제가 확인된 것은 아니다. [ComfyUI 이슈 #15452](https://github.com/Comfy-Org/ComfyUI/issues/15452)

PyTorch는 ROCm Flash Attention에서 AOTriton과 Composable Kernel 백엔드 선택을 제공하며 실제 사용 가능 여부는 빌드에 따른다. GPU·버전·형상에 따라 선택 경로가 달라질 수 있으므로 CUDA에서 관측되지 않은 이유를 확인하려면 동일 입력과 설정에서 실제 경로와 결과를 비교해야 한다. [PyTorch 백엔드 구현](https://github.com/pytorch/pytorch/blob/main/torch/backends/cuda/__init__.py)

### Animate2 Wan VAE 실측

Radeon 8060S `gfx1151`, PyTorch `2.13.0+rocm10.0.0`, HIP `7.15.26333`, BF16, 시드 42에서 Animate2의 고정 VAE 가중치·런타임을 사용했다. 64×64 합성 단일 프레임을 인코딩·디코딩하며 VAE 내부 SDPA의 실제 Q/K/V를 가로채 같은 텐서와 의미로 수학 경로 1회, 기본 경로 3회를 비교했다. 진단 코드는 로컬 `.tmp/rocm-vae-check/check.py`에 있으며 생성 입력은 실제 사용자 영상이 아니다.

인코더와 디코더 양쪽의 Q/K/V는 `[1, 1, 64, 384]`, stride `[73728, 73728, 1152, 1]`이고 모두 유한했다. 기본 출력 세 번과 수학 출력도 유한했지만, 기본 첫 출력의 수학 출력 대비 평균 절대 오차는 각각 **2.10054**, **0.23022**, 기준 평균 절대값 대비 비율은 **6.21445**, **1.01458**이었다. 각 경계에서 동일 입력의 기본 출력 3회는 서로 일치하지 않았다. 인코딩·디코딩 최종 텐서의 유한값 검사도 통과했다. 디코더 입력은 기본 경로로 얻은 인코딩 결과이므로 독립적인 전체 VAE 정확도 비교는 아니다.

별도 합성 BF16 Q/K/V `[1,1,1024,384]`, `[1,1,4096,384]`도 모두 유한했지만 기본 첫 출력의 수학 대비 평균 절대 오차는 각각 0.24160, 0.02107, 상대 평균 오차는 5.94883, 1.0이었다. 동일 입력의 기본 출력 3회는 일치하지 않았다. 따라서 **우리 Animate2 VAE의 해당 실행에서도 유한하지만 크게 다른 기본 SDPA 결과가 재현됐다.** 이는 외부 사례와 같은 증상이지 내부 커널의 동일 근본 원인이나 다른 Wan 구현·모든 형상의 실패를 증명하지 않는다. 실제 사용자 입력·대표 해상도, CUDA 비교, 선택된 정확한 커널과 해당 빌드의 수정 포함 여부는 미검증이다. 수학 경로를 적용한 전체 생성의 품질·성능·회귀 검증도 아직 수행하지 않았다.

### Animate2 VAE 한정 수학 SDPA 적용 후 검증

VAE 인코딩·디코딩에만 수학 SDPA를 선택하도록 우회했으며 Transformer 어텐션은 기존 경로를 유지한다. 관련 범위·예외 복구 단위 검사 7건은 통과했다. 실사용 입력과 같은 참조 이미지·동작 영상, 832×480, 5프레임·2스텝·시드 42로 공용 대기열에서 실행한 작업 `2026-11-15_22-44-40-e6540e10`은 유한값 검사를 통과하고 완료됐다. 결과 기록에서 VAE 수학 경로를 확인했다. 총 약 93.22초, 5초 간격 샘플 기준 작업자 GPU 메모리 피크 46,777 MiB였다. 이전 같은 요청의 완료 실행은 약 93.32초, 피크 46,771 MiB였다. 실행별 환경·측정 오차가 있어 이 수치는 엄밀한 성능 벤치마크가 아니다.

**품질 실패:** 생성된 5개 프레임을 시각 검수한 결과 심한 색상·배경 손상과 인물 외형 불일치가 관측됐다. 이전 완료 실행의 첫 프레임은 참조 인물과 유사하게 보였으나, 실행 간 비교만으로 수학 SDPA 변경이 품질 차이의 원인임을 입증할 수 없다. ## Wan VAE 공통 경로 조사

## 재발 방지와 신규 사례 기록 기준

1. 입력 전처리·단위·dtype·shape·stride·마스크·캐시·시드와 GPU/ROCm/PyTorch/모델 리비전, 할당 설정을 기록한다.
2. VAE/인코더 → 모델 입력 → Q/K/V → 어텐션 출력 → 스케줄러 → 최종 결과에서 최초 비유한 경계를 찾는다. 발견 시 원본을 보존하고 실패 처리한다. NaN 치환으로 통과시키지 않는다.
3. 유한한 입력에서만 커널 원인을 분리한다. 동일 마스크·길이·scale·causal·dropout 의미로 GPU 기본/수학 경로를 비교한다. 패딩의 전부 가려진 행과 실제 사용 행을 구분한다.
4. 한 번에 하나의 설정을 바꾸고 반복한다. 버전·커널·메모리 배치 변경 후 짧은 재현과 대표 길이 생성, 오차·메모리·속도·품질을 확인한다. 다른 모델의 해결책을 일괄 적용하지 않는다.
5. 사례 상태를 `관측`, `원인 분리`, `우회 적용`, `회귀 검증`, `미해결`로 명확히 적는다. 커밋 해시·실패/검증 작업 ID·증거 파일명·검증하지 않은 조건을 남긴다. 재현 데이터는 작업 저장소에 보관하며 존재·해시를 확인한 범위만 보고한다.

- [PyTorch 이슈 #189849](https://github.com/pytorch/pytorch/issues/189849): 같은 GPU의 D512 Flash SDPA가 오류 없이 잘못된 유한값을 출력한 별도 재현과 gfx11의 D256 초과 제한 수정 이력이다. D512 보고를 D384의 직접적인 재현으로 취급하지 않으며, NaN 검사만으로 출력 정확도를 보장할 수 없음을 보여 준다.
- [ROCm TheRock 이슈 #6584](https://github.com/ROCm/TheRock/issues/6584): 동일 GPU에서 긴 비연속 SDPA 입력을 연속 배치로 복사하면 일부 형상의 실행 시간이 단축됐다는 성능 보고다. 짧은 입력이나 별도 GPU에서 복사 비용이 더 컸던 실험도 포함된다. 이는 로컬의 긴 참조 어텐션 개선과 방향이 같지만 Flex의 헤드 분할이나 모든 모델의 성능 개선을 보증하지 않는다.
- [PyTorch 수치 정확도 문서](https://pytorch.org/docs/stable/notes/numerical_accuracy.html)는 math SDPA가 일반적으로 FP16/BF16 입력을 FP32 중간 연산으로 처리하여 정확도를 높이는 대신 메모리와 시간 비용이 증가할 수 있다고 설명한다. 실제 설치 버전·선택된 백엔드와 플래그를 확인해야 하며 math 경로도 전체 생성 파이프라인의 정확성 보증은 아니다.

2026-11-16 경량 합성 재검증: Radeon 8060S, PyTorch `2.13.0+rocm10.0.0`, HIP `7.15.26333`에서 BF16 `[1,1,64,384]` Q/K/V를 같은 입력으로 재사용했다. Flash 사용 가능 판정은 `True`였다. math를 기준으로 기본 SDPA를 3회 실행한 결과 모두 유한했지만 평균 절대 오차는 각각 0.48309, 0.48117, 0.18796이고 기준 출력의 평균 절대값은 0.15586이었다. 최대 절대 오차는 4.41016, 4.20508, 1.40430이었다. 출력은 반복 간 달라졌다. 이 작은 합성 시험은 기본 경로가 해당 빌드에서 신뢰할 수 없음을 보이지만 실제 실행된 백엔드나 설치 빌드의 수정 포함 여부, 전체 NaN의 최초 원인을 확정하지 않는다. 강제 Flash 실행과 영상 생성은 하지 않았다. 기존 VAE 한정 math 우회를 유지한다.

### 2026-11-16 실제 실행 경로 및 VAE 입력 재생

- Radeon 8060S·PyTorch `2.13.0+rocm10.0.0`·HIP `7.15.26333`, BF16 `[1,1,64,D]`, 시드 42에서 프로파일러는 D256과 D384 모두 기본 경로의 `aten::_scaled_dot_product_flash_attention`과 `aten::_flash_attention_forward`를 기록했다. 이는 PyTorch 연산 경로 식별이며 하위 GPU 커널의 구현명까지 특정한 것은 아니다. D256 기본 출력 3회의 math 대비 평균 절대 오차는 모두 0.000192, 최대 0.003906이었다. D384는 평균 오차 0.48389·0.48523·약 9.57e24, 기준 출력 평균 절대값은 0.15586이었다. 세 출력 모두 유한했으나 반복 결과가 달랐다. 결과는 이 입력에 한정된다.
- 실제 기준 이미지 `85512daf8d77bb367f35bc5af13e5fe88b9d9c9a609d0151e13efd0500047aeb`를 128×128으로 축소해 운영 Animate2 VAE의 인코더와 디코더를 실행했다. 두 경계의 BF16 Q/K/V `[1,1,256,384]`를 `actual-vae-qkv.safetensors`로 보존했으며 SHA-256은 `74e26be5dcba58adb3920b75684581a3a408355feb3d1ea1c9d1481893884325`다. 기록은 `.tmp/test/rocm-sdpa-investigation/2026-11-16_10-36-46/`에 있다. 원본 해상도·전체 동영상 검증은 아니다.
- 운영 `install_animate_vae_math_attention` 적용 중 두 VAE 경계 모두 math 활성, Flash·efficient 비활성이었고 입력·인코딩·디코딩 출력은 유한했다. 보존한 실제 Q/K/V의 원래 stride `[294912,294912,1152,1]`를 GPU에 재구성해 반복하면 기본은 Flash 연산을 선택했다. 인코더 기준 출력의 평균 절대값 0.29047 대비 기본 출력의 평균 절대 오차는 0.82500·0.81695·0.81695였다. 디코더 기준 평균 절대값은 0.14903이고 기본 경로 오차는 약 1.06e29였다. 이 샘플에서는 출력 유한값 검사만으로 오차를 감지하지 못했다.
- GPU 커널의 내부 구현·실패 상태와 최초 NaN의 원인은 이 비교만으로 확인하지 못했다. 참조 VAE 인코딩·디코딩에서 math 경로를 유지하며 실제 생성의 나머지 수치 경계와 품질을 별도로 검증한다.
- 별도 동일 형상 GPU profiler에서 D256은 `attn_fwd.kd` GPU 커널이 기록됐지만 D384는 Flash ATen 연산이 반환됐음에도 GPU 커널 이벤트가 기록되지 않았다. 이는 지원되지 않는 경로가 연산을 실행하지 않고 반환했을 가능성과 양립하나, 프로파일러 이벤트 누락이나 내부 실패 상태를 배제한 증명은 아니다. Flash eligibility만으로 안전성을 판단하지 않는다.
- 운영 경로의 새 짧은 검증 `2026-11-16_10-39-31-59aa84eb`은 같은 참조·동작 입력, 832×480, 5프레임·2스텝·시드 42로 공용 대기열에서 완료됐다. 결과 기록은 ROCm·VAE math·가중치 오프로드 없음을 보였고 5개 PNG 디코딩에 성공했다. 표본 육안 확인에서 인물과 배경은 보였으나 2스텝 결과의 품질과 장시간 안정성은 승인하지 않았다. 기존 주요 경계 검사에서 비유한 값은 보고되지 않았으며 모든 중간 연산의 정확성에 대한 증거는 아니다.
