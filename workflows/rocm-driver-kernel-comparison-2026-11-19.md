# ROCm 메모리 재매핑 오류: Ubuntu 커널과 AMD 드라이버 비교

작성 기준: 2026-11-19. 시험 장비는 Ubuntu 26.04.1 LTS, AMD Ryzen AI Max+ PRO 395, Radeon 8060S (`gfx1151`)다. 이 문서의 Pass와 Fail은 **이 장비와 아래에 명시한 입력·반복에 대한 관측**이다. 모든 GPU나 모델의 장기 안정성을 뜻하지 않는다.

## 결론

Ubuntu 기본 `7.0.0-43-generic`의 내장 AMDGPU 드라이버에서 GPU 가상 주소를 다른 할당에 재사용하면 이전 할당 또는 새 할당의 값이 손상되는 현상이 재현됐다. PyTorch가 없는 HSA 진단에서도 나타났으며, Animate2 VAE에서는 `expandable_segments:True` 조건의 잠재값이 기준과 달라졌다. NaN이 없는 경우에도 값은 달라질 수 있다.

같은 Ubuntu 커널에서 실험한 **AMDGPU 31.70 모듈**, **TLB 펜스 백포트 모듈**과 별도 **Ubuntu 메인라인 7.4-rc3 비교 커널**은 아래 시험 범위에서 이 현상을 재현하지 않았다. 31.70의 TLB 호출을 실험적으로 제거하면 오류가 다시 발생했다. 다만 각 대안은 운영 지원과 검증 범위가 다르므로 통과 결과만으로 운영 교체를 권장하지 않는다.

> **커널 명칭 주의:** 실제 검증한 `7.4.0-070400rc3-generic`은 Ubuntu 정식 업데이트 커널이 아니라 Ubuntu가 제공하는 **상류 Linux 메인라인 시험 빌드**다. 7.3.5는 소스만 확인했으며 GPU에서 시험하지 않았다. 작성 시점 호스트의 APT 캐시에서 정식 generic 후보는 `7.0.0-43.43`, OEM 후보는 `7.0.0-1018.18`이었지만 저장소 정보는 변할 수 있다. [Ubuntu 메인라인 빌드 안내](https://canonical-kernel-docs.readthedocs-hosted.com/explanation/about-mainline-builds/)

## 판정 기준

- **HSA 재매핑 Pass:** 20MiB 할당을 해제·재매핑하고 이전 물리 할당의 별칭과 새 할당을 비교했을 때 불일치 바이트가 0이다. 같은 가상 주소 재사용과 별도 주소 대조를 구분한다.
- **VAE Pass:** 동일한 65프레임 입력의 잠재값 1,577,600개가 기준과 비트 단위로 일치하며 NaN·Inf가 없다. `False`/`True`는 PyTorch `expandable_segments` 설정이다.
- **전체 생성 Pass:** 동일 입력·시드, 832×480, 65프레임·20스텝 생성이 완료되고 검사한 VAE·스케줄러·최종 프레임에 NaN/Inf가 없으며 결과 PNG 65장 해시가 비교 기준과 일치한다. 모든 중간 텐서를 검사한 것은 아니다.
- **미검증:** 실행하지 않았거나 관측만으로 판정할 수 없는 항목이다. Fail과 구분한다.

## Ubuntu 정식 7.0: 어떤 동작이 실패하고 어떻게 통과했나

기본 드라이버의 최근 독립 진단에서는 **같은 GPU 가상 주소를 새 할당에 재사용한 경우** 이전 할당 불일치가 19/20회, 새 할당 불일치가 2/20회였다. 새 할당을 다른 주소에 매핑한 대조는 둘 다 0/20회였다. 따라서 단순한 모델 출력 이상보다 주소 재사용과 관련된 메모리 가시성 문제를 확인할 수 있다. 이 진단의 자세한 바이트 수는 로컬 결과 JSON에 남는다.

실제 VAE에서는 `True`의 두 잠재값이 기준과 달랐다. `False`는 해당 입력의 기준 결과를 생성했으며 운영 우회 설정이다. 다만 HSA 시험은 PyTorch를 사용하지 않기 때문에 `False` 설정이 드라이버 결함 자체를 고친다는 뜻은 아니다.

같은 7.0 커널의 격리 부팅에서 상류 TLB 펜스 수정의 **실험적 백포트**를 적용한 결과 HSA 두 조건이 20회씩 모두 일치했고, VAE `False`·`True` 각각 10회도 기준과 일치했다. 별도 전체 생성 `True` 1회는 약 5,974.5초가 걸렸고 기준 PNG 65장과 일치했다. 비교 커널과 시간 측정 조건이 완전히 통제되지 않아 이 시간 차이를 패치 성능 효과로 판단하지 않는다.

별도로 기본 7.0 소스에 compute TLB 호출만 추가한 **실험 모듈**에서도 HSA 두 조건 각각 20회와 VAE 설정별 10회가 통과했다. 심화 추적의 해제 구간에서는 하위 무효화 함수 반환과 링 펜스 대기 완료가 관찰됐다. 이 최소 개입은 비동기 갱신과 여러 XCC의 일반 처리가 완성되지 않아 운영 패치가 아니다.

## AMDGPU 31.70: 통과와 실패의 구분

시험한 것은 Ubuntu `7.0.0-43-generic`에 별도 빌드·서명해 격리 부팅으로 로드한 31.70 계열 모듈이다. 추출한 DKMS 패키지 버전은 `1:7.2.3.31700000-2428518.26.04`였다. **변경하지 않은 31.70 시험 모듈**에서는 HSA 재사용·대조 각 20회, VAE `False`·`True` 각 2회, `True` 전체 생성 1회가 위 기준을 통과했다. 전체 생성 시간은 6,046.960초였으며 단일 실행이다.

이 정상 모듈에서 해당 시험의 Fail은 관측되지 않았다. 다만 다른 입력, 반복 전체 생성, 장기 안정성, 모든 중간 텐서 및 일반 데스크톱 사용은 미검증이다. 시험 과정에서 텍스트 콘솔 출력에 `tty1` I/O 오류가 기록된 적이 있으나, 그것을 GPU 메모리 손상 Fail이나 31.70 고유 결함으로 단정할 근거는 없다.

**실험적으로 수정한 31.70**은 별개다. GEM VA 경로의 compute TLB 호출을 제거하면 HSA 재사용에서 이전 할당 19/20회·새 할당 3/20회가 불일치했고 다른 주소는 0/20회였다. 같은 변경의 VAE `True` 통합 시험은 10/10회 기준과 달랐으며 그중 1회에 NaN이 있었다. `False`는 10/10회 일치했다. 이는 변경하지 않은 31.70 배포 드라이버의 실패가 아니라 원인 분리를 위한 개입 결과다. TLB 호출 대신 약 170µs 지연만 둔 대조에서도 HSA 재사용 이전 할당이 15/20회 손상돼, 단순 지연은 해결책이 아니었다.

AMD의 [드라이버 저장소](https://repo.radeon.com/amdgpu/)에는 31.70 계열이 게시되어 있다. 다만 AMD의 [ROCm 호환성 표](https://rocm.docs.amd.com/projects/install-on-linux/en/latest/reference/system-requirements.html)는 Radeon 8060S가 포함된 지원 Ryzen APU에 대해 지원 Ubuntu의 **내장 커널 드라이버**를 명시한다. 따라서 이 장비의 31.70 격리 시험 통과를 AMD 지원 구성이나 일반 설치 권고로 해석하지 않는다. 현재 기본 시스템 모듈은 교체하지 않았다.

## Ubuntu 메인라인 7.4-rc3: 어디까지 통과했나

`7.4.0-070400rc3-generic`에서 같은 HSA 재현을 독립 프로세스 세 쌍으로 실행해 같은 주소와 다른 주소 각각 60회에서 불일치가 없었다. 65프레임 VAE `False`·`True` 각 2회도 기준과 일치했다. 전체 생성은 `False` 1회, `True` 1회 완료됐고 두 결과 PNG 65장 해시가 같았다. 검사한 경계에서 NaN·Inf 오류는 없었다.

이 시험 범위에서 해당 메모리 손상 Fail은 관찰되지 않았다. 장기 안정성, 다른 GPU·입력, 모든 중간 텐서 및 운영 지원은 미검증이다. 같은 GPU에서도 커널 전체와 부팅 상태가 달라졌으므로 7.4 시험만으로 특정 커밋 하나가 원인이라고 증명할 수 없다. Ubuntu는 [메인라인 빌드가 지원 대상이 아니고 보안 업데이트를 받지 않는 진단용 빌드](https://canonical-kernel-docs.readthedocs-hosted.com/explanation/about-mainline-builds/)라고 명시한다.

## 기존 실험에서 함께 확인한 경계

### VAE 손상과 어텐션 오류는 구분한다

기본 7.0의 실제 VAE 조사에서 첫 공간 축소 합성곱의 선택 위치에 필요한 96개 입력 채널과 출력 네 채널을 보존한 별도 계측에서는, False·True의 입력 표본은 같았지만 True 출력 네 값이 달랐고 최종 잠재값에 NaN이 있었다. 다른 계측에서는 출력 표본이 bias만 남은 형태도 관측됐다. 다만 표본 보존을 위한 GPU 할당·복사가 실행을 바꾸며, 합성곱 커널이 실제 읽은 전체 입력·가중치를 독립 검증하지 못했다. 이 결과를 합성곱 자체가 최초 결함이라는 증거로 쓰지 않는다.

초기 Animate2 조사에서는 잘못된 Q/K 입력을 보존한 뒤 기본·수학 SDPA 양쪽에서 NaN이 재현된 사례도 있었다. 이 경우 커널 교체만으로 비정상 입력이 복구되지 않는다. 별도로 gfx1151의 D384 Flash SDPA에서 **유한한 출력도 기준과 달랐던** 실험과 외부 이슈가 기록돼 있다. 두 증상이 항상 같은 원인이라는 증거는 없다. VAE 수학 SDPA, 할당기 설정, 입력의 유한성과 기준값 비교를 각각 확인한다. 세부 조건은 [ROCm NaN 사례집](rocm-nan-cases.md)을 따른다.

### 커널 추적에서 확인한 것과 확인하지 못한 것

7.4-rc3에서는 펜스 생성 반환과 작업자 객체를 연결한 별도 추적에서 151개가 생성 → 같은 객체의 작업자 진입 → 같은 PASID의 무효화 호출·정상 반환 → 작업자 반환으로 이어졌다. 이 숫자는 전체 관측이지 특정 해제 구간만의 반복 횟수가 아니다. 연결되지 않은 이벤트와 누락·객체 재사용 가능성이 있어 모든 호출의 관계나 물리 TLB 상태를 증명하지 않는다.

기본 7.0과 OEM 후보 모듈의 일부 BTF·역어셈블 비교에서는 조사 대상 상류 변경과 동일한 구조가 확인되지 않았다. OEM 커널은 부팅해 시험하지 않았고, 다른 방식의 동등 수정이 없다는 결론도 아니다. Linux 7.3.5 역시 소스 조사만 했으며 실제 GPU Pass/Fail 결과가 없다.

### 화면 종료는 별도 현상

장시간 Animate2 실행 중 AMDGPU 그래픽 큐 timeout과 GNOME 세션 종료가 관측됐고, 다른 시점에는 GNOME Shell의 키맵 관련 충돌이 기록됐다. Chrome의 GPU 가속 변경 시험은 다른 화면 프로세스를 모두 제거한 대조가 아니었다. **이 화면 종료와 HSA 재매핑 손상이 같은 원인인지 확인되지 않았다.** 정황과 한계는 [그래픽 세션 조사](rocm-graphics-reset-investigation.md)에 별도로 기록한다.

## 원인 해석과 현재 대응

기본 드라이버의 CPU 페이지 테이블 갱신 경로에는 입력 펜스가 없을 때 TLB 펜스 생성을 건너뛰는 분기가 있다. 실제 실패 구간에서 해당 조건이 관측됐고, TLB 관련 경로를 추가하거나 31.70의 해당 호출을 제거하는 개입에 따라 HSA와 VAE 결과가 달라졌다. 이는 **GPU 주소 재사용 뒤 드라이버의 무효화·동기화 경로가 관여한다는 강한 근거**다. GPU의 물리 TLB 내부 항목을 직접 판독하지 못했으므로 최초 하드웨어 상태나 단일 코드 줄을 확정된 근본 원인으로 표현하지 않는다.

현재는 운영 Animate2의 `expandable_segments:False`와 VAE·추론 경계의 비유한 값 검사를 유지한다. 정식 커널·드라이버가 갱신되면 [드라이버 설치와 갱신 후 점검](rocm-inference.md#드라이버-설치와-갱신-후-점검)의 HSA 진단 및 모델별 회귀 시험을 수행하고, 통과해도 별도 검토 없이 우회 설정을 해제하지 않는다.

## 시험 환경 정리 상태

2026-11-19 시험 후 일반 `7.0.0-43-generic` 부팅 상태에서 7.4-rc3 시험 이미지·모듈 패키지와 시험 GRUB 메뉴·자동 진단 서비스를 제거했다. `/boot/vmlinuz`와 `/boot/initrd.img`는 일반 7.0 부팅 파일을 가리킨다. MOK 인증서·키와 로컬 실험 기록은 보존했으며, 정리 후 새 부팅 검증은 수행하지 않았다.
